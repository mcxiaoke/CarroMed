# 易用性改造方案（对标 MyTherapy）

> 2026-09-29 · 依据用户实机截图（`F:\Temp\1111`，MyTherapy 中文版）× 本项目代码核实
> 状态：**已全部实施**（4 个 commit：`d896712` / `faf59b8` / `c644087` + 前置的 `8f6f630`）
> 测试 420 项全绿，走查 41/41。本文档保留作为**决策依据与取舍理由**的记录。

**改动一览**：① 新建药品去掉提醒大块 ② 服药记录独立详情页（2 天内可撤销/跳过/确认）
③ 进展页：7 天矩阵 + **服药流水**（跨月分页、按日分组、含补录记录）+ 单药历史页。

## 实施期间与本方案不一致的地方（以代码为准）

| 方案原文 | 实际落地 | 原因 |
| :--- | :--- | :--- |
| §3.2 时间**永远只读** | 手动补录的记录**可改时间** | 方案里"只有 `slot_id == null` 允许全改"是对的，但我在实现时先做成全只读，随后发现文案对 PRN 记录说"计划内的服药不能改时间"是**错的** —— 补录记录根本没有计划。补上 `editDose(newActualTs)` 与日期时间选择器 |

| §5 分 4 步 | 实际 3 个 commit（第 3、4 步合并） | 单药历史与新建页瘦身共用同一批导航改动，拆开反而会产生一个编译不过的中间态 |

## 0. 先说被否掉的一个提议

方案初稿里我提议"给 PRN 药在今日清单加常驻记一次入口"。
**用户指出这是重复设计** —— 核实后确认用户是对的：

`ManualDoseScreen` 已经是完整的一次性服药入口，且能力齐全：

| 能力 | 现状 |
| :--- | :--- |
| 从药箱选药 | ✅ `uiState.medications.forEach` |
| 指定日期 + 时间 | ✅ 且**拒绝未来时间** |
| 剂量 / 备注 | ✅ |
| 库存联动开关 | ✅（未开启追踪时置灰） |
| 底层落库 | ✅ `logManualDose(..., slotId = null)` |

`slot_id == null` 正是"无排班的那条记录"——**PRN 的数据通路早就打通了**，
缺的只是一个 UI 入口，而它已经存在。

真正要修的是另一件事：**进展页流水只取 `todaySlots`，
手动补录的记录因此不显示**。详见 §3.2。

## 1. 三个改动的前提：数据层现状

先把"已经有什么"和"要加什么"分清，避免重复劳动。

| 能力 | 现状 | 说明 |
| :--- | :--- | :--- |
| `PolicyType.PRN` | ✅ 枚举里已有 | `SlotProjectionEngine` 对它 `return emptyList()` |
| A2 不变量（每药恰好一行 `reminder_settings`） | ✅ 保持不变 | 该表存的是**行为设置**（推迟/暂停/重要提醒），与"有无排班"无关 |
| `undoDose(slotId)` | ✅ 已有 | 槽位回 PENDING、事实标 REVERTED、台账冲正 |
| `skipDose` | ✅ 已有 | |
| `RecordStatus.REVERTED` | ✅ 已有 | |
| `dose_records.note` | ✅ 列存在 | |
| `logManualDose` | ✅ 已有 | `slotId = null` 即 PRN 记录 |
| `getRecordsForMedication` | ✅ 查询已存在 | 按 `actual_ts DESC` |
| 改剂量 / 改时间 | ❌ 缺 | 需要新增 |
| 物理删除记录 | ❌ **刻意不做** | 见下 |

### 1.1 为什么不做"删除"

`DoseRecordDao` 第 16 行明确写了不提供任何 `@Delete`，理由成立：

- 第二承诺是"吃过的药永不丢失"；
- 台账 `inventory_transactions.record_id` 会变成悬空引用。

**撤销（REVERTED）在语义上就是删除**——记录仍在库里，只是不再计入统计。
所以详情页提供"撤销"，不提供"物理删除"。

## 2. 改动一：新建药品去掉提醒大块

### 2.1 决定

- **详情页的"提醒设置"完全不动**（用户明确要求）。
- 新建页**删除**"提醒频次与时间"整段（现在的 `SectionCard(index = 3)`）。
- 保存后**直接跳药品详情页**，用户在已有的"提醒设置"里配置。
- "注意事项 / 禁忌"（`SectionCard(index = 2)`）**移到最后并默认折叠** ——
  低频操作占了太大版面。

### 2.2 段位重排

| 现在 | 改后 |
| :--- | :--- |
| 1. 药品基本信息 | 1. 药品基本信息 |
| **2. 注意事项 / 禁忌** | **2. 初始库存 (选填)** |
| **3. 提醒频次与时间** | **3. 注意事项 / 禁忌（默认折叠）** |

### 2.3 数据层影响：无

- `saveProfile` 已经独立于提醒计划，`AddEditMode.FULL` 的 `policyRequired`
  是**新建**路径专用的。
- 需要确认：`med_add` 保存成功后原本停在列表，改为 `navigate(detail/medId)`。
- 新建时若用户没配计划，**不写 `schedule_policies`**。
  下游读路径（药箱、详情、闹钟）必须容忍"无 active policy"——
  `getActivePolicyForMedication` 返回 null 是既有合法路径（PRN 药就是这么用的）。

### 2.4 风险

⚠️ **新建的药默认没有任何提醒**。用户加完可能直接以为"设好了"，
结果永远不响。这与本项目 §2 第 6 条"静默降级 = 给用户虚假的保证"同源。

**对策**：详情页在 `getActivePolicyForMedication == null` 时，
在"提醒设置"卡片上显示醒目提示「**尚未设置服药计划，点击设置**」，
而不是让它长得跟已配置的一样。**诚实的空缺好过虚假的保证。**

## 3. 改动二：服药记录详情页

### 3.1 入口与时限（对标 MyTherapy）

用户从今日清单 / 进展页流水点 item → 独立页面 `DoseRecordEditScreen`。

| 距今 | 可用操作 |
| :--- | :--- |
| **≤ 2 天** | 标记为**已确认 / 已跳过 / 撤销**（三个动作齐全） |
| **> 2 天** | **只读**，撤销与跳过入口**不显示**（不是置灰） |
| 任意时间 | 备注、剂量、时间（按 §3.3 的规则） |

**2 天规则的落点**：这是**产品规则**，不是数据规则。
判定用 `ChronoUnit.DAYS.between(recordDate, today) <= 2`。
2 天外的记录走只读分支，**不查询、不构造**那些操作入口。

### 3.2 页面内容

```
┌─────────────────────────────┐
│ ←  醋酸泼尼松        (状态) │
├─────────────────────────────┤
│  剂量    [ 1        ] 片     │  ← 可改（见 §3.3）
│  时间    2026-09-29  09:00   │  ← 可改（见 §3.3）
│  备注    [              ]    │  ← 自由文本
├─────────────────────────────┤
│  [确认]  [跳过]  [撤销]      │  ← 仅 ≤2 天
└─────────────────────────────┘
```

### 3.3 关键约束：槽位来源的记录不许改时间和剂量

`dose_records` 有两种来源：

| `slot_id` | 来源 | 允许的操作 |
| :--- | :--- | :--- |
| `!= null` | 闹钟打卡 | **只改备注、改状态** |
| `== null` | 手动补录（PRN） | 全部可改 |

**理由**：槽位来源的记录如果改了时间，事实行 `actual_ts` 与
`dose_slots.scheduled_time` 就分叉了——两处各说一个时间。
这与本轮已修的 C-40（`scheduledTs` 用回退值、`scheduledTime` 留坏串）
是**同一类缺陷**，不能新造一个。

所以页面上：来源为槽位时，剂量与时间**只读并附一行说明**
「计划内的服药不能改时间与剂量，可撤销后重新打卡」。

### 3.4 改剂量必须动台账

用户已确认：**要回补库存**。

`DoseTrackingService` 新增：

```kotlin
suspend fun editDose(
    recordId: Long,
    newDoseAmount: Float?,   // null = 不改
    newActualTs: Long?,      // null = 不改
    newNote: String?         // null = 不改
): Boolean
```

改剂量的算法（**台账只增不改**，绝 UPDATE 原流水）：

1. `net = inventoryDao.getSumOfChangeByRecordId(recordId) ?: 0`
   —— 这正是 `undoDose` 已有的净额口径，沿用不另发明。
2. 若 `net < 0`（说明这条记录确实扣过库存），补一条
   `changeAmount = -(newDose - oldDose)` 的冲正流水，
   `txType = DOSE_EDIT_ADJUST`（**新枚举值**）。
3. 走 `appendLedger`，`balanceAfter` 由它统一计算，**I2 不可能分叉**。

改时间 / 改备注不产生台账流水。

### 3.5 与撤销的交互

`undoDose` 当前签名是 `undoDose(slotId)`。
手动补录的记录 `slot_id == null`，**无法撤销**——
需要新增 `undoManualDose(recordId)`，语义与 `undoDose` 一致：
事实标 REVERTED + 按净额补冲正流水。

**这是个真实的缺口**：现在撤销一个 PRN 记录没有任何路径。

## 4. 改动三：进展页

### 4.1 「今日服药流水」→「服药流水」（跨月分页 + 按日分组）

用户修正了原方案：**只显示今日没有意义**——首页「今日」Tab 干的就是这件事。
进展页要给的是**历史**。

#### 4.1.1 两个必须先解决的语义问题

**① 数据源从槽位换成事实行**

现在 `timeline` 构造是 `todaySlots.map { ... }`，只覆盖**有排班**的槽位。
而服药事实（`dose_records`）有两个来源：

| 来源 | `slot_id` | 现在可见？ |
| :--- | :--- | :--- |
| 闹钟打卡 | `!= null` | ✅ |
| 手动补录（PRN / 忘记打卡） | `null` | ❌ **完全不可见** |

**这是本轮要修的真缺陷**：PRN 药手动补录后，今日清单查得到，进展页流水里没有。
跨月改造顺带把它一起解决——数据源直接换成 `dose_records`。

⚠️ 换源后行为变化：**未打卡的 PENDING 槽位不再出现在流水里**。
这是对的——"流水"记录的是**已发生的事实**，不是计划。
待服清单是首页的职责。

**② REVERTED 记录要不要显示**

`undoDose` 不物理删除，只把事实标 `REVERTED`。跨月视图会翻出很久以前的记录，
用户可能想知道"这条为什么没了"。**显示，但置灰 + 「已撤销」标签**
（沿用本轮 M7-2 已加的 chip）。

`SKIPPED` 同样显示（它是用户主动动作，有信息量）。

#### 4.1.2 分页策略：keyset，不用 OFFSET

```sql
SELECT * FROM dose_records
WHERE actual_ts < :beforeTs          -- 游标（严格小于，避免重复）
ORDER BY actual_ts DESC
LIMIT :pageSize
```

**为什么不用 `LIMIT offset, n`**：offset 分页在往回翻时，
前面若有记录被撤销/删除，会**整段错位漏记录**。
游标分页对数据的变更免疫——这与本项目"历史只追加不改"的取向一致。

✅ `dose_records` 已有 `Index(value = ["actual_ts"])`（`DoseRecordEntity:27`），
游标查询走索引，**无需加索引、无需升 schema 版本**。

**首屏**：`beforeTs = Long.MAX_VALUE`（即今天末尾），`pageSize = 60`（约一个月的量级）。
**触底**：`beforeTs` = 已加载的最小 `actual_ts`，再取 60 条。
**到底判定**：返回条数 < `pageSize`。

**边界**：日期按**本地时区**从 `actual_ts` 分组。
跨时区/夏令时不在本轮范围（现有代码已统一用 `ZoneId.systemDefault()`）。

#### 4.1.3 按日分组

参照 MyTherapy 的「列表」视图（截图 `15-05-04`）：
按天分节，节内按时间倒序，节头显示「星期二, 26/9/29」。

用 `LazyColumn` + `stickyHeader` 效果（`stickyHeader` 是实验 API，
需加 `@OptIn(ExperimentalFoundationApi::class)`）。
节头展示当天该节的记录数与合计剂量。

#### 4.1.4 UI 落点

- 进展页 tab 文案：`今日服药流水` → **`服药流水`**
- 空态文案改写：现在写的是「今天没有排班…」，
  跨月后不成立 → 「还没有服药记录。用「手动补录」记录临时用药。」
- 药品名、剂量、备注、状态 chip 沿用现有 `TodayTimelineCard` 的渲染，
  **不重写**。

⚠️ 现有 `TimelineItem` 持有 `slot: DoseSlotEntity`，
换源后要改成持有 `record: DoseRecordEntity` + `medication`。
这是**该文件的结构性改动**，不是加个字段。

### 4.2 单个药品的历史页

`ProgressScreen` 每行卡片右边的 `>` → `MedHistoryScreen(medId)`。

- 数据源：`doseRecordDao.getRecordsForMedication(medId)`（**已存在**，倒序）
- 按月分组（对齐 MyTherapy 的"2026年9月"，截图 `15-00-04`）
- 每行点进 §3.2 同一个详情页，**复用入口**
- 同样纳入 REVERTED（置灰）

### 4.3 7 天矩阵：多次服药的可视化

MyTherapy 用**上下两个圆点**表示一天两次（环孢素那行两圆点一目了然）。
我们现在是单圆点，**1/1 与 2/2 在视觉上分不出来**。

改法：`total > 1` 时纵向排列 N 个小圆点（`Column`），
`total == 1` 时保持现状。PARTIAL 的浅底深字方案沿用本轮已修的配色。

### 4.4 "图表 / 列表"双视图

MyTherapy 的进展页有这个切换。对齐：**不加**（用户说"功能尽量对齐，UI 不用完全一样"），
我们已有"7 天打卡矩阵 / 今日服药流水"双 tab，功能上覆盖了。

## 6. 测试要补的（每条都要能失败）

| 测试 | 守什么 |
| :--- | :--- |
| `editDose` 改剂量后 I1/I2 仍成立 | 台账只增不改，余额不分叉 |
| `editDose` 改剂量后 `SUM(change_amount)` 等于新剂量 | 改剂量真的改了账 |
| 槽位来源的记录 `editDose` 拒改时间剂量 | §3.3 约束生效 |
| `undoManualDose` 后该记录不计入统计、账目回补 | PRN 撤销通路 |
| **补录记录（`slot_id == null`）出现在服药流水** | §4.1 修掉的缺陷 |
| **翻页时无重复、无遗漏** | keyset 游标用严格小于；构造"同一天多条" fixture |
| **翻页中途 REVERTED 某条，后续页不漏不重** | 游标分页对数据变更免疫（OFFSET 会错位） |
| **流水含 REVERTED 且被标灰** | §4.1.1 ② |
| **未打卡的 PENDING 槽位不进流水** | 流水只记事实 |
| 无 active policy 的药详情页显示"尚未设置计划" | §2.4 的诚实提示 |

⚠️ 分页测试要**避开本项目记录过的时点陷阱**（AGENTS.md §3）：
断言按「日期集合 + 记录 id 集合」，**不要按条数**，
否则 fixture 时点一跨天就变色。

## 7. 明确不做

- **物理删除服药记录** —— 会让台账 `record_id` 悬空，违反第二承诺。
- **详情页提醒设置改成两张卡** —— 用户明确要求不动。
- **PRN 药常驻"记一次"按钮** —— 手动补录已是完整入口，重复设计。
- **进展页"图表/列表"切换** —— 现有双 tab 已覆盖。
- **服药流水加筛选（按药 / 按状态）** —— 先不做，等真实使用反馈。
  MyTherapy 有，但我们的药量级（几十味）下分组已够用。
- **流水页预取 / 缓存策略优化** —— 首屏 60 条走索引，
  实测不够再优化。**先量再优化**，不做想象中的性能工程。
