# CarroMed 方案架构审查报告

> **版本**：v1.0
> **日期**：2026-09-27
> **审查范围**：`docs/APP_DESIGN_SPEC.md` (v1.0)、`docs/ARCHITECTURE.md` (v2.0)、`docs/UI_DESIGN.md` (v1.1)、`docs/demo/index.html`
> **审查性质**：仅针对方案架构与设计，不涉及具体代码实现。
> **总体结论**：核心设计思想（三层时序解耦、事件溯源库存账本、软归档、规则版本化）方向正确，明显优于同类初级方案。但存在 **1 个结构性缺口（槽位层无存储设计）、5 处会直接导致实现返工的高危问题**，以及一批文档间口径冲突。建议在动工前先解决 P0 项并做文档治理。

## 一、P0 级问题（结构性，动工前必须解决）

### P0-1 三层模型的"槽位层"没有存储设计，ER 图与场景描述自相矛盾

这是整个方案最大的结构性缺口。

ARCHITECTURE.md 第二章明确画了三层：规则层 → **槽位层 (Daily Dose Slots)** → 事实层。但第三章的 ER 图只有 4 张表（MEDICATIONS / SCHEDULE_POLICIES / DOSE_RECORDS / INVENTORY_TRANSACTIONS），**槽位层没有任何表**。

矛盾在于，第四章的场景高度依赖槽位状态的持久化：

- **场景 1**：将 PENDING 槽位标记为 `CANCELLED_BY_RULE_CHANGE` 并取消闹钟——这条状态写到哪？规则已截断换版，若槽位是"每次从当前规则实时投影"派生的，旧规则的槽位第二天重算时就不存在了，`CANCELLED_BY_RULE_CHANGE` 无处安放；
- **场景 6**：槽位持有 `snooze_target / snooze_count` 状态机——推迟后 App 被杀，这些状态如何恢复？若纯靠重算，"推迟中"信息丢失；
- **今日页面**的 PENDING/SNOOZED 列表展示同样需要槽位有真源。

**建议**：补一张 `DOSE_SLOTS` 物化表，字段至少含 `(id, date, medication_id, policy_id, scheduled_time, status, snooze_target, snooze_count, updated_at)`。由"调度对齐引擎"负责生成/回填/结算，状态机落库。这张表同时解决 P0-2（MISSED 结算）、P0-5（RequestCode 可直接用 slot id）、场景 6 的 snooze 持久化。备选方案是明确声明"槽位为纯派生视图"并给出派生算法 + 状态如何外化，但那样复杂度反而更高，不推荐。

### P0-2 MISSED（漏服）状态的结算机制完全缺失

"全天未打卡视为漏服"只定义了语义，没有定义**谁、在什么时机、用什么流程**把 PENDING 槽位写成 MISSED。这不是小事：

- 统计 SQL 的分母（应服总次数）由 TAKEN+MISSED+SKIPPED 构成，若 MISSED 从未被结算，依从率分母失真、虚高；
- "用户整天没打开手机"恰恰是本 App 目标用户（漏服药的人）的典型行为，不能假设"打开 App 时顺带结算"就足够；
- 结算还涉及顺序问题：次日零点结算昨日未服槽位时，若用户 00:05 才补打卡昨晚 22:00 的药，已结算的 MISSED 要能被补录覆盖回 TAKEN。

**建议**：设计一个 Missed Settler（结算器）：每日零点由零点闹钟触发一次对前一日 PENDING 槽位的批量结算；App 启动时再兜底结算"历史上所有已过结算线但仍为 PENDING 的槽位"（覆盖用户多天不开机的回填）。补录时允许 MISSED→TAKEN 转换并写 updated_at。

### P0-3 两代方案并存、无权威源声明，三份文档三套口径

APP_DESIGN_SPEC.md (v1) 与 ARCHITECTURE.md (v2) 是**两代不同的数据模型**，但 v1 没有任何"已被 v2 取代"的标记。实现者打开 docs 目录看到的第一份文档就是 v1，按它建表必然返工。具体冲突清单：

| 维度 | APP_DESIGN_SPEC v1 | ARCHITECTURE v2 | UI_DESIGN v1.1 |
| :--- | :--- | :--- | :--- |
| 排程表 | REMINDER_SCHEDULES（无版本化） | SCHEDULE_POLICIES（版本化） | — |
| 打卡表 | DOSE_LOGS | DOSE_RECORDS | — |
| Tab 命名 | 今日/药品库存/历史日历/统计 | — | 今日/**药箱**/**进展**/统计 |
| 状态枚举 | TAKEN/SKIPPED/MISSED/SNOOZED | +REVERTED、槽位层另有 PENDING/CANCELLED_* | ✅/⏳ 图标 |
| 通知按钮 | 已吃/推迟**15m**/跳过（3 个） | 已吃/推迟**30m**/推迟**1h**/跳过（4 个） | 同 v2 |
| 库存流水 type | DOSE_AUTO_DEDUCT/REPLENISH/INVENTORY_CHECK | AUTO_DEDUCT/REVERT_ROLLBACK/REPLENISH/INVENTORY_CHECK，场景 3 又引入 MANUAL_INTAKE/DOSE_CORRECTION | — |
| 库存字段 | alias/desc/precautions/icon 等丰富字段 | 精简为 name/category/description | 用到 precautions 展示 |

**建议**（文档治理，见第五章）：确立 ARCHITECTURE v2 为唯一技术权威源；APP_DESIGN_SPEC v1 顶部加"已废弃，以 ARCHITECTURE 为准"横幅或直接删除归档；UI_DESIGN 与 v2 对齐 Tab 命名与按钮规格。另：UI_DESIGN 是与 v2 对齐的，但 v1 与 v2 的功能字段（alias/precautions/icon）取舍需要拍板——UI 线框里"⚠️ 注意事项"卡片在多处出现，若按 v2 精简模型，注意事项只剩 description 一个自由文本字段，快捷标签体系就没有落点，**字段取舍会影响 UI 设计，需明确决策**。

### P0-4 依从率统计口径三处互相矛盾，且 v2 的 SQL 区间过滤维度是错的

- **v1（第六章）**：依从率 = "TAKEN 且在计划时间 ±60 分钟窗口内" / 计划总次数，有"准时窗口"概念；
- **v2（第七章 SQL）**：`WHERE d.actual_time BETWEEN :rangeStart AND :rangeEnd`——用**实际时间**做区间过滤是错的：补录昨天的药会被算进今天；22:00 的药 00:30 推迟跨天服用会被算进次日；而"过去一年"报表的语义应该按**计划时间**归属；
- **v2 的"按时率"**：`TAKEN / (TAKEN+MISSED+SKIPPED)`，完全没有 ±60 分钟窗口概念，"推迟 2 小时才吃"也算"按时"，与 v1 定义冲突；
- **REVERTED 的处理**：撤销后重新打卡，是新增一条记录还是复用原记录改状态？两种做法统计结果不同，未定义（与 P1-8 关联）。

**建议**：单独写一份《统计口径规范》，明确：① 区间归属以 scheduled_time 为准；② "按时"的窗口定义（建议 ±30 或 ±60 分钟，作为常量）；③ 撤销重打的记录规则；④ 补录（is_manual=1）是否计入依从率的分子；⑤ 跨天推迟服用的归属规则。统计是本 App 的核心卖点之一，口径必须在写第一行统计代码前定死。

### P0-5 RequestCode 号段算法存在整数碰撞硬伤

场景 6 的公式：`RequestCode = med_id × 10000 + hour × 100 + minute`，推迟闹钟用 `RequestCode + 500000`。

**500000 = 50 × 10000**。当 `med_id ≥ 50` 时，该药的**正常闹钟** RequestCode（如 med_id=50 的 08:30 → 500000+830）与 `med_id=0~49` 药品的**推迟闹钟**号段（如 med_id=0 的正常码 +500000）**正面相撞**，互相覆盖/互相取消。数据库自增 id 很快就会超过 50，这不是边界情况，是必然触发。

**建议**：不要用算术拼号段。既然补了 DOSE_SLOTS 表（P0-1），`RequestCode = DOSE_SLOTS.id`（全局唯一自增）即可，正常闹钟与推迟闹钟天然隔离，代码也最简单。若坚持无表方案，也应以 `med_id × 10_000_000 + slot_seq` 这类足够大的乘子并显式划段，但不如前者干净。

### P0-6 精确闹钟权限被拒后的降级链路完全缺失，且 Play 政策风险未评估

第三章（v1）与第五章（v2）都默认 `setExactAndAllowWhileIdle()` 一定可用，但：

- Android 12+ 的 `SCHEDULE_EXACT_ALARM` **默认拒绝**，需用户手动到设置里授予；Android 14+ 趋势收紧；
- `USE_EXACT_ALARM` 是普通权限自动授予，但 **Google Play 政策将其限定为日历/闹钟类核心用途 App**，服药提醒类是否算"alarm clock app"处于灰色地带，上架 Play 有被拒风险（若只发 APK/国内渠道则无此风险，但文档未声明分发渠道）；
- 最关键的：**用户拒绝授权（或国产 ROM 静默回收）之后 App 走什么路径，方案只字未提**。setExactAndAllowWhileIdle 不可用时静默降级到 inexact alarm，在 Doze 下可能延迟数小时——对"精准提醒"这一核心承诺是致命的。

**建议**：设计三级降级链并写入方案：① `setExactAndAllowWhileIdle`（有权限时）；② 无权限时 `setAlarmClock()`（闹钟型，不受 Doze 限制，精度足够且不需 exact 权限，是最合适的兜底）；③ 两者皆不可用时 inexact + App 启动时对账补偿。同时在"防漏提醒自检页"中把 exact alarm 权限检测作为第一项。

## 二、P1 级问题（功能与设计缺口）

### P1-1 缺少"持续/重复提醒"机制——老人场景的核心需求缺位

Heads-up 通知只横幅浮现几秒，锁屏后一条通知可能永远不被看到。同类 App（MyTherapy/Medisafe）均有"持续响铃直到确认"（insistent alarm）能力。目标用户里有"需要被提醒才吃药"的人，一次性通知是不够的。

**建议**：增加可选的"强提醒模式"：闹钟触发后全屏响铃 Activity（setAlarmClock 类闹钟体验）或重复通知（未确认前每 N 分钟再响），直至用户确认/跳过。这同时自然覆盖 P0-6 的降级（setAlarmClock 路径与强提醒共用）。另外**勿扰模式**未在保活章节覆盖：需引导用户将渠道加入勿扰白名单（或使用可绕过勿扰的 RINGER/ALARM 音量通道）。

### P1-2 纯本地 + 仅手动备份 = 数据单点，卸载即全丢

方案只有手动 JSON 导出。Android 卸载应用会连同沙箱数据一起清除；手机丢失/损坏同理。用户一年服药历史无任何自动保护，与"数据 100% 归用户"的定位相悖。

**建议**：增加自动备份设计——每日/每周通过 SAF 写入用户指定的外部目录（如 Downloads/CarroMed/），保留最近 N 份轮转；备份时机选在每日结算后（数据一天只变一次完整快照，时机天然合适）。

### P1-3 隐私设计与"注重隐私"定位自相矛盾

- v1 明确"支持分享到微信、QQ、网盘"——明文 JSON 包含完整病史与用药记录，经第三方 IM/网盘传输与留存，隐私风险显著；
- 锁屏通知直接显示药品名（"环孢素 10:30"），对不想让旁人知道自己病情的用户是隐私泄露；
- 无应用锁（PIN/生物识别）选项。

**建议**：① 备份支持可选口令加密（如 AES-GCM + passphrase，或至少提供"加密 zip"）；② 通知渠道提供"锁屏隐藏详情"开关（showWhenLocked/visibility 配置）；③ 应用锁列为可选功能（P2 优先级即可，但方案应提）。

### P1-4 `time_doses_json` 用 JSON 列存时间-剂量组合，建模粒度过粗

SCHEDULE_POLICIES 把 `[{time, dose}]` 塞进一个 JSON 文本列。问题：

- 只改 22:00 一个时间点的剂量，也要整条规则换版本，历史无法表达"只改了哪个时间点"；
- 统计页"每天 2 次（10:30 和 22:00）"的展示需要解析 JSON（SQLite JSON1 可用但失去索引与外键能力，Drift 侧类型也不友好）。

**建议**：拆出 `SCHEDULE_POLICY_TIMES(policy_id, time_of_day, dose)` 子表，一行一个时间点。版本化语义不变（对时间点行的增删改仍通过 policy 换版实现），但查询与展示回归关系模型。

### P1-5 库存模型四个具体缺陷

1. **单位语义不闭环**：剂量单位含 ml/滴，但滴眼液"每次 1 滴"无法换算成"库存 X 支"的扣减粒度（1 瓶 = 多少滴？）。建议外用/滴剂类药品提供"不跟踪库存"开关；
2. **REAL 浮点对账**：`真实库存 = SUM(change_amount)` 用浮点累加必有精度误差，对账比较需整数化（以最小步长 ×1000 存整数）或明确容差；
3. **负库存策略未定义**：打卡时库存不足，是允许扣成负数（仅提醒），还是阻止？必须定义（建议：允许扣负 + 醒目提示"库存不准，请盘点"，绝不阻止服药记录——服药是事实）；
4. **流水无单位快照**：若用户中途把药品单位从"片"改为"mg"，历史流水的 change_amount 语义漂移，SUM 对账直接错。建议：改单位视为盘点事件强制走 INVENTORY_CHECK 平账，或流水加 unit 快照字段。

### P1-6 撤销语义二义未定案，且未区分"槽位层"与"事实层"的撤销

场景 2 写"状态从 TAKEN 转为 REVERTED（**或**重新回到 PENDING）"——括号二选一没有定案，两种语义完全不同。正确做法是把两层分开：**槽位层**回 PENDING（今天还能再打）、**事实层**记录保留并标 REVERTED（审计留痕）。这个二义同时污染统计口径（P0-4）。补 DOSE_SLOTS 表后此问题自然消解，但方案需把两层撤销写成定案。

### P1-7 槽位生成的回填与竞态未设计

"每天零点或进入今日时生成槽位"：用户三天不开机，中间两天的槽位与 MISSED 结算需要回填，回填顺序（先生成后结算、避免重复结算）未描述；23:59 打卡与 00:00 结算/新日生成的竞态未考虑。补 DOSE_SLOTS 表 + Missed Settler 后一并定义回填流程即可。

### P1-8 UI 展示了数据模型无法表达的数据（"记水"）

UI_DESIGN 今日页线框里有"✓ 晨起空腹温开水 (250ml) 已服"，APP_DESIGN_SPEC 也有"+ 临时加服/**记水**"。但 DOSE_RECORDS.medication_id 是非空外键，**"温开水"不是药品，塞不进模型**。这是模型与 UI 直接冲突的实锤。二选一：① 明确砍掉饮水记录（从两份文档删除）；② 把 medication_id 改为可空并引入"非药品条目"类型。建议 ①（砍 scope），饮水不是本 App 核心价值。

### P1-9 疗程药结束提醒缺失

SCHEDULE_POLICIES 有 effective_until 字段，但 UI 没有任何"疗程配置"入口（如"阿莫西林吃 7 天"），疗程到期后也没有"该停药了，是否归档"的提醒交互。抗生素吃满疗程正是 v1 自己强调的场景（"完成整个疗程"出现在注意事项示例里），规则层支持但交互层断裂。

## 三、P2 级问题（打磨与规范）

### P2-1 里程碑无验收标准（DoD）与测试策略

M1~M6 只有任务清单没有验收标准。尤其 M3（提醒可靠性）必须有真机测试矩阵：Doze 模式、杀后台、重启、勿扰、exact 权限被拒、主流国产 ROM（MIUI/HyperOS、ColorOS、OriginOS）差异——保活这件事不真机验证等于没做。调度对齐引擎、库存对账、MISSED 结算是纯逻辑模块，应规定单测覆盖。建议每 Milestone 补一段 DoD。

### P2-2 技术选型留白过多

状态管理"Riverpod / ValueNotifier"二选一未定；更关键的是**通知动作回写数据库的执行路径**（通知栏点"已吃"→ 广播接收器里开 Drift 事务）需要原生代码：BroadcastReceiver 有 ~10 秒限制，直接在原生层写 SQLite 还是拉起 Flutter 引擎（慢且易超时）？这决定要不要自研原生模块，属于架构级决策，应在方案中定下来（建议：原生 receiver 直写 SQLite，App 前台通过 Stream/事件感知刷新——Drift 的表变更通知恰好支持）。另需评估 `android_alarm_manager_plus` 等包的维护状态，可能需自研 plugin。

### P2-3 药品名错别字："环孢素" 应为 "环孢素"

ARCHITECTURE.md 与 UI_DESIGN.md、demo 原型中共出现 10+ 次"环孢素"，正确写法是**环孢素**（Cyclosporine，免疫抑制剂）。医疗类应用出现药品名错别字会直接损伤专业可信度，全部文档与示例数据需修正。

### P2-4 索引与性能设计缺失

"毫秒级统计一年数万条记录"的承诺下，没有任何索引设计。至少需要：`dose_records(medication_id, scheduled_time)` 复合索引、`dose_records(status)`、`inventory_transactions(medication_id, created_at)`、`dose_slots(date)`。数据量级小，问题不大，但应写进 schema 设计。

### P2-5 Schema 迁移与备份版本兼容策略缺失

Drift 的 schema migration 策略、JSON 备份的 schema_version 升级/降级兼容规则（新版本 App 导入旧备份、反之）均未提及。导出一致性也需定义（导出期间正在打卡：应在单事务内做快照导出）。

## 四、时区与时间语义（横切问题，需一句话定案）

全案未声明时区策略。建议直接写明：**所有时间按设备本地时区存储与计算，不做 UTC 归一、不做跨时区适配**（目标用户为中国大陆，无夏令时，该简化成立且大幅降低复杂度）。但需注意两个残留点：① anchor_date 与时间戳两种表示并存（TEXT 日期 vs INTEGER 时间戳），换算规则要写死（建议规则层统一存本地时间戳，展示层转 HH:mm）；② 隔 N 天规则基于"本地日历日"而非 86400×N 秒，避免任何潜在 DST/时间调整漂移。

## 五、更好的做法（文档治理与建议汇总）

1. **确立单一权威源**：`ARCHITECTURE.md` (v2) 为唯一技术权威。APP_DESIGN_SPEC v1 顶部加"⚠️ 本文档数据模型已被 ARCHITECTURE v2 取代，仅存档"横幅（或移入 docs/archive/）；UI_DESIGN 修正 Tab 命名、按钮规格与 v2 对齐；demo 原型同步。**在补齐废弃标记前，v1 就是最大的返工风险源。**
2. **补一张 DOSE_SLOTS 物化表**（P0-1），它是六个场景中四个的地基，同时解决 RequestCode（用 slot id）、snooze 持久化、MISSED 结算三个问题——一次投入解决四个 P0/P1。
3. **补一个 Missed Settler 设计**（P0-2），与每日零点闹钟、App 启动兜底、补录覆盖规则一起写进第四章。
4. **写一份《统计口径规范》**（P0-4），作为统计功能的验收依据。
5. **设计三级闹钟降级链**（P0-6）：exact → setAlarmClock → inexact+对账，并明确分发渠道（Play or APK）以评估 USE_EXACT_ALARM 政策风险。
6. **需求分级砍 scope**：建议明确 P0（今日打卡+提醒+库存+导出）/ P1（统计报表、强提醒、自动备份）/ P2（应用锁、桌面 Widget、加密备份、非药品条目）。Widget 是这类 App 的高频增值需求，目前方案未提，建议进 P2 备选。
7. **术语表（GLOSSARY）**：Slot / Record / Policy / Transaction 四个词在文档里一词多义（如"打卡记录"同时指槽位和事实），建议加术语表，一词一义。
8. **示例数据勘误**：环孢素错别字、v1 示例"硝苯地平控释片整片吞服严禁嚼碎"这类内容是对的、可保留，但所有示例药品名统一从 v2 术语表取。

## 六、审查结论

方案的核心抽象（规则版本化、事实不可变、账本式库存）经得起推敲，v2 相比 v1 的演进方向正确。当前最大的风险不在"想错了"，而在：

1. **槽位层说了没设计**（P0-1）——三层模型是全案的骨架，中间一层悬空；
2. **两代文档并存**（P0-3）——按 v1 实现等于推倒重来；
3. **可靠性承诺没有降级路径**（P0-6）——"精准提醒"是产品的第一承诺，Android 权限现实面前它是脆弱的。

建议动工顺序：先做文档治理（半天）→ 补 DOSE_SLOTS + Settler + 统计口径三份设计（1~2 天）→ 再启动 Milestone 1。方案补强后，这个架构可以支撑长期演进，不需要推倒。
