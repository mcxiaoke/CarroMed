## 0. 结论摘要

### 0.1 总体评价

**优点（应保留，不要在重构中丢掉）**

| 项 | 说明 |
| :--- | :--- |
| 三层时序解耦 | 规则 / 槽位 / 事实分离，方向完全正确，是本方案最有价值的部分（ARCH:40-72） |
| 双向会计式库存账本 | 用流水而非 `stock = stock - 1` 覆盖，思路专业（ARCH:42, 264-270） |
| 归档优先于删除 | 保护就诊场景的数据连续性，方向正确（ARCH:196-207） |
| 边缘场景清单 | 6 个场景（改计划/撤销/补录/归档/PRN/Snooze）覆盖度高于同类开源方案 |
| 零登录零广告定位 | 在个人健康数据场景下是正确的价值主张 |

**但方案目前处于"文档层已经推倒过一次、且下一次还会推倒"的状态。** 判据很直接：`APP_DESIGN_SPEC` v1.0.0 已经定稿了完整表结构、6 个里程碑和全部线框；`ARCHITECTURE.md` v2.0.0 顶着"防推倒重构"的标题，直接换掉了表名（`DOSE_LOGS` → `DOSE_RECORDS`）、换掉了规则表（`REMINDER_SCHEDULES` → `SCHEDULE_POLICIES`）、丢掉了 v1 的三个字段、合并了两个字段、换掉了统计口径、换掉了 4 Tab 中的一个。**一份以"防推倒"为纲的文档，在发布当天就推倒了上一份文档，这件事本身就是最大的架构问题。**

### 0.2 问题分布

| 严重度 | 定义 | 数量 |
| :--- | :--- | :--- |
| **P0 致命** | 会导致数据失真、提醒丢失、上架/合规事故，或必然引发二次推倒 | 10 |
| **P1 重要** | 核心需求缺失、模型能力不足、体验断裂，改动成本中等 | 32 |
| **P2 优化** | 规范缺失、表述不严谨、可延后 | 12 |
| **需求空白** | 方案中完全未出现、但目标用户必然需要的能力 | 14 |

### 0.3 三句话结论

1. **领域层设计（ARCHITECTURE）质量高于工程层设计**，三层解耦与事件溯源账本是亮点，但两者之间存在一个致命空洞：**"槽位层"在架构图里存在，在数据模型里不存在**（见 P0-2）。
2. **统计口径当前是错的，不是粗糙而是错**：SQL 用 `actual_time` 过滤，导致漏服记录被 WHERE 剔除，依从率会恒等于 100%（见 P0-4）。
3. **不要在 M1 写第一行代码之前，先做 P0-1（文档 SSOT 合并 + schema 冻结 + 5 个 ADR）**。因为第 6 节列出的 10 个决策问题中，有 4 个会直接改变数据模型（主键、量纲、产品边界、疗程），这些问题在写代码前回答的成本是 1 天，在写完数据库后回答的成本是 1 个月的数据迁移。

### P0-2 槽位层（Slot）存在于架构图，不存在于数据模型 —— 架构最大的空洞

ARCH:60-64 把"单日任务槽位层"作为三层解耦的中间层，并让它承载：
- 状态机 `PENDING / SNOOZED / TAKEN / SKIPPED / CANCELLED_TODAY`
- 今日改计划时的差分对齐（ARCH:157-160）
- `snooze_target`、`snooze_count`（ARCH:228）
- AlarmManager 的注册与注销

但第三章的四张表里**没有任何一张是 slot**。这留下一个二选一、且方案没有回答的问题：

- **若 slot 不落库**：`snooze_count`、推迟目标、`CANCELLED_BY_RULE_CHANGE` 这些运行时状态全部在内存里。Android 进程随时可能被杀（Doze、厂商清理、低内存、用户划掉），重启后这些状态全部丢失。后果是：用户推迟的服药被"复活"、今日临时取消的药又冒出来。这是同类 App 最高频的客诉来源。
- **若 slot 落库**：那它就是第 5 张核心表，必须定义幂等键、唯一约束、生命周期、生成时机——而这些在方案里一个字都没有。

同时 ARCH:61 写"每天零点或进入'今日'时生成"。**"零点"在 Android 上是一个不可靠前提**：设备可能关机、可能处于 Doze、App 进程不存在。零点没有进程，槽位就不会被生成；等到用户中午打开 App，"今日"页要么是空的，要么是当场补生成的——两者的行为必须在设计里区分。

**建议**：
1. 明确 slot **落库**，作为领域模型的一等实体（`dose_slots`）。
2. 生成时机改为**读路径惰性物化 + 写路径即时物化**双轨：
   - 读路径：任何时候打开今日页 / 计算报表 / Reconciler 触发时，按"当前有效 policy 展开今天起未来 N 天（建议 N=7）"，**幂等 upsert** 补齐缺失槽位；
   - 写路径：改规则、归档、暂停时立即对账受影响区间。
3. 定义幂等唯一键：`uid_key = hash(policy_id | policy_version | scheduled_ts)`，并加数据库 UNIQUE 约束。**这是"不重复发闹钟"的技术前提，方案完全没提**。
4. slot 明确规定为"可再生缓存"：任何时候可从 policy + 规则变更日志完全重算，因此允许被清理/重建；record 不可变。这个非对称性要在文档里写清楚，否则开发时会有人把 slot 当真相。

### P0-3 「履约事实不可变」原则被自己的场景设计违反

ARCH:38 立法则一：*"每一次服药打卡记录，记录的是真实物理世界中已经发生的客观事实……未来的任何计划变更，严禁破坏已发生的历史记录"*。

但方案自己的两个场景违反它：
- ARCH:171-172：撤销打卡把 `status` 从 `TAKEN` **原地 UPDATE** 为 `REVERTED`。
- ARCH:191-192：改剂量时**原地 UPDATE** `dose_taken = 2.0`，只补一条库存流水。

**更讽刺的是，库存层用了正确的 append-only 模式（补偿流水 + 对冲凭证），打卡层却用了原地修改。** 两层在同一份文档里用了两套相反的哲学，说明这个原则没有被真正贯彻。

这带来的实际后果不是"风格不统一"，而是**不可审计**：一个"1 片改成 2 片"的操作，在数据层看不出是谁、什么时候、为什么改的。而这恰恰是这个 App 唯一真正的差异化场景（就诊出示、医生追问"你到底吃了多少"）里最需要的。

**建议**：全面改为**追加式（append-only）+ 查询时折叠**：
- `dose_records` 只 INSERT，永不 UPDATE、永不 DELETE。撤销 = 追加一条状态为 `REVERTED` 的对冲记录，或用下方修正表。
- 新增 `dose_adjustments`（修正表）：引用 `record_id`，记录 `被改字段 / 旧值 / 新值 / 原因 / 操作来源 / 时间`。
- 统计口径中明确："有效剂量 = 基础剂量 + SUM(修正差额)"，被 REVERTED 的记录按对冲记录抵扣。
- 库存账本已经是这个模式，直接复用；**两层终于对齐了。**

### P0-4 统计 SQL 用 `actual_time` 过滤，漏服记录会被 WHERE 直接剔除

ARCH:299：
```
WHERE d.actual_time BETWEEN :rangeStartTimestamp AND :rangeEndTimestamp
```

`DOSE_RECORDS.actual_time`（ARCH:123）的语义是"实际服药打卡时间"。而 **`MISSED` 记录的 `actual_time` 必然为 NULL**（没吃，哪来的实际时间）。

结果：
1. `MISSED` 行被 `WHERE` 整行过滤掉 → `missed_count` 恒为 0（ARCH:291）；
2. 依从率分母 `COUNT(status IN ('TAKEN','MISSED','SKIPPED'))` (ARCH:295) 退化为"只数已打卡记录"；
3. **"按时依从率"会永远等于 100%**（只要用户只打自己记得的那几次卡）。

这与 UI_DESIGN:229-230 展示的"应服总次数 1,460 次 / 已按时服用 1,405 / 漏服跳过 55"直接矛盾 —— 那个 55 在这个 SQL 下永远算不出来。

同时 ARCH:293-296 的分子只判 `status='TAKEN'`，**完全不看 `actual_time` 与 `scheduled_time` 的差值**。也就是说 ARCH 定义的"依从率"其实是"记录完成率"，而 UI 上标的是"按时依从率"。**定义、算法、界面三者互不相同。**

对比 APP:403 用的是 `WHERE d.scheduled_time BETWEEN` —— **v1 是对的，v2 改错了**。这正是"两版文档并行"造成的典型伤害。

**建议**（统计口径应单独成文，见 P1-19）：
1. 归属区间一律按 **`scheduled_time`（计划时间）** 切分，不用 `actual_time`。这样也顺带回答了"跨零点服药归属哪天"。
2. 分子必须是"计划窗口内确认服药"的比例，需要引入每个槽位的 **`window_end_ts`（依从窗口截止）**。方案里"±60 分钟"是写死在文档里的常量（APP:389），应改为**按药品/剂型可配**（长效制剂每日一次时 ±60 分钟毫无意义）。
3. 报表 SQL 用 `LEFT JOIN`，让"该周期零记录 / 应服 0 次"的药品也出现在报表里（否则用户以为数据丢了）。
4. 明确排除 `REVERTED`（按 P0-3 折叠后排除）。
5. 明确 `is_manual` / `AS_NEEDED`（PRN）**不进入依从率分母**（没有计划就没有应服次数），但**必须进入消耗量统计**。

### P0-5 闹钟 RequestCode 编码方案必然碰撞

ARCH:231-233：
```
RequestCode = (med_id × 10000) + (scheduled_hour × 100) + scheduled_minute
推迟闹钟使用 RequestCode + 500000
```

这个方案的四个硬伤：
1. **同药同刻冲突**：一个药品在 08:00 可能有"口服 1 片"和"雾化 1 支"两个槽位，编码完全相同 → 后注册的会 `FLAG_UPDATE_CURRENT` 覆盖前一个，**用户只收到一条提醒，另一条永久丢失**，且没有任何报错。真实场景里"早上一把药"极其常见。
2. **`+500000` 是猜测式编码**：`med_id × 10000` 已经铺满低位空间，正常段 med_id=51 的编码就落在 510000 附近，与 med_id=1 的推迟段（150000+time）**在同一数量级**。方案没有说明为什么不碰撞。
3. **溢出与量纲不匹配**：`hour × 100 + minute` 最大 2339，若 `med_id ≥ 234`，编码就开始与下一个药品的正常段重叠。
4. **放弃系统自带的唯一性**：`AlarmManager` + `PendingIntent` 本来提供"天然唯一"的三种机制（requestCode / data URI / 差异化 extras），方案选了最脆弱的一种编码推导。

**后果**：线上会出现"随机漏提醒 / 串药提醒"，且**极难排查**（无崩溃、无日志、只是"今天没响"）。这是提醒类 App 的头号事故类型。

**建议**：
1. 改用 **`PendingIntent.setData(Uri.parse("carromed://slot/<slot_uid>"))`** 唯一化 —— 系统按 URI 判重，天然不碰撞，且不依赖任何编码推导。配合 `FLAG_UPDATE_CURRENT | FLAG_IMMUTABLE`。
2. 若坚持用 requestCode，则必须用 **`slot.id`（自增主键或 ULID 末位）** 直接作为 requestCode，**放弃任何算术编码**。slot 表存在后这几乎是免费的。
3. 所有注册/注销统一走一个幂等的 `Scheduler.ensure(slots) -> cancelled[]`，不要在各处零散调用 AlarmManager。

### P0-6 主键用自增整型，使备份迁移的成本被严重低估

APP:421-422 的表述是"*包含完整的 SQLite 镜像数据*……3 秒内无缝恢复"；ARCH:313 表述是"*版本化 JSON：包含 `schema_version, medications, schedule_policies, dose_records, inventory_transactions`*"。**这两句描述的是两种完全不同的技术方案，方案本身没有选定。**

如果走 JSON：
- 新库的 `policy_id`、`dose_record_id` 是新库的自增值，与备份里的旧值不一致；
- `dose_records.policy_id`、`inventory_ledger.dose_record_id` 是外键，必须**两阶段 ID 重映射**（先插入新对象收集 `旧ID→新ID` 映射表，再回填外键）；
- 若选择"原样保留旧 ID"，则要额外处理自增序列重置（`sqlite_sequence`）、潜在主键冲突、以及旧备份比新库脏数据更复杂的场景。

**方案把这件事写成"3 秒"，但两阶段重映射 + 冲突处理 + 部分失败回滚 + 导入前快照，是一个数百行且必须写集成测试的子系统。** 这是典型的"看起来 1 天、实际 1 周"的低估。

**建议**：
1. **主键改为 UUID/ULID（有序 ULID 最佳）**。这是 Android 专属应用，自增的性能收益可以忽略；而它让备份迁移退化为"直接写入 + 幂等跳过已存在"，几乎消灭整个重映射子系统。
2. 备份格式二选一并写死：**JSON（可读、可跨版本迁移、可部分导入）** 作为默认；同时提供"专家模式"的 `.db` 文件直传（先 WARN 后写，明确说明仅限同版本恢复）。
3. JSON 必须带 `schema_version` + `app_version` + `exported_at` + `checksum`，恢复端按版本走迁移链。
4. 恢复必须是**事务 + 导入前自动本地快照**，任何一步失败整体回滚，并在 UI 上明示"将覆盖当前全部数据"。

### P0-7 关键运行时权限缺失，Android 13+ 上核心功能静默失效

APP:132-134 的权限清单只声明了 `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM`。**漏掉了 Android 13 (API 33) 引入的 `POST_NOTIFICATIONS` 运行时权限** —— 没有它，App **无法发出任何通知**，而且是"不崩溃、不报错、只是什么都不响"的静默失效。这对一个纯提醒 App 是致命的。

其他缺失项：
| 权限 | 缺失后果 |
| :--- | :--- |
| `RECEIVE_BOOT_COMPLETED` | 重启后无闹钟（ARCH:135 提到逻辑，但清单没列） |
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` | 无法跳转电池白名单（APP:147 提到了功能） |
| `VIBRATE` | 闹钟无震动提醒 |
| `WAKE_LOCK` | 屏幕不亮，提醒有效性大幅下降 |
| `FOREGROUND_SERVICE` (+ Android 14 的 `FOREGROUND_SERVICE_SPECIAL_USE`) | 若走前台服务保活则必需 |
| Android 15+ 后台启动 Activity 限制 | APP:256 / UI:262 依赖"闹钟触发后拉起 Quick Action Activity"，在国产 ROM 与 A15 上**基本不可行** |

关于精确闹钟，方案表述也过于乐观（APP:131-134）："*在设备进入 Doze 深度休眠时依然能唤醒 CPU*"。准确说法是：Doze 下 `setExactAndAllowWhileIdle` 受系统**每设备 9 分钟一次**的唤醒配额限制，且国产 ROM 的"自启动/后台弹出界面"开关会直接拦截 Receiver 拉起 Activity。**Quick Action Activity 路径应从主链路降级为"尽力而为"，主路径必须是通知 Action（BroadcastReceiver，无 UI，可靠）。**

**建议**：
1. 补全权限矩阵，并明确每项是"必需 / 可选 / 厂商特定"，以及拒绝后的降级行为。
2. **做一个决策点：是否上架 Google Play？** 上架则 Android 13+ `SCHEDULE_EXACT_ALARM` 默认不授予，须改用 `USE_EXACT_ALARM` 并在 Play Console 声明核心功能理由，且 API 34+ 对"非闹钟/日历类"审核严格；若不打算上架（或只在国内分发），可以直接用 `SCHEDULE_EXACT_ALARM` + `targetSdk` 宽松配置，路径大幅简化。**这个决策必须在动工前定，它会改变权限层与调度层的实现范围。**
3. 新增 `canScheduleExactAlarms()` 运行时检测（不是 `shouldScheduleExactAlarms()`）并纳入"提醒健康检查"。
4. 主链路改为：闹钟 → Receiver（纯逻辑事务，无 UI）→ 发通知（含 Action）→ 用户点 Action 直接完成；点通知体再拉起 Activity 作为增强体验（允许失败）。

### P0-8 `allowBackup` 默认值与"数据不出设备"的定位直接冲突

APP:5 / ARCH:5 把"数据 100% 归用户所有、纯本地、零云端"作为**核心卖点**。但 Android 的 `android:allowBackup` **默认为 true**，`android:dataExtractionRules`（Android 12+）也默认允许云备份与设备迁移。结果是：

> 用户的药品名、疾病、服药历史，会在用户完全不知情的情况下进入 Google 云的备份通道。

这是**产品定位与平台默认行为的正面冲突**，且是隐私类 App 最常见也最致命的疏漏。**方案里一个字都没提。**

**建议**（列为隐私基线，写进 SSOT 的强制章节）：
1. `android:allowBackup="false"` + 显式 `dataExtractionRules`（仅允许恢复到同一设备，或完全禁止）。
2. **改为 App 自管备份**：本地加密滚动备份（保留最近 3~5 份）+ 30 天一次的"该导出备份了"提醒。绕开系统备份，同时不丢数据。
3. 其余隐私基线（当前全缺）：
   - **锁屏通知隐私分级**：可配置"完整显示药名 / 仅显示'该吃药了' / 完全静默"。APP:161 与 APP:215 都要求把"注意事项"直接放进通知 —— 在锁屏上等于公开你的病情。必须做成默认保护、用户可放开。
   - **应用生物识别锁**（进入 App 需验证）：App 内全是健康数据，这是同类 App 的标配，方案完全没提。
   - 分享 CSV 给微信/QQ（APP:417）默认对药品名做**可配置的脱敏**（如"药品 A / 药品 B"），需要完整名称时用户显式打开。
   - 加密备份（口令派生密钥 + AES-GCM）。
   - 隐私政策 + Google Play Data Safety 表单 + 无崩溃统计的自愿上报（本地诊断包 opt-in 导出）。

### P0-9 库存不足 / 库存为负时的行为完全未定义

方案定义了"打卡即自动扣库存"（APP:164, ARCH 事件溯源章），但**没有定义当 `current_stock < 本次剂量` 时会发生什么**。而这是**每个用户出差、忘带药、旅游时每天必然遇到**的场景，方案中零覆盖：

- 阻止打卡？（用户会因为"没库存"而不敢确认已服 → 数据反而失真，且违反医疗常识：药肯定吃了）
- 允许扣成负数？（那 APP:255 的"约可用 1.5 天"、警戒线提示怎么表现？）
- 还是弹出"库存不足，请先补药"？（把库存管理凌驾于服药记录之上，是危险的交互设计）

UI 线框里也没有负库存态（APP:254、UI:141 都只展示"充足/告急"两态）。

**建议**：
1. **默认策略：允许服药，库存照扣为负数**（服药事实优先于库存记账），库存与服药是两个正交的事实。
2. 增加 `stock_tracking_enabled` 开关（部分用户压根不想管库存，只想收提醒 —— 强制填库存是这类 App 的第一大流失原因）。关闭时跳过扣减、跳过库存 UI、跳过低库存提醒。
3. 负库存单独视觉化：卡片显示"库存 -2（已欠）"，预计可用天数显示"需补药"，但**绝不影响打卡按钮可用性**。
4. 低库存预警改为**双重触发**：绝对阈值（`min_stock_alert`，保留）**或**预计服完日期落入采购周期（新增）——慢性病 90 天量程和抗生素 7 天量程用同一个"10 片"阈值毫无意义。

### P0-10 领域层与平台层强耦合，没有 Port 抽象，导致不可测试也不可降级

ARCH:240-260 的"定时提醒与 Android 系统保活链路"把 `BOOT_COMPLETED`、`AlarmManager`、`BroadcastReceiver`、`Heads-up 通知` **直接画进了核心流程图**。这在架构上是把领域逻辑和平台 API 焊死了，带来三个无法回避的后果：

1. **不可单元测试**。整个应用最有价值的部分（改计划对账、跨天槽位生成、依从率计算、Snooze 链）都依赖"现在几点"和"系统会不会响"，而 `DateTime.now()` 和 `AlarmManager` 在 Android 单元测试里是不可控的。**没有 Clock 抽象，跨天/DST/时区/重启这些场景的自动化测试根本写不出来。**（方案中也确实没有测试计划，见 P2-9。）
2. **不可降级**。"精准闹钟 → 普通闹钟 → 启动时自愈对账"这样的三档降级（见 P0 补充建议）需要调度器是一个**可替换的实现**，而不是散落在业务代码里的 `if (SDK_INT >= 31)`。
3. **不可移植、不可演进**。定位写死"Android 专属"（APP:5）本身没问题，但领域层跟着一起写死就没有回旋余地；且换一种提醒实现（前台服务、WorkManager）就等于重写业务。

**建议**（本报告认为这是最有价值的一条架构建议）：

在领域层与平台层之间定义 **5 个端口（Port）**，领域层只依赖接口，Android 实现为适配器：

| 端口 | 职责 | 为什么必须有 |
| :--- | :--- | :--- |
| `Clock` | `now()` / `today()` / 时区 | 跨天、DST、时区、月末、跨年统计的测试前提；也是"所有时间读取单点化"的强制约定 |
| `AlarmScheduler` | `ensure(slots)` / `cancel(ids)` | 降级策略可替换；调度逻辑可单测 |
| `Notifier` | 通知分级、渠道健康、Action 回调 | 多药合并、锁屏隐私需要在这一层集中实现 |
| `Repository` | 事务边界 | 库存扣减 + 打卡必须原子 |
| `Exporter` / `Store` | 备份/导出 | 换机迁移不污染领域逻辑 |

同时明确**分层依赖规则**（写进 SSOT）：`UI → Domain → Port(接口)`，Domain **不得**依赖 Flutter SDK、Android SDK、任何具体 IO。APP:31 把状态管理写成 "Riverpod / ValueNotifier" 这种二选一未决状态，说明分层规则在文档层就没有约束力。

## 2. P1 重要问题清单

### 2.1 领域模型能力缺失

**P1-1 量纲模型缺失（影响所有消耗量与库存数字）**
`REAL dose` / `REAL current_stock` / 单个 `dosage_unit` 文本（ARCH:93-94）无法承载方案自己的用例：
- UI:146 写"每次 0.2g / 2片" → **mg 与 片 之间需要换算关系**（片 = 规格 × 数量），模型里没有"规格"字段；
- UI:118 出现"晨起空腹温开水 250ml"、APP:262 出现"每次 1 滴" → **滴 / ml / 支 无法直接相加**；
- APP:305「补药 +1 盒 24 片」、APP:359 报表「涉及补药 15 盒」→ **"盒"是包装单位，数据层无处安放**；
- `REAL` 累加会产生浮点误差，"累计消耗 720 片"可能算出 719.9999996（UI:235 正好展示 720）。

**建议**：拆为四个正交字段 —— `form`(剂型：片/胶囊/口服液/滴剂/注射/外用)、`strength_value + strength_unit`(含量：0.25 g)、`pack_size + pack_unit`(包装：24 粒/盒)、`dispense_unit`(记账基本单位)。库存用**整数最小单位**记账（微小步长），UI 层做包装换算。

**P1-2 有效期 / 开封期完全缺失**
APP:263 明确写了"开封后 30 天内用完"，说明场景真实存在，但 ARCH 的 `MEDICATIONS` (ARCH:86-100) **没有任何 `expiry_date` / `opened_at` / 开封后使用期限字段**。对一个自称"库存健康助手"的产品，这是核心功能的遗漏：过期药应触发清理提醒、应计入"浪费统计"、到期后不应再作为可用库存。

**P1-3 缺「疗程（Course）」概念**
APP:257 的注意事项写着"完成整个疗程"，但模型里疗程不存在。抗生素、疗程性强的药物需要：起止日期、计划疗程天数、当前进度、是否已完成、停药原因。缺少它就无法实现"疗程还剩 3 天""疗程已完成"这类高价值提醒，也无法在报表里把"2 个完整疗程"（APP:366）算出来。

**P1-4 缺患者级健康档案，过敏史无处安放**
APP:293 的注意事项"用药前必须确认无青霉素过敏史"——**过敏是患者级属性，跨药品共享**，把它写进单个药品的注意事项是建模错误。同时缺：基础疾病、当前诊断、身高体重、孕期/哺乳期。这些缺失直接导致"**药物相互作用 / 重复成分 / 禁忌冲突**"这类用药安全提醒永远无法自动化。

**P1-5 缺「临床备注」实体**
APP:415 声明 CSV 导出包含"就诊医生备注"，但四张表里没有任何备注实体。这类备注是**跨时间、跨记录、可能跨药品**的（一次慢病随访产生多条备注），既不属于药品也不属于单次打卡。需要独立的临床备注表（药品维度 + 就诊日期 + 标题 + 正文）。这是"就诊出示"这一核心差异化场景的数据基础。

**P1-6 v2 相对 v1 的三处功能退化**
`ARCHITECTURE` v2 相对 `APP_DESIGN_SPEC` v1 **删掉了** `alias`(APP:74)、`icon`(APP:80)，并把 `precautions` 合并进 `description`(ARCH:90)。后果：
- `alias`（"降压药"、"商品名"）是用户识别药品的主要线索，UI 至今仍在按"通用名(商品名)"展示 (APP:283)；
- `icon` 删除后，UI 只能退回 emoji（UI:93/119/125）—— **emoji 在 Android 通知栏与不同字体下渲染不一致**，且色觉障碍用户无法区分；
- `precautions` 合并后，**"预置快捷标签（随餐服用/饭前空腹/服药忌酒…）"（APP:160）在数据层无处存放**，纯长文本无法做标签筛选、无法做通知摘要、无法高亮关键警告。

**P1-7 通知需要独立的短句字段**
APP:161 / APP:215 / UI:271 都要求"在通知/横幅中直接展示注意事项摘要"，但 Android 通知只有 2~3 行可用。方案只有长文本 `description`/`precautions`，客户端只能**截断长文本**——而截断恰好会切掉最关键的警告。需要一个显式的 `notice_short`（≤20 字，长尾警告 + 用法要点），并在编辑器里做字数提示。

**P1-8 暂停 / 归档 / 规则生命周期三者关系未定义**
`MEDICATIONS` 有 `is_paused`(ARCH:96) 与 `is_archived`(ARCH:97)，`SCHEDULE_POLICIES` 有 `effective_from/effective_until/is_active`(ARCH:112-114)，但三者的组合语义一个都没定义。已知问题：
- ARCH:204 的归档流水线把 `is_paused` 也置 1 → **"暂停"与"归档"被焊死**。而 UI_DESIGN 药箱 Tab 有独立的"已暂停"筛选 (UI:134)，说明用户把这两件事当两件事。需要"暂停 N 天后自动恢复"（出差、术前停药、感冒期间停慢病药）——当前模型**无法表达**。
- 归档后恢复，能否恢复旧 policy？未定义。
- `is_active` 与 `effective_until` 冗余，可能不一致。

**建议**：把"暂停"建模为独立的**暂停区间表**（`med_id, from, until, reason`），`is_paused` 降级为该区间的物化缓存；`is_archived` 只表示生命周期终结（policy 全部 `effective_until = now`），两者解耦。UI 保留三个筛选：服用中 / 已暂停 / 已归档。

**P1-9 缺"服药与检验/测量的关联"与"同日多药间隔"**
如"环孢素与某药需间隔 2 小时"，以及"服药前后测血压/血糖"。当前模型无任何字段承载时间约束。这类需求在慢病场景高频出现，且**现在加约束成本为 0**（policy 上加一个 `min_gap_minutes`），上线后再加要回填历史。

### 2.2 统计与报表

**P1-10 依从率指标选型错误（不只是实现 bug，是指标选错）**
APP:389 定义"±60 分钟内视为准时"。对**长效制剂**（每日一次的环孢素、降压药、二甲双胍），09:00 吃和 21:00 吃的临床意义完全相同，但该定义会把它判成"不按时"，给出误导性的低分。而这类"每日一次慢病药"恰恰是本 App 的主力用户。

**建议**：主指标改用临床与药事领域通用定义，并明确说明取舍：
- **MPR（服药比例）** = 实际服药次数 / 应服次数 —— 作为"总体达成度"；
- **PDC（用药覆盖天数比例）** = 覆盖天数 / 应覆盖天数 —— 作为"长期坚持度"，**这是 PD 类研究的标准指标**；
- "准时率"降级为次要指标，且窗口**按药品可配**（长效制剂可设 ±6 小时或直接关闭）。
UI 上不要把三者混在一个"按时依从率"数字里（UI:229）。

**P1-11 统计口径缺少"边界情形规范"，数字不可复现**
未定义的至少有：跨零点服药归属哪一天；计划在统计区间内生效/失效的药，分母如何切分（新开始疗程第 1 天算 1 次还是 0.5 次）；补录的历史记录归入哪一天；`CANCELLED_*` 槽位是否进分母；PRN/按需是否进分母。**"过去 30 天"是滚动 30 天还是自然月**（UI:224 给了"过去 7 天/30 天/1 年/自定义"，但未定义归属规则）也未说明。

**建议**：新建 `docs/METRIC_SPEC.md` 作为统计口径的唯一真相源，逐条列出每个指标的分子/分母/归属规则/排除项/边界示例（至少 5 个边界样例），SQL 与 UI 文案都从它派生。**这是本 App 数据可信度的地基，比 SQL 本身重要得多。**

**P1-12 报表性能宣称无依据，且缺索引与物化**
APP:384 宣称"毫秒级聚合一年甚至数万条记录"。真实瓶颈不是记录数（5 药 × 3 次/天 × 365 天 ≈ 5500 行，任何 SQLite 都是毫秒级），而是：缺索引设计（`dose_records(scheduled_time)`、`(medication_id, scheduled_time)`、`(status)`）、缺 `REAL` 浮点误差处理、缺多年数据量下的策略。
同时 "过去 1 年 = 12 个月柱状图 + 3 个排行榜"（UI:246-252）每次打开都实时全表聚合并非必要。

**建议**：补索引清单 + **月度物化汇总表**（`(年月, med_id)` 为键，打卡时增量 upsert），报表查询走汇总表。明细查询按需实时。删除"毫秒级"这类不可验证的宣称（见 P2-12）。

**P1-13 零记录药品在报表中消失**
ARCH:297 用的是 `FROM medications m JOIN dose_records d`（INNER JOIN）。该周期一次都没打卡的药品**不会出现在报表里**。用户看到"我吃了 5 种药，报表只有 3 种"会怀疑数据丢失。应改 `LEFT JOIN` 并显式展示"应服 0 次 / 消耗 0"。

**P1-14 `EXPIRED`（过期未响应）与 `MISSED`（漏服）必须区分**
方案把所有"过期未打卡"都记为 `MISSED`。但"用户忘了打开 App"和"用户真的没吃药"是**两件不同的事**，混为一谈会让依从率失真且对用户不公平（用户会看到自己被无端判为漏服，进而放弃使用）。
**建议**：区分 `EXPIRED_PENDING`（通知已发、用户未响应，**不计入依从率分母**，仅作为"待确认"提示）与 `MISSED`（用户明确点了"跳过"或主动标记未服，计入分母）。SKIPPED（主动跳过，如"医生说这次不用吃"）是否进分母，需按药品类型可配。

**P1-15 补录/补卡缺去重机制**
ARCH:181-188 允许补录任意历史时刻的服药。如果用户在两个入口各补录一次"昨天 20:00 的药"，会出现重复扣库存、重复计入消耗。`dose_slots` 落库后（见 P0-2）应在补录时**优先绑定到已存在的 PENDING/EXPIRED 槽位**而不是无条件新建；确实需要新建时，用 `(med_id, scheduled_ts, is_manual)` 做幂等检查并提示"该时段已有记录"。

### 2.3 调度与保活

**P1-16 保活触发点严重不全**
ARCH:240 列出三个触发源：`BOOT_COMPLETED` / 前后台切换 / 规则变更。**缺失但必需**的还有：
| 触发源 | 场景 |
| :--- | :--- |
| `TIME_SET` | 用户改系统时间 / NTP 自动校时后，所有闹钟全部错位 |
| `TIMEZONE_CHANGED` | 出境、换 SIM、坐飞机改时区；跨零点时今日槽位需重算 |
| `MY_PACKAGE_REPLACED` | App 升级后系统可能清空该应用的闹钟 |
| `ACTION_MY_PACKAGE_REPLACED` 之外的强制停止 | 用户"强行停止"后，闹钟被清且**广播不再送达**（需引导用户加白名单） |
| 每日兜底 | 用 `WorkManager` 的周期性任务（≥15 min，或每日一次）做对账，防止任何漏网情况 |
| 版本迁移后 | DB 迁移后需重建所有索引与闹钟 |

**P1-17 没有降级策略，"对账"后如何补通知未定义**
ARCH:243 提到 Reconciler 会扫描未来 48 小时。但**当 Reconciler 发现"槽位时间已过、从未通知"时该怎么办**（比如设备关机 3 小时，期间 3 次服药时间已过）？
- 逐条补发 → 开机瞬间弹 3 条通知，骚扰且用户已错过；
- 静默记 `EXPIRED_PENDING` → 合理，但要配合 P1-14；
- 合并成一条"你今天有 2 次服药未确认" → 需要定义阈值（建议：过期 < 2h 合并补发；≥ 2h 静默标记）。
**方案完全没有这一段。** 同时缺三档降级矩阵：精确闹钟 → `setWindow` 粗略闹钟（Doze 下延迟但可接受）→ 仅靠前台对账 + 下次打开 App 汇总提醒。降级状态应在"提醒健康检查"页可见。

**P1-18 Snooze 链缺边界规则**
ARCH:228 定义了 `snooze_count`，但没有：次数上限；推迟到第二天怎么办（08:00 连推 20 次到次日 04:00，与次日 08:00 槽位的关系）；跨天仍未处理的 `SNOOZED` 槽位如何终局（转 `EXPIRED`？转 `MISSED`？）；`snooze_until` 落在下一个槽位之前时的合并提示。建议：次数上限 3 次，之后自动转 `EXPIRED_PENDING` 并在今日页顶部汇总提示"该药今天已错过"。

**P1-19 通知的"多药同时到点"合并与批量操作完全缺失**
最常见的真实场景是**早上一把药**（08:00 同时 4 种药）。方案里每个槽位一条通知，会造成：4 条横幅刷屏、用户必须逐条处理、无法一键全吃。UI_DESIGN:277-286 的 Quick Action Sheet 也是单药形态。
**建议**：
- 同一时间点（±5 分钟窗口）的多药**合并为一条通知**，用 `MessagingStyle` 或折叠列表展示 4 个药品；
- 通知 Action 提供"**全部已吃**"（原子事务，逐条扣库存）；
- 今日页按"服药时机"分组而非仅按时间点，让"这一把药"成为一个可整体操作的对象（与 P1-20 联动）。

**P1-20 今日页"服药把次"抽象缺失**
UI:92-121 已有"上午 09:00 / 10:30 / 13:30"的时间分组 + "已解决的任务"折叠（UI:115）。但没有定义"一把药"作为可整体确认的对象。**这个抽象同时能解决 P1-18（推迟一把药而非一次）、P1-19（合并通知）、P1-9（间隔约束提示）三个问题**，性价比很高。

**P1-21 通知 Action 的事务性未定义**
"已吃"按钮被连点两次、通知 Action 与今日页按钮同时点击、通知回调时 Flutter 主 isolate 未启动 —— 这些都会导致**重复扣库存**。需要：通知 Action 走**原生侧独立事务**（不依赖 Flutter isolate）→ 成功后通过 MethodChannel 通知 Flutter 刷新；且扣减流水带**幂等键**（`(dose_record_id, type)` UNIQUE），让重复执行天然幂等。这与 P0-2 的幂等键设计是同一件事。

### 2.4 产品边界与需求空白

**P1-22 产品边界从"用药"漂移到"待办"，但数据模型只支持药**
APP:5 的定位是"*服药/待办管理工具*"，UI:118 出现了"晨起空腹温开水 (250ml)"。但领域模型全部围绕 `MEDICATIONS`，**没有任何通用待办实体**。
**这是必须在动工前决定的分叉**：
- 若只做用药 → 删掉"待办"定位与饮水示例，模型不动；
- 若要做待办/饮水/量血压 → 必须把 `medications` 抽象为 `items`（`ItemType = MEDICATION | WATER | VITAL_CHECK | TODO`），且库存/规格字段对非药项无意义，需要拆出 `item_specs` 子表。
**现在决定的成本：改 3 个字段名 + 加 1 层抽象。现在不决定、写到一半再决定：一次完整的数据迁移。** 见 D-3。

**P1-23 缺 Onboarding（首次使用流程）**
方案从"药品列表"开始讲，**没有首次启动引导**。而"今天该吃什么"必须在用户录入第一个药品后才成立。空状态下用户看到 4 个空 Tab，**60 秒内感受不到任何价值**，这是这类 App 留存杀手。
**建议**：首次启动 3 步引导 —— ① 添加第一个药品（预置常见药品模板，含分类/规格/常用注意事项，可一键带入）→ ② 设置时间与提醒（同时触发"提醒健康检查"）→ ③ 设置库存/警戒线（**可跳过**）。空状态页必须给"添加第一个药品"的主 CTA 与示例卡片。

**P1-24 缺「防漏提醒健康检查」的完整设计**
APP:145-149 有"防漏提醒自检页"的雏形（只列了 3 项），但这实际上是**本 App 相对同类产品的核心竞争力所在，值得做成完整功能**。完整清单应包括：
通知权限（API 33+）· 通知渠道是否被用户关闭 · 渠道重要性是否被下调 · 精确闹钟权限（`canScheduleExactAlarms()`）· 电池优化白名单 · 厂商自启动/关联启动 · 后台弹出界面 · 锁屏显示通知 · 勿扰/专注模式 · 通知渠道静音 · 时区异常。
呈现形式：首页一个"提醒健康度"徽标（正常 / 有风险 / 已失效）+ 可勾选清单 + **每项一键跳转对应系统设置页**（不同厂商跳转 Intent 不同，需要一张厂商 → Intent 映射表）。

**P1-25 缺"休息/旅行模式"与"漏服升级提醒"**
- 旅行/外出模式：批量暂停若干天、期间不打扰但保留统计（与 P1-8 的暂停区间联动）。
- **漏服升级**：忘记吃药是本产品要解决的核心问题，但方案的应对手段**只有"发一次提醒"**。缺少"连续 N 次未响应 → 升级提醒（更响/更多次/文案更醒目）/ 连续 3 天全漏 → 首页红色警示"。这是 MyTherapy/Medisafe 的标准能力，也是差异化亮点。
- 缺"提前提醒窗口"可配（有些药需提前 15 分钟）。

**P1-26 缺 Android 平台级入口设计**
定位是"Android 专属"（APP:5），但方案**没有任何 Android 平台入口的设计**：桌面小组件（Glance/RemoteViews）、锁屏小组件、通知栏常驻的"下次吃药倒计时"、快捷设置磁贴（Quick Settings Tile）、长按快捷方式直接打卡、时钟应用集成。
其中**"通知栏常驻下次吃药倒计时"与"锁屏小组件"是 Android 上提醒类 App 最高效的入口**，缺失它们等于放弃了这个平台最大的差异化优势。**这是本方案在平台特性利用上最大的浪费。**

**P1-27 缺"报告可视化产物"（就诊出示）**
UI:171 有"[ 分享/导出报告 ]"按钮，但**报告长什么样完全没设计**。用户拿去给医生看，需要的是一张/一页可打印的 PDF 或图片：药品清单、依从率、消耗总量、疗程、临床备注。方案只设计了 CSV 表格（APP:414-417）——**医生不会看 CSV**。这与 P1-5（临床备注实体）配套。

**P1-28 换机数据丢失风险被低估**
方案明确"不登录、不联网"（APP:5），换机只能靠本地文件迁移。但**真实用户（尤其中老年慢病患者）完成"导出→微信传输→新手机接收→导入"的比例极低**，因此实际数据丢失率会非常高，而这个 App 的数据是**不可再生的长期健康档案**。
**建议**（低成本高价值）：① 本地**自动滚动备份**（保留最近 5 份，无需用户操作）；② 30 天一次的"建议导出备份"温和提醒；③ 把导出做成一步到分享面板；④ 在 Onboarding 中明确告知数据仅存本机、如何备份。

### 2.5 视觉与可访问性

**P1-29 "Material You 动态取色"与"固定品牌色"冲突**
APP:29 声明"Material 3 Design（适配深浅色与动态色彩 Material You）"，UI:46 却固定品牌色 `#2563EB`，UI:42-52 给出全套固定色值。**动态取色会覆盖强调色**，两套策略不能同时成立。需明确：哪些色跟随系统动态（强调色）、哪些恒定（语义色：告警琥珀、错误红、成功绿），并给出**对比度保护规则**（动态取色后文字对比度不足时的回退）。同时 UI 只给了浅色 token，**深色模式完全没有定义**（APP:29 却声明支持）。

**P1-30 颜色语义编码选错了维度**
UI:47-52 把 5 个语义色绑定到"药品类别"（处方/中成药/维生素/激素/滴剂）。问题：
- 类别与**用药安全**无关，用户真正需要一眼看到的是"随餐/空腹/睡前"（P1-20 的服药时机）和"告警状态"；
- 用户常有 8~15 种药（UI:134 显示 5 种，实际用户更多），靠类别色无法辨识；
- 5 色里有绿/橙/红，**红绿色觉障碍（约 8% 男性）无法区分**。

**建议**：语义色改为编码**服药时机**（空腹/随餐/餐后/睡前）或让用户自由取色（UI:302 已有取色 UI，但色板固定 6 色）；**状态色（告警/严重告警/正常）从类别色中剥离**，始终保留给状态；所有颜色**必须配形状或图标冗余编码**（WCAG 非颜色依赖）。

**P1-31 用 emoji 作为药品图标（UI:93/119/125）**
通知栏与大字体下渲染不一致、部分 ROM 显示为方块、无法做形状冗余编码。**应改为矢量图标集（片剂/胶囊/注射/滴剂/瓶/外用/喷雾）**——这同时是 P0-7 之外的另一个 v1→v2 功能退化（APP:80 有 `icon` 字段，ARCH v2 删掉了）。

**P1-32 关键按钮的防误触与可撤销性未做风险评估**
UI:345 的"1-Tap Undo"是双刃剑：它防误触，但也让用户能在 3 秒内误撤销一条**真实的服药记录**（而按 P0-3，撤销是不可变的对冲事件，撤销本身也要留痕，用户不容易发现）。
**建议**：Undo 提供 5 秒窗口（期间可"恢复"）；撤销的撤销也走同一条流水链；今日页"已解决"区提供"查看流水"入口让用户能自查。

**P1-33 药品与"待办"混排在同一列表（与 P1-22 联动）**
UI:118-119 把"醋酸泼尼松"与"晨起空腹温开水"并列在"已解决"里，视觉与语义完全一致。药物是**有剂量、有库存、有禁忌**的实体，待办不是。这个混排会让数据模型和 UI 同时失控。

### 2.6 备份与导出

**P1-34 导出格式未定义细节，会直接产出"打不开/看不懂"的文件**
- **编码**：CSV 必须带 UTF-8 BOM，否则 Excel 打开中文全是乱码（这是国内用户最高频的导出投诉）。
- **时间格式**：给医生看的表必须是"本地时间字符串（2026-09-27 08:05）"，不能用 Unix 时间戳或 ISO 裸值。跨时区场景还应标注时区。
- **列定义**：APP:415 声明包含"注意事项"——**一条大段文本塞进 CSV 单元格会破坏可读性**，应单独成表或在备注列做摘要。
- **分享路径**：APP:417 提到"保存到 Downloads 目录"——Android 10+ 分区存储下需走 SAF (Storage Access Framework) 或 `MediaStore`，且需 `FileProvider` 授权才能分享给微信/QQ。方案未提。
- **导入的冲突处理**未定义：同一份备份导入两次会怎样？部分数据存在时导入是"合并"还是"覆盖"？导入前是否自动做一次本地快照（**这是防误操作毁数据的最后一道安全网，必须写死在方案里**）？

**P1-35 备份未加密、分享未脱敏（与 P0-8 联动）**
APP:421 生成的 JSON 是明文，且 APP:417 明确支持分享给微信/QQ。药品名+疾病+服药史的明文文件经社交软件传播是不可逆的隐私泄露。必须提供**口令加密备份（AES-GCM，口令派生密钥）**，并对分享内容提供脱敏开关。

### 2.7 工程治理

**P1-36 里程碑停留在 v1 模型，无"模型冻结"关口**
APP:430-437 的 6 个里程碑是围绕 `REMINDER_SCHEDULES`/`DOSE_LOGS` 写的，M3（提醒）这种最难的模块排在 M2 之后是对的，但**没有一个"schema 冻结 / 迁移机制就绪"的强制关口**。而方案当前正处于"v1 已定稿、v2 已改写"的中途。
**建议**：在 M1 之前插入 **M0：文档 SSOT 合并 + schema 冻结 + ADR × 10 + 迁移机制（Drift migrator + 版本号 + 迁移测试）落地**，并把"schema 变更需新增 ADR"写成硬性流程。
同时 M1 之后的每个里程碑应带**可验证的验收标准**（当前只有"打通""完工"这类不可验收的描述），尤其 M3 必须有真机测试矩阵（见 P2-9）。

## 5. 推荐的架构修订方案

> 目标：在不推翻三层解耦与事件溯源账本这两个正确决策的前提下，补齐空洞并消除 P0。

### 5.1 分层与 Port（对应 P0-10）

```
┌────────────────────────────────────────────────────────┐
│ UI 层 (Flutter / Material 3 / Riverpod)                 │
└───────────────────────────┬────────────────────────────┘
                            │ 依赖抽象
┌───────────────────────────▼────────────────────────────┐
│ Domain 层 (纯 Dart, 零 Flutter/Android 依赖)             │
│  - 规则版本管理 / 槽位对账 Reconciler / 履约与修正        │
│  - 库存账本 / 统计聚合 / 备份序列化                     │
│  仅依赖 5 个 Port 接口:                                   │
│    Clock · AlarmScheduler · Notifier · Repository · Store│
└───────────────────────────┬────────────────────────────┘
                            │ 实现
┌───────────────────────────▼────────────────────────────┐
│ Adapters 层 (Android)                                    │
│  - AlarmManager (含降级策略) / Notification (含隐私分级) │
│  - Drift/SQLite / SAF / MethodChannel / 原生通知事务      │
└────────────────────────────────────────────────────────┘
```

**硬性约定**：
1. 所有时间读取必须经 `Clock`，**禁止在 Domain 层出现 `DateTime.now()`**（否则跨天/DST 测试无法编写）。
2. Domain 层不得 import `dart:io` 的文件 API、不得 import `package:flutter/*`。
3. 通知 Action 的"已吃"事务在**原生侧独立完成**（Adapter 内），不依赖 Flutter isolate 存活；完成后 MethodChannel 通知 UI 刷新。

### 5.3 调度与保活（修订）

**三档降级矩阵**（在"提醒健康检查"页对用户可见）：

| 档 | 条件 | 机制 | 用户可见状态 |
| :--- | :--- | :--- | :--- |
| 精确 | 权限齐全 + 非省电激进 | `setExactAndAllowWhileIdle` | 绿色"准时" |
| 降级 | 缺精确闹钟权限 | `setWindow`（可容忍延迟窗口） | 黄色"可能延迟 N 分钟" |
| 自愈 | 深度省电 / 厂商管控 | WorkManager 周期对账 + 打开 App 时全量对账 | 橙色"依赖打开 App 时提醒" |

**Reconciler 触发源（幂等，缺一不可）**：`BOOT_COMPLETED` · `TIME_SET` · `TIMEZONE_CHANGED` · `MY_PACKAGE_REPLACED` · 应用前后台切换 · 规则变更 · 打卡/撤销 · WorkManager 周期任务（每日兜底）· DB 迁移后。

**过期槽位处理规则**（P1-17）：`过期 < 2h` → 合并为一条"未确认的服药"通知；`过期 ≥ 2h` → 静默转 `EXPIRED`，**不进依从率分母**（P1-14），今日页顶部汇总一行提示。

**通知策略**：同时点（±5min）多药合并为一条；提供"全部已吃"原子批量；锁屏显示级别可配（完整 / 仅"该吃药了" / 静默）；通知 Action 走原生事务 + 幂等流水键。

### 5.4 统计口径（修订）

新建 `docs/METRIC_SPEC.md` 作为唯一真相源，核心裁定：
- **归属日**：一律按 `scheduled_time` 所属本地日（解决跨零点与实际时间过滤问题）。
- **主指标**：MPR（服药比例）+ PDC（用药覆盖天数比例）；"准时率"为次要指标且窗口按药品可配。
- **分母排除**：`EXPIRED`（用户未响应）、`CANCELLED_*`（规则变更取消）、PRN/按需（本就无计划）。
- **分母切分**：按统计区间内"计划有效"的槽位计算（新开始/已结束疗程自然切分）。
- **消耗量**：`Σ(有效剂量)`，其中有效剂量 = 基础剂量 + Σ修正差额 − Σ撤销对冲；**整数记账，零浮点误差**。
- **报表完整性**：`LEFT JOIN`，零记录药品显示"应服 0 / 消耗 0"。
- **性能**：走 `monthly_stats` 物化表；明细查询按需实时 + 索引清单。

### 5.5 隐私基线（修订，作为强制章节）

1. `allowBackup=false` + 显式 `dataExtractionRules`，绕开系统云备份。
2. 本地自动滚动加密备份（保留 5 份）+ 30 天温和导出提醒。
3. 锁屏通知隐私分级（默认"仅显示该吃药了"）。
4. 应用生物识别锁。
5. 分享默认脱敏（药品别名），完整名称需显式开启。
6. 口令加密的对外备份（AES-GCM）。
7. 隐私政策 + Play Data Safety + 可选本地诊断包。
