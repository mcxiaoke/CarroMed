# CarroMed 方案与架构审查报告 (dsf)

> **审查对象**：`docs/APP_DESIGN_SPEC.md` (v1.0.0)、`docs/ARCHITECTURE.md` (v2.0.0)、`docs/UI_DESIGN.md` (v1.1.0)、`docs/demo/index.html` (原型 v2.0)
> **审查范围**：方案、架构、数据模型、交互设计层面（含 Android 系统集成的设计边界）。不含具体代码与实现细节。

## 0. 总体结论

方案的核心判断是正确的：**把"计划规则"与"执行事实"解耦**，是同类产品（MyTherapy 等）最容易推倒重来的地方，CarroMed 抓住了要害，"事实不可变 + 三层解耦 + 会计式账本 + 归档不删除"这四条法则方向明显优于同类。

但当前处于 **"思想先进、模型未闭合"** 的状态：提出来的第二层（槽位）没有落到数据模型上，两份文档并存两套互相冲突的表结构，依从率的分母与漏服（MISSED）的产生机制缺失且现有 SQL 存在事实性错误，"事实不可变"被文档自身多处违反，提醒可靠性建立在一个过于乐观的假设上。**这些问题如果不在编码前钉死，会在 M3/M4 阶段引发大规模返工或数据错误。**

## 1. P0 阻断级问题

### P0-1 两套数据模型并存且互相冲突

**现状**：`APP_DESIGN_SPEC §二` 定义 `REMINDER_SCHEDULES` + `DOSE_LOGS`（一个时间点一行，无版本概念）；`ARCHITECTURE §三` 定义 `SCHEDULE_POLICIES` + `DOSE_RECORDS`（版本化）。两者表名、字段、约束、状态枚举均不同。例如：

* 状态枚举：`SPEC L107` 为 `TAKEN/SKIPPED/MISSED/SNOOZED`；`ARCH L126` 为 `TAKEN/REVERTED/SKIPPED/MISSED/SNOOZED`（有 REVERTED，与事实不可变冲突，见 P0-5）。
* 统计 SQL 分别引用 `dose_logs/scheduled_time`（`SPEC L403`）与 `dose_records/actual_time`（`ARCH L299`）。

**影响**：开发者无法判断以实现哪套为准；v1 的"一行一个提醒时间"模型无法表达版本化、隔 N 天锚点、同一时间点不同剂量，与 v2 的场景 1/4/6 直接冲突。这是最容易导致"推倒重构"的根因。

**建议**：
1. 明确 **ARCHITECTURE v2 为唯一数据模型权威**，`APP_DESIGN_SPEC` 降级为纯产品需求文档（PRD），§二/§三/§六 删除重复定义，改为引用。
2. 在文档开头增加"单一事实来源 (Single Source of Truth)"约定表：数据模型/状态机 → ARCH；交互与页面 → UI_DESIGN；功能需求 → SPEC（不含模型）。

### P0-2 第二层"单日槽位"有描述、有状态机，但没有数据模型

**现状**：`ARCH §二` 把 Daily Dose Slots 列为三层之一并给出状态机 `PENDING/SNOOZED/TAKEN/SKIPPED/CANCELLED_TODAY`；`ARCH §四` 大量依赖槽位（`CANCELLED_BY_RULE_CHANGE` L159、`snooze_target/snooze_count` L228-229、闹钟 RequestCode L232）。但 `ARCH §三` 的 ER 图只有 4 张表，**没有槽位表**。

**影响**：场景 1（差分对齐）、场景 2（撤销回滚到哪个槽位）、场景 6（推迟链）全部无法落地；"只操作 PENDING 槽位"没有操作对象；闹钟没有稳定的槽位 ID 可以对齐与幂等。这是整个架构最关键的结构性缺口。

**建议**：新增槽位实体（建议名 `DAILY_DOSE_SLOTS` / `dose_occurrences`），承载全部"可变的当日状态"（待服/推迟/今日取消/跳过），事实表只保留终态。设计要素至少包含：`medication_id`、`policy_id`、`policy_version`、`scheduled_date`(本地日期)、`scheduled_time`、`dose`、`slot_status`、`snooze_target`、`snooze_count`、`alarm_request_code`、`resolved_record_id`。

### P0-3 槽位生成依赖"每日零点"，该假设不成立

**现状**：`ARCH §二` 写"每天零点或进入'今日'时，根据当天有效的规则生成任务槽位"。

**影响**：Android 无法保证零点执行（Doze、后台限制、用户当天根本没打开 App）。一旦零点未执行且用户未打开 App，**当天不会生成任何槽位 → 当天所有提醒静默失效**。对一个服药提醒 App 这是致命路径。

**建议**：
1. 槽位改为**惰性投影**：不依赖任何定时任务，读取时按规则实时计算；只有发生"偏离"（已服/跳过/推迟/今日取消）时才落库为持久槽位。
2. 提醒调度与"槽位是否落库"解耦：闹钟由调度器直接从规则计算下一次触发点，不依赖槽位已生成。
3. 明确"零点任务"从方案中删除或降级为纯优化（可选，不作为正确性前提）。

### P0-4 MISSED 产生时机缺失 + 依从率分母错误 + 统计 SQL 事实性错误

**现状**：
* `ARCH §七` 依从率分母为 `COUNT(status IN ('TAKEN','MISSED','SKIPPED'))`，即**假设 MISSED/SKIPPED 记录一定存在**；
* 但全文没有任何机制/时点负责把过期的 PENDING 变成 MISSED（Android 后台不可靠，"23:59 定时判定"同样不成立，与 P0-3 同源问题）；
* 更严重的是 SQL 用 `WHERE d.actual_time BETWEEN :start AND :end` 过滤（`ARCH L299`），而 MISSED/SKIPPED/SNOOZED 的 `actual_time` 为空 → 这些记录会被 `BETWEEN` 直接过滤掉，导致 `missed_count/skipped_count` 恒为 0、**依从率被系统性高估**。`SPEC §六 L403` 用 `scheduled_time` 过滤，两份文档口径不一致。
* 依赖"记录数"的分母还无法回答"计划总次数 730 次"（`SPEC L353`）——没有记录的日子不会被计入。

**建议**：
1. **依从率分母必须由规则投影计算"应服次数"（expected doses）**，而不是由记录数聚合。这是唯一在"用户长期不打开 App"时仍正确的算法。
2. 时间区间过滤统一改用 `scheduled_date`（本地日期列，见 P1-3）或 `scheduled_time`，禁止用 `actual_time`。
3. MISSED 采用**惰性判定**：查询时依据 `now` 与宽限期推导；能落库则落库（便于通知/统计缓存），但**不作为唯一事实来源**。
4. 明确"宽限期"数值（多久未服判为漏服），并与"准时窗口"区分开。

### P0-5 "事实不可变"与文档多处自相矛盾

**现状**：法则一（`ARCH L38`）声明 DoseRecord 不可篡改，但：
* 场景 2 把已 TAKEN 的记录改为 REVERTED（`ARCH §四·场景 2`）；
* 场景 3 直接"更新打卡记录中的 `dose_taken = 2.0`"（`ARCH L192`）；
* `UI §七.4` 沿用同样的原地修改交互。

**影响**：这是原则性矛盾。事件溯源的价值在于"任何时点的历史都可重放/可审计"，原地改事实行会让"撤销"与"更正"变成不可追溯的覆盖操作，也与"以流水为准自动平账"冲突。

**建议**：二者选一并在全文统一（推荐 A 为主、B 为辅，或直接 A 全包）：
* **A 追加式（推荐）**：事实表只追加，不改不删。撤销 = 追加一条 REVERT 记录并指向原记录；更正剂量 = 追加一条更正记录（含 `supersedes_id`），报表按"最后有效版本"聚合。库存流水天然对应。
* **B 可改 + 审计**：允许更新，但每条修改必须生成审计流水，并把法则一改述为"历史记录永不删除、永不改变归靠关系，修正可追溯"。
* 无论哪种，**必须补一张完整的状态机合法转移表**（含非法转移的拒绝规则）。

### P0-6 提醒可靠性的真实边界未定义

**现状**：`ARCH §五` 只画了 `BOOT_COMPLETED / 前后台切换 / 规则变更` 三条触发，并称"计算未来 48 小时内的下一次待触发时序点"。

**缺失的关键点（每一条都会导致真实漏提醒）**：
1. **触发后必须重排下一次**：只注册 48h 窗口内的闹钟而不在每次触发时重新调度，48 小时后链路静默失效。方案未提"触发即重排"。
2. **Force Stop / OEM 清理**：用户"强行停止"或 OEM 一键清理后，AlarmManager 与所有广播失效，**直到用户再次手动打开 App**。这是药物提醒的头号现实风险，方案没有任何对策或已知限制说明。
3. **重启之外的系统事件**：`TIME_SET`、`TIMEZONE_CHANGED`、`MY_PACKAGE_REPLACED`（应用升级后闹钟失效）、`LOCKED_BOOT_COMPLETED`（Direct Boot）均未覆盖，仅覆盖 `BOOT_COMPLETED`。
4. **精确闹钟权限会被撤销**：Android 12+ `SCHEDULE_EXACT_ALARM`、14+ 默认可被系统/用户撤销；Play 政策要求声明核心用途；被撤销时的降级路径（转不精确闹钟 + 常驻提示）未定义。
5. **Doze 限流**：`setExactAndAllowWhileIdle` 在 Doze 下存在每 App 约 9 分钟一次的限流，密集/多药提醒会互相挤占，方案未考虑。
6. **闹钟无枚举 API**：Android 没有"列出已注册闹钟"的接口，因此"全清重建"需要本地维护**闹钟登记表**才能精确取消。方案中的 RequestCode 公式（`ARCH L232`）解决了唯一性，但没解决"登记与取消"。

**建议**：
1. 采用业界惯例的 **"只排下一次触发点 + 触发即重排 + 幂等"** 模型，而不是"一次性铺满 48h"。
2. 分层可靠性：**主路径** 精确闹钟（`setExactAndAllowWhileIdle`）；**关键药** 可选 `setAlarmClock`（系统级，最抗 Doze，且以系统闹钟形式呈现）；**兜底** `WorkManager` 周期自愈 + 启动/开机/时区变化全量重建；**自检** 启动时校验权限与电池白名单。
3. 新增"闹钟登记表"设计（槽位 ID ↔ RequestCode ↔ 触发时间），支撑精确取消、幂等与自检。
4. 把"Force Stop 后失效"作为**已知限制**写入文档，并在自检页给出引导与"每次打开 App 全量重建"的补偿。

### P0-7 通知权限与降级路径缺失；通知动作执行边界未定义

**现状**：通知是本产品的核心交付路径，但文档对通知只讲了渠道重要性与快捷按钮，未涉及权限与失败面。

**缺失**：
* Android 13+ `POST_NOTIFICATIONS` 运行时申请与"被拒"后的兜底（应用内提醒？常驻通知？）。
* `USE_FULL_SCREEN_INTENT`（14+ 受限）、锁屏可见性、免打扰(DND)旁路、渠道被用户关闭后的检测与引导。
* **通知按钮在 App 进程已死时如何执行**：写库、扣库存、取消闹钟这些动作由谁完成（原生 Kotlin 直写？唤醒 headless Flutter engine？）。这是必须提前定死的边界（见 P0-8）。

**建议**：补"权限与降级矩阵"章节（权限项 × 是否必需 × 缺失时降级行为 × 引导入口），并明确通知动作的执行归属。

### P0-8 Flutter / 原生分工边界与跨边界写库未定义

**现状**：`SPEC §一` 说状态管理用 Riverpod，域层又写 BLoC（自相矛盾）；数据层是 Dart 侧 Drift；而闹钟/通知/开机恢复在 Kotlin 侧，通知动作还要写库。**跨界写库的归属、并发控制（双写者）、事务边界完全没有定义。**

**建议**：
1. 明确职责边界：**原生负责**闹钟注册/接收、通知展示与动作、开机/时区恢复；**Dart 负责**领域逻辑与 UI；**跨边界的写操作收敛到单一入口**（例如原生只投递"用户已点已吃"事件，由单一写入者落库），避免双写。
2. 明确 SQLite 的 `WAL` 模式与单写事务约定。
3. 补一份技术选型权衡（Flutter vs 原生 Kotlin/Compose）：本产品"Android 专属 + 深度系统集成（精确闹钟/通知动作/电池白名单/Direct Boot）"，原生的启动速度、包体、系统集成与插件维护成本更优；Flutter 胜在开发效率与 UI 一致性。**文档承诺的"毫秒级启动"（`SPEC L5`）与 Flutter 现状不符**，需二选一：改承诺，或改技术栈。

## 2. P1 重要缺陷（数据正确性 / 用药安全）

### P1-1 库存用 REAL 浮点，账本求和自校验必然漂移
`current_stock`、`change_amount`、`balance_after` 均为 `REAL`。二进制浮点在 0.25 片、ml 类剂量上会累积误差；更严重的是 `ARCH §六` 的权威式 `真实库存 = Σ change_amount` **本身就在浮点域求和**，会导致"自校验本身不可靠"，甚至反复平账。**建议**：库存改用整数最小计量单位（如"千分之一单位"整型）或定点小数，加减与求和全部在整数域完成，单位换算只在 UI 层做。

### P1-2 账本缺"期初余额"凭证，不变量从第一天即破
新药建档录入 `current_stock = 86` 时，没有任何对应流水 → `Σ流水 ≠ current_stock`，`ARCH §六` 的核心不变量从第一条数据起就不成立。**建议**：建档即写一条 `OPENING_BALANCE` 流水；并补全枚举（场景 3 用到的 `MANUAL_INTAKE`、`DOSE_CORRECTION` 未列入 `ARCH L139` 的 type 枚举）；同时明确是否允许负库存（建议禁止或强提示）。

### P1-3 缺本地日期键与时区 / 跨零点语义
全部时间用 INTEGER 时间戳，但"今天""过去一个月""月度趋势""隔 N 天锚点""规则生效日"本质都是**本地日历语义**。仅靠时间戳在时区变更、跨午夜、跨月（按秒除法分组）时会错位。且 `SCHEDULE_POLICIES` 内部就不一致：`anchor_date` 是 TEXT，而 `effective_from/until` 是 INTEGER（`ARCH L108/L111/L112`）。**建议**：事实与槽位除 epoch 外冗余一列本地日期 `scheduled_date (YYYY-MM-DD)`；规则生效范围与锚点统一用本地日期而非时间戳；统计按月分组用本地日期列；并明确"跨零点服药（如 00:30 是否算前一天的末次）"的口径。

### P1-4 快照不完整 + 报表 JOIN 主数据现值，历史会"变形"
法则一只快照了药名（`med_name_snapshot`），但 `ARCH §七` 的统计 SQL 取 `m.name / m.dosage_unit / m.category / m.color` 的**当前值**。改名、改单位（片→粒）、改分类后，历史报表随之变化，直接违背"历史不可变"。**建议**：报表以快照为准（补齐 name/unit/dose/color 或整条策略快照），或明确"展示名随主数据变化"的产品取舍并写进文档。

### P1-5 场景 1 漏掉"当天更早的未服槽位"
11:00 改计划时，若当天 08:00 那次**并未来得及服**（仍 PENDING 且时间已过），它既不在"未来槽位"集合（`ARCH L158-160` 只取消 after now），又不属于已服事实 → 形成**永久悬挂的 PENDING**，污染今日进度与依从率。**建议**：差分对齐算法补"早于 now 的未服槽位"处理规则（结转补服 / 判漏服 / 保留），并纳入状态机转移表。

### P1-6 同药多版本规则无唯一性 / 并发约束
无任何约束保证"同一药品同一时刻只有一条生效中规则"；场景 1 的"截断旧规则 + 新建新规则"在并发或失败回滚时未定义。**建议**：加"同药规则生效区间不重叠"的约束/唯一索引，并把版本切换放进单个事务。

### P1-7 Snooze 落点错位，推迟污染事实表
场景 6 把 `snooze_target/snooze_count` 放在槽位（无表），而 `SNOOZED` 又出现在事实表状态枚举里（`ARCH L126`）。**建议**：推迟完全归属槽位（或独立 snooze 调度记录），事实表只保留 `TAKEN/SKIPPED/MISSED/REVERTED` 终态；并定义推迟链上限、推迟后与下一个时段重叠时的策略（合并展示 or 各自独立）。

### P1-8 依从率两份定义互相矛盾；按需用药未从分母剔除
`SPEC §六` 用"前后 60 分钟窗口"定义准时；`ARCH §七` 只看 `status=TAKEN`（推迟 5 小时仍算 TAKEN 且算准时）。**建议**：统一为两级指标——**完成率**(TAKEN/应服) 与 **准时率**(窗口内 TAKEN/应服)，窗口可配；并明确 `AS_NEEDED`（按需）用药必须从依从率分母剔除（两份文档都未讲清，场景 5 的按需记录会被错误计入）。

### P1-9 备份明文外泄 + Auto Backup 未关闭 + 恢复语义未定义
* JSON 明文备份导出到 Downloads / 分享到微信 = **健康数据明文外泄**，与"注重隐私"定位冲突。
* 未提 Android Auto Backup（`allowBackup`）会把 DB 上传到 Google 云端，与"纯本地离线"直接矛盾，必须显式关闭/排除。
* 恢复语义未定义：覆盖 vs 合并、去重、失败回滚、跨 `schema_version` 兼容。

**建议**：备份默认加密（口令/设备密钥）；恢复采用"覆盖式 + 校验 + 原子替换"；明确 `schema_version` 前向兼容与降级策略；关闭 Auto Backup，把本地导入导出作为唯一迁移通道。

| 导出 | **CSV 兼容** | 导出给 Excel/微信需 UTF-8 BOM 与正确转义（逗号/换行/引号），否则中文乱码、列错位。 |

## 5. 建议的架构修订蓝图（设计层面）

### 5.1 实体清单（修订版）

| 实体 | 状态 | 关键修订 |
| :--- | :--- | :--- |
| `medications` | 保留 | + `strength`、`pack_size`；库存整型化；可选 `profile_id`（若入范围） |
| `schedule_policies` | 保留 | 生效范围与锚点改本地日期；加"区间不重叠"约束；枚举集中定义 |
| `daily_dose_slots` | **新增** | 承载 PENDING/SNOOZED/CANCELLED_TODAY 等可变态；惰性投影 + 偏离落库；含 `alarm_request_code` |
| `dose_records` | 保留 | 追加式终态事实；快照补齐；+ `scheduled_date`；+ `supersedes_id`（可选） |
| `inventory_transactions` | 保留 | + `OPENING_BALANCE`；整型量；补全枚举 |
| `scheduled_alarm_registry` | **新增** | 已注册闹钟登记，用于精确取消 / 幂等 / 自检 |

### 5.2 三条不变量（写成可测试断言）

1. **库存平衡**：`current_stock ≡ Σ inventory_transactions.change_amount`（整数域）。
2. **规则不重叠**：同一药品任一时刻至多一条生效规则。
3. **事实只追加**：`dose_records` 只插入、不修改、不删除（修正以追加方式表达）。

### 5.3 提醒可靠性分层

`精确闹钟(主) → setAlarmClock(关键药，可选) → WorkManager 周期自愈(兜底) → 启动/开机/时区/升级全量重建 → 自检页(权限与电池白名单)`，并配"只排下一次 + 触发即重排 + 幂等"。

## 7. 结论

方案的"时序解耦 + 事实不可变 + 会计式账本 + 归档不删除"这套骨架是对的，价值主张（离线、免登录、零广告、数据自主、长周期统计）也清晰。但当前存在 **模型未闭合**（槽位无表、两套模型打架）、**数据正确性缺口**（依从率分母、MISSED 机制、浮点库存、缺本地日期键）、**原则自相矛盾**（事实不可变被原地修改违反）、**系统集成假设过于乐观**（零点生成槽位、闹钟不重排、Force Stop、权限降级）四类问题。

建议的处置顺序：**先做 P0 的模型闭合与不变量定义（新增 M0），再补 P1 的数据正确性设计，最后进入编码与 M2–M6。** 这样可以把最大的一次性返工风险提前消灭在方案阶段。
