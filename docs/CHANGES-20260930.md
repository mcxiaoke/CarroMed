# CHANGES 2026-09-30

> 本文件按时间倒序**追加**要点摘要。时间取本机真实 GMT+8。

## 未来槽位不可操作：从"点一下明天 → 丢明天的闹钟"到"只读预览"

时间戳：2026-09-30 10:18 (GMT+8)

实施 `docs/PLAN-FUTURE-SLOT-20260929.md`（分 6 步），并对原方案做了 4 处修正（见该文档
新增的「实施记录」段）。核心缺陷：`scheduled_date` 从未参与"用户能否对这个槽位表态"的
判据 —— 翻到明天点一下 ✓，同时发生三件事：凭空生成"明天已服"事实、扣一次库存、
**静默撤掉明天的闹钟**（槽位变 COMPLETED 后 `AlarmReconciler` 只给 `getOpenSlots()`
排闹钟，这一撤**再也排不回来**）。

- **判据一处定义、两处使用**：新增 `core/domain/engine/SlotActionPolicy.kt`
  （`isActionableOn(scheduledDate, todayStr)`，字符串比较：零填充 `yyyy-MM-dd` 的
  字典序 == 时序，永不抛异常）。SQL 的三条写入口与 Kotlin 的归因/渲染都走它 ——
  刻意**不加**格式校验维度，否则会出现"SQL 放行、Kotlin 拒绝"的分叉。
- **守卫下沉到 SQL**：`DoseSlotDao.markCompletedIfOpen` / `markSkippedIfOpen` /
  `snoozeSlot` 三个 `WHERE` 并列加 `AND scheduled_date <= :todayStr`。
  `revertToPending`（撤销）**刻意不加**：它是修复坏数据的唯一通道。
  ⚠️ Room 对未使用的查询参数直接报错（`Unused parameter: todayStr`）——
  守卫无法被"悄悄删掉"，必须连参数一起处理。
- **服务层注入时钟**：`DoseTrackingService(db, todayProvider = { LocalDate.now() })`。
  不读挂钟是为了让测试确定：原方案让服务层直接 `LocalDate.now()`，
  而库里已有多个把"今天"写死的 fixture（如 `DoseTrackingServiceTest` 锁定 2026-10-01），
  那种测试会**随真实日历变红再自己变绿**。`DoseEntryActions` 共用同一个时钟。
- **`restateSlot` 前置未来判据（原方案漏掉的一处）**：改判是"先作废、再施加"，
  施加用的 `markCompletedIfOpen` 已带守卫 ⇒ 一条未来的已产生结论槽位会让
  "作废已完成、施加被拒"，而 `return@withTransaction false` **提交**了作废
  （`withTransaction` 只在抛异常时回滚）⇒ 槽位停在 PENDING、事实全标 REVERTED、
  台账已冲正。必须在作废**之前**拦下（变异验证已确认这条测试能抓到）。
- **未来被拒时绝不撤闹钟**：`DoseEntryActions.confirm/skip` 引入
  `DoseActionResult`（`APPLIED` / `ALREADY_HANDLED` / `FUTURE_SLOT`）。
  原先"失败也撤闹钟"对"已处理过"是对的，对未来是灾难 —— 只加 SQL 守卫会造出
  比原缺陷更隐蔽的新缺陷。通知栏 toast 也因此能说真话
  （"未来的服药时间不能提前确认"）。
- **UI 只读化**：`TodayUiState` 增 `today`（来自 `CurrentDateHolder`，页面不再各写
  `LocalDate.now()`）与 `isActionable`；未来日的待服卡**不渲染 ✓**，改为两行只读说明
  （「明天」/「10:30 服用」——单行长句会在 44dp 位宽里折出孤儿行，走查看图后改的）；
  分组标题旁提示「未来排班预览 · 到达当天才能打卡」；「今日已服」按选中日显示。
  **按既有约定不置灰**：置灰会让人以为"再等等就能用"。
- **详情页**：`DoseEntryUiState.isActionable` 关掉确认 / 推迟 / 跳过（不渲染，不置灰），
  顶部信息卡补上**计划日期**（「计划 10月1日 09:00」——从进展页点进来也能分清是哪天），
  页脚说明原因；备注区文案区分"会随确认保存"与"现在填写不会落库"。
  日期格加 `contentDescription`（可访问性 + 走查脚本的定位锚点）。
- **`canUndo` 补坏数据逃生口**：事实的自然日**早于**槽位计划日 ⇒ 判为坏数据，
  即使不是当天也允许撤销。否则本缺陷留下的坏记录到第二天就永久锁死用户。
  连带把 `DoseRecordDetailStateTest` 里三处"计划日=今天、事实日=三天前"的 fixture
  改成计划日与事实日对得上（那是坏数据形态，不该用来断言"较早记录不可撤销"）。
- **保留滑动窗口**（用户拍板）：未来日仍可选、用于预览排班；不做"锚定今天"，
  因为那会带来"翻不到 3 天以前"的产品回归，且与原缺陷正交。
- **测试**（478 → 502 项，全绿）：新增 `SlotActionPolicyTest`（纯函数，含跨月/跨年/闰年/
  坏串）、`FutureSlotActionGuardTest`（未来三入口零写入、今天过去照常、坏数据可撤销、
  改判不留半截状态）、`DoseEntryActionsAlarmGuardTest`（ShadowAlarmManager：
  未来被拒后闹钟仍在；今天成功后闹钟照撤），扩展 `DoseRecordDetailStateTest`。
  **变异验证 4 项全被抓**：①去掉 SQL 守卫 ②`<=` 改 `<` ③守卫误加到 `revertToPending`
  ④去掉 `restateSlot` 前置判。另做了一次更刁的变异：保留"未来"归因但照旧撤闹钟 ——
  只有"明天的闹钟仍在"这条断言变红，证明它不是冗余断言。
- **走查脚本**：新增 `present_desc` / `absent_desc` 两个负向断言动作
  （"看到只读文案"证明不了 ✓ 没渲染，必须断言缺失）与未来日 9 步；
  把未来详情页之后的 `back` 换成 `home`（该页在根路由上，back 会把 App 退到桌面）。
  修掉一个真 bug：`dumpsys window grep mCurrentFocus` 的 adb 写法会被 `dumpsys`
  当成窗口过滤条件（回 `Bad window command`），导致"App 是否在前台"**恒为假**、
  通知栏自愈分支是死代码。现统一走 `focus_window()` 管道形式，
  并在 `back` 之后加前台兜底（失败要看得见，不能让后续 20 步全拍通知栏）。
- **实测**（emulator-5554）：39 张截图 / `manifest.md` 全部断言通过，改动页面已看图
  （未来日清单、未来槽位详情、今天照常）。库内校验：未来槽位只有 PENDING（0 条坏槽位、
  0 条未来 COMPLETED 事实）、四药台账守恒、明天仍有闹钟、82 条告警全部 `window=0`。
- 已知边界：跨午夜时 `TodayViewModel` 的 M3-2 会把"未来选中日"夹回今天
  （`current > realToday`），所以把 App 开着过夜会退出预览；影响极小，
  与本次改动方向一致，未改。非规范 `scheduled_date` 的可达性由入口校验负责。
