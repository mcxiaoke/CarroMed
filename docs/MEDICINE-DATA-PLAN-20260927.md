## 0. 结论摘要

| # | 结论 | 依据 |

## 1. 数据规模（实测）

| 数据源 | 数据行数 | 体积 | 粒度 | 可用主键 |
|---|---:|---:|---|---|
| 国家药品编码本位码（国产） | 156,999 | 25.3 MB | 批准文号级 | 药品编码（14 位） |
| 国家药品编码本位码（进口） | 3,181 | 0.5 MB | 批准文号级 | 药品编码（14 位） |
| 医保药品分类与代码（西药、中成药） | 281,838 | 67.5 MB | **包装级** | 药品代码（20/23 位，唯一） |
| 2025 年医保目录（含商保创新药） | 4,830 | 340 KB | 品种级 | 编号（**跨章节重复**） |
| 国家基本药物目录 2026 年版 | 955 | 80 KB | 品种级 | 无 |

### 1.1 去重粒度（医保库口径）

| 粒度 | 记录数 |
|---|---:|
| 原始行（含包装明细） | 281,838 |
| + 企业 | 149,491 |
| **+ 剂型 + 规格**（建议的主表粒度） | **77,105** |
| + 剂型 | 25,860 |
| 仅通用名 | 16,598 |

本位码文件同口径「通用名+剂型+规格」为 63,560（国产 61,852 + 进口 2,415）。

> ⚠️ **不能直接把两个来源按「通用名+剂型+规格」并集去重**：两者「规格」列语义不同。
> 医保库的 `规格` 是规范化的短值（`0.25mg`），本位码文件的 `规格` 是整段注册规格原文
> （`每瓶内含四(2-甲氧异腈)络铜(I)氟硼酸盐 1.0mg,氯化亚锡 75μg,…`）。
> 实测：77,105 ∪ 63,560 = 125,633，但**交集只有 15,032**——说明这个口径下两边几乎不重叠，
> 强行并集会产生大量重复条目。**跨源去重必须走「药品本位码」。**

## 2. 四个关键发现

### 2.1 本位码文件不是最全的，且比医保库旧

| 指标 | 数值 |
|---|---:|
| 本位码文件编码数（原始口径） | 160,167 |
| 医保库本位码数 | 120,813 |
| 两者交集 | 104,963 |
| 仅在本位码文件（医保库没有） | 55,204（34.5%） |
| **仅在医保库（本位码文件没有）** | **15,850（13.1%）** |

本位码文件快照是 2026-06-30，医保库是 2026-08-28，**晚两个月**，所以有 1.5 万个新编码。
**结论：两者互补，必须合并，不能二选一。**

补充：本位码文件有 4,412 行的 `药品编码` 是**多值**，形如 `86906004000056；86906004000339`
（一个批准文号对应多个本位码，`；` 分隔）。拆开后本位码文件实际含约 16.2 万个编码。
**预处理必须按 `；` 拆行**，否则会漏掉约 9,800 个编码。

### 2.2 跨源唯一可靠主键是「药品本位码」

```
药品本位码（14 位数字）
  ├─ 本位码文件 .药品编码           约 162,349（拆行后）
  └─ 医保分类与代码 .药品本位码        281,752 行 / 120,813 个去重值
      交集 104,963    并集 约 176,000
```

医保库 `药品本位码` 字段格式规范度 **99.97%**（281,752 / 281,838 为标准 14 位数字），可放心做主键。
本位码文件标准化率 97.2%（152,587 / 156,999 单值），其余是多值待拆。

### 2.3 医保标记已内联，不需要 JOIN

医保分类与代码表的这 5 列**就是**医保目录信息：

| 列 | 含义 | 空值率 |
|---|---|---:|
| `甲乙类` | 甲 / 乙；**空表示不在医保目录** | 35.1% |
| `编号` | 医保目录编号 | 35.1% |
| `药品名称` | 目录中的药品名 | 35.1% |
| `剂型_目录` | 目录中的剂型 | 35.1% |
| `备注` | 目录支付限制（如「限消化道严重出血」） | 35.1% |

四列空值率完全一致（99,039 / 281,838 = 35.1%），自洽。

→ **判断「某药是否医保、甲类还是乙类、支付限制是什么」直接读这张表即可，零 JOIN。**
→ 医保目录表（4,830 行）只在需要「按分类树浏览目录」时才有独立建表价值。

关于 `编号` 的坑：目录西药部分编号 1–1446、中成药部分 1–1335、谈判部分 1–399，**编号跨章节重复**，
单独用 `编号` 关联会得到虚高的 100% 命中率。加上「药品名称」双条件后真实命中率为 **82.2%**，
其余差异来自目录用「通用名+剂型」（`克霉唑阴道乳膏`）而分类库用通用名（`克霉唑`）。
**因为 §2.3 已内联，本方案不需要依赖这个关联。**

### 2.4 基本药物标记：不需要 794 条人工映射

> **勘误**：本方案初稿估算「基药目录 794 条品种必须做一次性人工映射」，过于悲观。
> 补齐规则后实测可自动匹配 98.1%，人工量降到 15 条。以下为修正结论。

#### 匹配层面：加两条规则后自动率 98.1%

| 分层 | 条数 |
|---|---:|
| ① 精确命中药品库名称 | 565 |
| ② 前缀命中 / 剥离盐基后前缀命中 | 214 |
| ③ 仅子串命中（待确认） | 6 |
| ④ 完全无命中 | 9 |
| **合计** | **794** |

**三条关键规则**：

1. **剥尾部英文名**——基药化学药的名称是「中文名 + 英文名」拼接（`维A酸Tretinoin`、`青霉素Benzylpenicillin`），
   这是化学药精确匹配率为 0% 的直接原因。
2. **剥盐基 / 酸根前缀**——**这不是自造规则，是目录《凡例》第七条明文规定的**：
   「中文通用名中主要化学成分部分与《药品目录》中的名称一致且剂型相同，而酸根或盐基不同的西药，
   属于《药品目录》的药品。」据此 `盐酸多西环素片`、`注射用盐酸多西环素` 与基药品种 `多西环素` 属同一品种。
   这一条把匹配率从 70%（纯前缀）拉到 98%。
3. **匹配库扩到「医保库 + 本位码文件」**（20,258 个名称）——否则非医保药品（如 `胃复春片`）永远匹配不上。

**④ 完全无命中 9 条**中，7 条是**类别占位条目**（`结核病用药`、`艾滋病用药`、`血友病用药`、
`国家免疫规划用疫苗`、`避孕药`、`青蒿素类药物`、`抗蛇毒血清`），本就不对应具体药品；
其余 2 条是复合制剂（`复方氨基酸18AA`、`脂肪乳氨基酸葡萄糖`），药品库中名称不同。

#### 精度层面：这才是真正的工作量

若用前缀规则批量给药品打基药标记，3,109 个被命中的药品名中 **583 个（18.8%）** 是
「剥掉基药名后剩余部分不是剂型」——绝大多数是**复方制剂被短名误吸**：

| 误配模式 | 典型例子 | 量级 |
|---|---|---:|
| **复方制剂** | `二甲双胍` ← `二甲双胍格列本脲片`；`阿司匹林` ← `阿司匹林双嘧达莫片`；`西格列汀` ← `西格列汀二甲双胍片` | 约 500 条 |
| 同母核不同药 | `青霉素` ← `青霉素V钾片` / `青霉素钠` / `青霉素皮试剂` | 少数 |
| 中成药剂型标注（实为正确） | `六味地黄丸` ← `六味地黄丸(浓缩丸)` / `(水丸)` / `(大蜜丸)` | 约 60 条 |

#### 结论与人工量

**不需要 794 条逐条人工映射。** 人工只做三件事：

1. **建一张「复方成分词表」**（格列本脲、格列吡嗪、二甲双胍、氢氯噻嗪、丙磺舒、克拉维酸、舒巴坦、
   他唑巴坦、双嘧达莫、布洛芬、甲氧苄啶、碳酸铋、呋喃唑酮…）。命中即判为复方、不标基药——
   这一步可批量消掉约 500 条，**是主要工作量，但属于一次性配置而非逐条校对**。
2. **处理 15 条边界**（9 条无命中 + 6 条待确认）。
3. **补全剂型后缀词表**（中成药的 `(浓缩丸)`/`(水丸)`/`(无糖型)`、溶媒型的 `氯化钠注射液`/`葡萄糖注射液`）。

映射表结构建议保留 `match_type`（exact / salt-stripped / prefix）与 `confidence`，
便于日后目录更新时只复核低置信部分。

### 2.5 数据缺陷（PDF 提取侧，必须清洗）

`raw/2026_医保药品分类与代码_提取质检报告.csv`（在 MedicinesDatabase 仓库内）实测 **29,373 处**可疑单元格（占全部约 536 万格的 0.55%）：

| 列 | 可疑数 | 典型表现 |
|---|---:|---|
| 规格 | 15,675 | 括号跨行溢出：`每支95克(每支65g,含丁香酚0.455g,硼` + 下一行 `砂1 625 )每支装125g` |
| 注册规格 | 9,935 | 字符错乱：`0 0026 l复方` |
| 药品名称 | 2,963 | **相邻单元格文字交错**：`人精胰蛋岛白素人胰岛素混合(30R)`（应为 `精蛋白人胰岛素混合`） |
| 包装材质 | 647 | 括号未闭合（内容被截断） |
| 其他 | 153 | 备注 / 商品名 / 剂型等 |

成因是**源 PDF 的字体子集 ToUnicode 映射缺陷**（换 pdfplumber 提取结果一致，非工具问题）。

→ 清洗策略建议**「标记 + 降级」而非自动修复**：保留原值到 `*_raw` 列，可用的规范化值写入主列；
药品名称列受污染的 2,963 条（1.05%）需重点处理，因为它是搜索结果的主展示字段。

## 3. 表设计

**分表依据是「实体粒度」与「可变性」，不是「来源文件」**——这是对「字段不一样就要分表」的纠正。
医保库和本位码文件字段确实不同，但它们描述**同一个实体**（一个批准文号/包装），
应当**合并成同一张表**，用 `药品本位码` 去重，加一列 `source` 标注来源。

### 3.1 必需 4 张

#### T1 `medicine_generic` — 通用名字典（约 16,600 行）
一级搜索联想的入口，避免在 12 万行上做 `DISTINCT`。

| 列 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| name | TEXT | 通用名（如 `阿莫西林`） |
| pinyin_abbr | TEXT | 拼音首字母（`amxl`），预处理生成 |
| pinyin_full | TEXT | 全拼（可选，用于「阿莫西林」之外的拼音输入） |
| product_count | INTEGER | 下属条目数，用于展示「共 N 种」 |

索引：`name`、`pinyin_abbr`

#### T2 `medicine` — 药品条目（约 126,000 行，核心表）
粒度 = 通用名 + 剂型 + 规格。用户在这个层级「选中」一条药。

| 列 | 类型 | 说明 |
|---|---|---|
| id | INTEGER PK | |
| generic_id | INTEGER | FK → T1 |
| generic_name | TEXT | 冗余存储，便于免 JOIN 搜索 |
| dosage_form | TEXT | 剂型 |
| spec | TEXT | 规范化规格 |
| spec_raw | TEXT | 原始规格文本（保留，含缺陷） |
| is_insurance | INTEGER | 0/1（来自医保库 `编号` 是否非空） |
| insurance_class | TEXT | `甲` / `乙` / NULL |
| insurance_no | INTEGER | 医保目录编号 |
| insurance_name | TEXT | 目录药品名 |
| insurance_note | TEXT | 目录支付限制 |
| is_basic | INTEGER | 0/1（来自基药规则映射表，见 §2.4） |
| source | INTEGER | 1=医保库 2=本位码 3=两者 |
| is_qc_flagged | INTEGER | 该条目含缺陷单元格（供 UI 降级展示） |

索引：`generic_id`、`generic_name`、`pinyin_abbr`（冗余）、`is_insurance`、`is_basic`

#### T3 `catalog_basic` — 基本药物目录（955 行）

| 列 | 说明 |
|---|---|
| id, section(化学药/中成药), seq | |
| category | 分类（如 `（一）青霉素类`） |
| func | 功能（中成药列） |
| name | 品种名 |
| dosage_form_spec | 剂型、规格 |
| note | 备注（含 `注释1`、`△` 等标记） |
| mapped_count | 已映射的药品条目数 |

#### T4 `basic_medicine_map` — 基药 → 药品映射（约 794–3,000 行）
多对多关系，不要塞进 T3。

| 列 | 说明 |
|---|---|
| basic_id | FK → T3 |
| medicine_id | FK → T2 |
| match_type | auto / manual |
| confidence | 0–100 |

### 3.2 可选 2 张

#### T5 `medicine_package` — 包装/批准文号明细（约 282,000 行）

## 4. 字段裁剪建议（体积优化的关键）

医保库 62 MB 原始文本的字段占比：

| 字段 | 占比 | 是否入库 |
|---|---:|---|
| 药品企业 | 15.2% | 仅 T5 |
| 包装材质 | 13.2% | 仅 T5，且可裁剪 |
| 药品代码 | 9.4% | 仅 T5（主键） |
| 批准文号 | 9.1% | 仅 T5 |
| 注册名称 / 注册规格 | 16.2% | 与 `通用名`/`规格` **重复**，不入库 |
| 规格 / 剂型 | 11.0% | 入 T2 |
| 药品本位码 | 6.1% | 入 T5（索引） |
| 药品名称 / 剂型_目录 | 7.7% | 入 T2 |
| 备注 | 1.1% | 入 T2 |

→ `注册名称`/`注册剂型`/`注册规格` 与 `药品名称`/`剂型`/`规格` 大量重复，**只保留一套**，可省约 10 MB。

## 5. 体积三档与推荐

| 档位 | 内容 | 预置 DB 体积 | 说明 |
|---|---|---:|---|
| **A 轻** | T1 + T2 + T3 + T4 | **11–13 MB** | 满足「搜索 + 自动填充 + 医保/基药标记」，个人提醒场景够用 |
| **B 中（推荐）** | A + T5（精简：只留 barcode/批准文号/企业/商品名，砍掉包装材质） | **约 45 MB** | 额外支持扫条码定位、按厂家筛选 |
| **C 全** | A + T5 全字段 + T6 | **90–130 MB** | 不建议；带来的是个人提醒 App 用不到的能力 |

估算依据：T2 12.6 万行 × 64 B ≈ 7.7 MB（+索引 ≈ 9.6 MB）；
T5 28.2 万行 × 100 B（精简）≈ 27 MB（+索引 ≈ 34 MB）；全字段 28.2 万行 × 231 B ≈ 62 MB。

> 建议先做 **A 档**跑通链路，需要时再升 B。数据是静态的，升级只是换个 asset 文件。

## 6. 与 App 的集成方式

### 6.1 用独立只读 DB，不要并进主库

现有 `AppDatabase` 是 `version = 2`，且有 `MIGRATION_1_2`、刻意不用 `fallbackToDestructiveMigration()`。

**不推荐**把药品表塞进 `AppDatabase`：
- 必须 bump 到 version 3 并写迁移；
- 更麻烦的是 `createFromAsset()` **只在数据库文件不存在时生效**，老用户升级时主库已存在，
  拿不到预置数据，只能在迁移里手动 `ATTACH` + `INSERT SELECT`，成本高。

**推荐**新建独立的只读库：

```kotlin
@Database(
    entities = [MedicineGenericEntity::class, MedicineEntity::class,
                CatalogBasicEntity::class, BasicMedicineMapEntity::class],
    version = 1,
    exportSchema = false
)
abstract class MedicineDatabase : RoomDatabase() { ... }
```

- 文件名带数据版本：`medicines-20260828.db`，放进 `app/src/main/assets/`
- 构建时用 `createFromAsset("medicines-20260828.db")`
- 与用户数据完全解耦；药品库升级＝换个 asset，主库版本不动
- 注意 Room 需要 DB 可写才能真正打开（SQLite 只读模式 + WAL 有坑），**只在代码约束上只读**，不要设 `readonly`

### 6.2 构建产物

清洗后的数据已独立成仓库 **`C:/Home/Projects/MedicinesDatabase`**（自带 git、README、字段字典与校验脚本），
本 App 侧只需要从它派生两样东西：

1. `medicines-<date>.db` — Room 只读预置库，放入 `app/src/main/assets/`

## 7. 搜索方案

| 层级 | 数据源 | 交互 |
|---|---|---|
| 一级 | T1 `medicine_generic`（1.66 万） | 输入 `amxl` 或「阿莫」→ 列出通用名 |
| 二级 | T2 `medicine`（12.6 万，`WHERE generic_id = ?`） | 列剂型+规格，显示医保/基药角标 |
| 三级（可选） | T5 `medicine_package` | 展开厂家 / 批准文号，或扫码直接定位 |

- **拼音**：预处理用 `pypinyin`（当前 venv 未安装）生成首字母与全拼，写入 `pinyin_abbr`。
  1.66 万个名字，一次生成即可。
- **索引策略**：一级搜索是**前缀匹配**（`LIKE 'amxl%'`），1.66 万行 + 索引足够快，
  **不需要 FTS**。若后续要「中间匹配」（输入 `mx` 命中「阿莫西林」），再考虑 FTS4 的 trigram 分词。
- **搜索范围**：T1 只有 1.66 万行，可全量联想；T2 按 `generic_id` 过滤后通常几十行，无性能问题。

## 9. 实施步骤

1. **预处理脚本**：读 5 个 CSV → 拆行 / 清洗 / 合并 / 生成拼音 → 输出 `medicines.db`
2. **人工复核**：基药映射的 15 条边界 + 复方成分词表 + 抽查 QC 缺陷处理结果
3. **接入 App**：`MedicineDatabase` + `createFromAsset` + DAO（只读查询）
4. **UI**：添加药物页改造成两级选择器（通用名 → 剂型规格），带医保/基药角标
5. **回归**：确认主库 `carromed.db` 版本仍为 2、迁移逻辑未受影响

## 10. 风险与边界

| 风险 | 影响 | 应对 |
|---|---|---|
| 药品名称列 2,963 条文字交错（1.05%） | 搜索结果展示错乱，可能选中错误药品 | 标记 `is_qc_flagged`，UI 降级提示；重点人工抽查常用药 |
| 基药前缀映射误吸复方制剂 | 约 500 个药品被错误标注「基药」 | 复方成分词表命中即不标；仅高置信（exact / salt-stripped）才自动打标，prefix 类标记为待确认 |
| 目录名与药品库名格式差异大 | 直接字符串匹配不可用 | 依据《凡例》第七条做盐基/酸根归一化，见 §2.4 |
| 数据快照静态 | 新药/目录调整后数据过期 | asset 文件名带日期；预留「数据版本」设置项展示 |
| 医保库与本位码文件编码不一致 | 同一药出现两条 | 以本位码为准合并；无本位码的条目保留但标注来源 |
| 45 MB 预置库增大 APK | 下载转化率 | 优先 A 档（12 MB）；T5 可做成可选下载包 |
| `编号` 跨章节重复 | 误用会得到假关联 | 本方案不依赖该关联；若要用必须按章节区分 |
