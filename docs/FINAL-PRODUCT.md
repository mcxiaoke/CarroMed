## 一、产品定位

**CarroMed 是一款纯本地离线、免登录、零广告、注重隐私的 Android 个人用药提醒与库存管理工具。**

核心用户价值（按优先级排序）：

1. **提醒可靠**：到点一定响，绝不静默漏提醒——这是产品第一承诺，一切设计为其让路；
2. **记录真实**：吃过的药永不丢失、永不串改，改计划不冲掉历史；
3. **数据自主**：数据 100% 存本机，随时完整导出带走，无任何云依赖；
4. **长期统计**：准确回答"过去一个月/一年吃了多少药、按时率多少"。

**目标用户**：需要长期/多药管理服药的个人（慢病患者、老人及其代管家属）。单设备单用户。

## 二、范围决策表（已拍板）

以下决策综合三份审查的争议点，全部在零代码阶段定死。任何一条的变更都需要重新评审架构文档。

| # | 决策项 | 结论 | 理由 |
| :--- | :--- | :--- | :--- |
| D-1 | 产品边界 | **仅做用药**。不做通用待办、不做饮水/量血压记录 | 通用条目需把 medications 抽象为 items + 子表拆分，成本高且偏离核心价值；"记水"从全部示例中移除 |
| D-2 | 用户模型 | **单用户单设备**，不做家庭成员/多 profile | 预留成本极低（所有表都在 medication 之下），v1 不做 |
| D-3 | 技术栈 | **原生 Android (Kotlin + Jetpack Compose + Room + Coroutines/Flow)** | 既然仅支持 Android，原生 Compose 彻底消除了 Flutter 与 Android 后台闹钟/通知栏事务跨语言调用的撕裂问题；Room 原生响应式 Flow 驱动 UI，包体积仅 5~8MB，冷启动 <300ms，后台 BroadcastReceiver 直写 Room 耗时 <15ms，架构最纯粹清晰 |
| D-4 | 分发渠道 | **仅国内渠道直发 APK**，不上架 Google Play | 规避 `USE_EXACT_ALARM` 的 Play 政策审核风险；精确闹钟走 `SCHEDULE_EXACT_ALARM` 申请 + `setAlarmClock` 兜底 |
| D-5 | 最低系统版本 | **Android 8.0 (API 26)** | 通知渠道为 8.0 引入，再向下兼容无意义 |
| D-6 | 语言 | v1 仅简体中文，但**全部文案走资源文件 strings.xml**，不硬编码 | 为未来 i18n 留口，成本为零 |
| D-7 | 库存记账 | **整数毫单位记账**（如 1.5 片 = 1500），全程无浮点 | 杜绝账本对账漂移；UI 层做单位换算展示 |
| D-8 | 库存参与度 | **库存为可选功能**（`stock_tracking_enabled` 开关），关闭则完全跳过扣减与预警 | 强制填库存是同类 App 第一大流失原因 |
| D-9 | 库存不足时 | **允许扣为负数，绝不阻止打卡**；负库存单独视觉化提示盘点 | 服药是物理事实，优先于库存记账；出差忘带药是日常场景 |
| D-10 | 主键策略 | **INTEGER 自增主键 + 覆盖式恢复**（不采用 ULID） | 恢复语义定为"整库覆盖替换"，自增 ID 原样写入即可，无需 ID 重映射子系统；比 ULID 更简单 |
| D-11 | 统计指标 | 主指标**完成率**，次指标**准时率**（窗口按药可配）；不引入 MPR/PDC 临床指标 | MPR/PDC 对个人用户认知成本高；完成率+准时率覆盖核心诉求，口径见架构文档第七章 |
| D-12 | 锁屏通知隐私 | **默认显示药品名**（可用性优先，目标用户含老人），提供"仅显示'该吃药了'"与"隐藏"两档开关 | 隐私默认保护会导致老人用户看不懂提醒反而弃用；把选择权交给用户并在设置中显眼呈现 |
| D-13 | 备份 | 本地**自动滚动备份**（保留最近 5 份，应用自管目录）+ 手动导出（可选口令加密）；系统云备份 `allowBackup=false` 显式关闭 | 数据不出设备是产品承诺，Android Auto Backup 默认会把用药数据传 Google 云，必须关 |
| D-14 | 提醒降级 | 三档：精确闹钟 → `setAlarmClock` 兜底 → WorkManager+启动对账自愈；降级状态在"提醒健康检查"页对用户可见 | 详见架构文档第五章 |
| D-15 | 疗程/有效期/患者档案/临床备注/PDF 报告/桌面小组件 | **全部列入 v2 backlog，不进 v1 模型** | v1 聚焦"提醒+打卡+库存+统计"闭环；上述能力均可在现有模型上增量扩展，不构成推倒风险 |
| D-16 | 极简录入体验 | **仅药品名称（title）与时间必填，其余全可选** | 绝大多数用户日常添加药品只需输入药名+选时间即可立即启用；描述、分类、颜色、库存、规格均为可选折叠项，并在 DB 中合理预留字段，杜绝录入卡点 |

## 三、核心领域术语表（一词一义，三份终稿共用）

| 术语 | 英文 | 定义 | 存储形态 |
| :--- | :--- | :--- | :--- |
| 药品 | Medication | 用户药箱中的一个实体（含名称、规格预留、注意事项预留、库存） | `medications` 表 |
| 排程规则 | Schedule Policy | 某药品在某时间区间内的服药规则（频次+时间点+剂量），版本化、可截断 | `schedule_policies` + `policy_times` |
| 槽位 | Dose Slot | 规则在某一天某一时点的**投影实例**，承载当日可变状态（待服/推迟/已服/跳过/过期/取消） | `dose_slots` 表，**可再生缓存，slot.id 即闹钟 RequestCode** |
| 服药事实 | Dose Record | 真实发生的服药事实（含撤销标记 `status=COMPLETED/CANCELLED`），含完整快照 | `dose_records` 表，单表完成统计 |
| 库存流水 | Inventory Transaction | 库存变动的记账凭证（自动扣、补药、撤销对冲） | `inventory_transactions` 表，append-only |

**关键非对称性**：槽位是缓存，任何时候可由规则重算重建；事实与流水是真相，永不可变。开发者严禁把槽位当真相使用。

## 五、六大边缘场景（最终行为定义）

以下场景全部基于"槽位层落库 + 事实层 append-only"的最终模型，行为已定死：

### 场景 1：当天已服药后中途改计划
- 08:00 已服的槽位与对应事实**绝对不动**；
- 改计划 = 旧规则 `effective_until_date` 截断至昨日（自今日起失效），新规则 `effective_from_date` = 今日；今日的槽位迁移由"当日差分对齐"完成（见架构文档 4.2）；
- 当日差分对齐：**未来**的 PENDING 槽位按新规则重建；**已过期未响应**的槽位转 EXPIRED；**今天更早且仍 PENDING** 的槽位转 CANCELLED 并提示用户可补服（消灭悬挂 PENDING）；
- UI 弹"历史保护提示"：已服记录完整保留。

### 场景 2：手滑点错打卡
- 5 秒 Undo 窗口（Toast 内可直接恢复）；窗口过后仍可从"已解决"区撤销；
- 撤销 = 槽位 TAKEN→PENDING（槽位是缓存，可回退）+ 事实层追加 REVERT 修正 + 库存对冲流水，全程留痕；
- 若计划时间已过且临近，提示是否重激活提醒。

### 场景 3：历史补录与修正
- 补录优先绑定已存在的 PENDING/EXPIRED 槽位（幂等，杜绝重复扣库存），无匹配槽位才新建事实（PRN 式）；
- 改剂量 = 追加 DOSE_CORRECTION 修正（含差额）+ 库存差额流水，原事实不动；
- 改实际时间 = 追加 TIME_CORRECTION 修正。

### 场景 4：停药换药
- 有历史记录的药品强制"停药归档"：`is_archived=1`、注销全部挂起闹钟、今日/药箱列表隐藏、统计与历史**永久保留**；
- 从未打卡过的药品允许物理删除。

### 场景 5：临时加服 / 按需药（PRN）
- 不建规则，直接记一条无槽位事实 + 扣库存流水；
- 计入消耗量统计，**不进依从率分母**（无计划即无应服）。

### 场景 6：多次推迟（Snooze 链）
- 推迟状态只存在于槽位（`snooze_until`/`snooze_count`），**事实层无 SNOOZED 状态**；
- 上限 3 次，超过自动转 EXPIRED 并在今日页汇总提示"该药今天已错过"；
- 推迟闹钟与正常闹钟用同一槽位 ID 隔离（RequestCode = slot.id，详见架构文档），绝不与其他槽位碰撞；
- 推迟跨越下一个槽位时点时，两条各自独立提醒（不合并、不覆盖）。

## 六、数据归属与隐私承诺（产品级约束）

1. 数据仅存于应用沙箱与应用自管备份目录，**零网络权限**（`INTERNET` 权限不声明，从权限层面物理断网）；
2. 系统云备份显式关闭（`allowBackup=false` + `dataExtractionRules` 禁止）；
3. 锁屏通知隐私三档可配（见 D-12）；
4. 备份可口令加密（AES-GCM）；CSV 分享默认含完整药名，提供脱敏开关（药品 A/B）；
5. 应用内提供隐私说明页：明示"数据仅存本机、如何备份、卸载即清除"。

## 九、v2 backlog 的扩展性论证（为何现在不做是安全的）

| backlog 能力 | 未来扩展路径 | 是否需要动 v1 模型 |
| :--- | :--- | :--- |
| 疗程 | `schedule_policies` 加 `planned_end_date` + 疗程提醒类型 | 加字段即可 |
| 有效期 | `medications` 加 `expiry_date`/`opened_at` + 报废流水类型 | 加字段+加枚举值 |
| 患者档案/过敏史 | 新增 `patient_profile` 表，独立于药品 | 新表，零侵入 |
| 临床备注 | 新增 `clinical_notes` 表 | 新表，零侵入 |
| PDF 报告 | 从统计模块派生渲染 | 纯展示层 |
| 小组件/磁贴 | 复用通知 Action 的原生事务路径 | 零模型改动 |
| 多用户 | 全表挂在 medication 之下，加 `profile_id` 列 + 过滤 | 一次迁移可完成，成本可控 |

**结论**：v1 模型对 backlog 全部能力保持前向兼容，砍 scope 不产生推倒风险。

## 十、里程碑（产品视角摘要，工程细节见架构文档第九章）

| 阶段 | 交付 | 出口标准 |
