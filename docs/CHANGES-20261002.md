# CHANGES-20261003 —— 崩溃现场外投 Downloads 批次（真机验证后定稿）

> **变更时间**：2026-10-03 08:55 (GMT+8)  
> **起因**：用户反馈「重装后首次打开不久即崩，只能清数据恢复，日志随清数据一并消失，无法 debug」。  
> **验证**：`testDebugUnitTest` **583 条全绿**（新增 11 条）；`compileDebugKotlin` / `compileReleaseKotlin` / `assembleDebug` / `assembleRelease` 全通过；  
> **模拟器 API 35（走 MediaStore 主路径）端到端实测通过**。  
>
> **重点变更摘要**：
> 1. **诊断日志双写**：崩溃现场除写内部 `filesDir/logs/crash-*.txt` 外，**额外外投一份到系统 `Download/CarroMed/`**。内部目录是应用私有数据，清数据即失；Downloads 不随清数据消失，是唯一能跨过"清数据"这道坎的落点。内部那份不省——App 内诊断入口要读，且外投超时时它是唯一兜底。
> 2. **零权限外投**：API 29+ 走 `MediaStore.Downloads` + `RELATIVE_PATH`（分区存储下该集合对写入方不设权限门，`WRITE_EXTERNAL_STORAGE` 在 29+ 已是 no-op）；26-28 仅在权限**已授予**时走公共 Downloads，否则降级 app 专属外部目录。**全程不主动申请存储权限**——为一个崩溃时才用一次的诊断功能在首启弹权限框，代价大于收益。已核对 manifest：**零新增存储权限**。
> 3. **崩溃现场外投有界超时**：MediaStore 写入是 Binder IPC，崩溃时 system_server 若恰好繁忙，这次 IPC 可能长时间不返回。在崩溃线程上同步写会把"留痕"变成"把崩溃 hang 成 ANR"，比不写更糟。故改为**守护线程 + 1.5s 有界 join**，超时即放弃（daemon 不阻止进程退出），由下次启动补投兜底。
> 4. **启动补投兜底**：外投超时的崩溃、以及压根走不到 `UncaughtExceptionHandler` 的 native crash / OOM kill，都由 `AppLogging.install` 的启动扫描补投。目标名由源文件名推导（崩溃件信**文件名内时间戳**而非 mtime，避免复制/同步致 mtime 漂移后用户对照时误以为丢了一次崩溃；解析失败才回落 mtime），故重复启动只覆盖同一份。
> 5. **分层**：`DiagnosticExport`（`core/domain`，零 `android.*`）只管命名与选片判据，纯 JVM 可直测（11 条）；`DownloadsLogExporter`（`core/data`）只管 IO 与权限分支。选片判据是本功能最易静默出错处（筛掉崩溃件=故障现场丢失且无报错）。
> 6. **debug 源集**新增 `com.mcxiaoke.carromed.dev.EXPORT` 广播，可 adb 主动触发外投以验证链路（release 包不含）。
>
> ### 外投文件名定为 `.txt`（真机实测拍板，非原始设计）
>
> 原始设计用 `carromed-crash-20261002221245.log`，模拟器实测 API 29+ 上 MediaStore 依
> `MIME_TYPE=text/plain` 反推扩展名，`.log` 不在映射表内 → 落盘变成 `.log.txt`（已用
> `content query` 核实 `mime_type=text/plain`）。**系统行为，换 MIME / 加 FLAG 均无效。**
>
> 更麻烦的是连锁反应：旧件叫 `xxx.log.txt`、新件请求 `xxx.log`，两者对不上，
> **按请求名去重彻底失效**，每次导出多一份 `xxx.log (1).txt` 僵尸副本。
>
> 既然 `.txt` 躲不掉（用户已确认接受），那就**直接用 `.txt`**：请求名 == 落盘名，
> 去重、清理、用户肉眼所见三者自然一致。最终产物：
> `Download/CarroMed/carromed-crash-20261003005324.txt`
> （另有 `carromed-log-20261003.txt` 运行日志外投）。
>
> ### 真机验证（API 35）——抓出三处单测看不见的缺陷
>
> 单测全绿不等于功能成立。端到端实测发现并修复：
>
> 1. **扩展名被改名**（见上）→ 定为 `.txt`。
> 2. **清理时机错误：写在清之前**。最初把 `purgeStaleArtifacts` 放在 `exportAll` 开头，
>    实测只清得掉**上一轮**遗留，本轮 insert 顺手生成的副本无人收拾，越导越多
>    （副本从 `(1)` 恶化到 `(2)`）。**修法**：清理内聚到 `writeViaMediaStore` 的 `finally`
>    ——**写完再清**，且崩溃路径（`exportCrashBlocking`）也因此获得清理覆盖。
> 3. **去重曾依赖"插入后回读实际名字"**这一 workaround。改用 `.txt` 后请求名即落盘名，
>    该回读逻辑降级为纯兜底（防某家 OEM 仍擅自改名），主路径不再依赖它。
>
> 清理判据收窄到三类且不误伤正常件：`.pending-` 孤儿、含 `(N)` 后缀的副本、
> `is_pending=1` 卡住的残留。
>
> **实测结果**：崩溃 → `Download/CarroMed/carromed-crash-20261003005324.txt`
> （含版本号/线程/崩溃前日志/完整堆栈含 `Caused by`）；**`pm clear` 后内部 `files/logs/`
> 消失而 Downloads 崩溃现场完好幸存**（核心承诺成立）；连启三次文件数/名/大小零变化
> （幂等成立）；启动补投日志确认
> `diagnostics exported to Downloads/CarroMed: carromed-log-20261003.txt (via MediaStore/Downloads)`。
>
> ⏸ 未覆盖：API 26-28 legacy 路径（模拟器为 API 35）、崩溃瞬间 system_server 繁忙导致
