## 0. 结论摘要

### 0.1 总体评价

CarroMed 的**底层产品判断是一流的**：「计划规则 / 槽位 / 服药事实」三层解耦、事实不可变、会计式库存账本、纯本地离线免登录——这套骨架在同类产品里明显领先，也确实在代码中落地了（不是停留在文档）。列表页「极简索引、详情页承载全部」的设计方向正确，打卡主操作单点突出、低频操作收拢，页面整体克制不喧宾夺主。

但当前产品处于一种 **「骨架先进、表层欠打磨」** 的状态，集中暴露三类问题：

1. **承诺未兑现（执行缺口）**：终版文档白纸黑字承诺的若干关键体验——**锁屏全屏闹钟、"一把药"分组批量确认、合并通知、健康状态徽标、锁屏隐私三档、铃声/震动模式**——在实际代码中**均未实现**，其中"全屏闹钟"恰恰服务于第一承诺"提醒可靠"，是最伤产品信用的缺口。
2. **信息架构有硬伤（可发现性）**：**全局"设置"入口仅存在于使用频率最低的"统计"Tab**，今日页声明了设置回调却未接线；用户最难找到的，恰恰是权限自检、备份、铃声这些"保命/保数据"功能。
3. **核心任务流被拉长（效率）**：新建药品与设置提醒被拆成两段，**新建的药默认没有任何提醒**，与 D-16"名称 + 时间必填"直接冲突，也与第一承诺相悖；误触后的"5 秒撤销"从列表上消失，纠错要多绕两层。

### 0.2 启发式评估打分（1–5 分，5 为最佳）

| 评估维度 | 得分 | 一句话诊断 |
| :--- | :---: | :--- |
| 信息架构与可发现性 | **2.5** | 设置入口错位、健康徽标缺失，全局功能可达性差 |
| 核心任务流效率 | **3.0** | 打卡单点清晰，但建药→提醒链路被人为拉长 |
| 视觉一致性 | **3.5** | 色彩/形状规范良好，但顶栏不统一、字号硬编码多 |
| 系统状态可见性与反馈 | **2.5** | 无全屏闹钟、无铃声可选、无打卡触觉反馈 |
| 错误预防与恢复 | **3.0** | 失败提示通道已补齐，但列表级 Undo 缺席 |
| 适老化与无障碍 | **3.0** | 形状冗余做得好，但热区偏小、TalkBack 未审计 |
| 首次启动体验 | **2.5** | 无三步引导，权限申请冷启动直给、缺上下文 |
| 承诺功能完整度 | **3.0** | 文档承诺的 6 项关键体验未落地 |

> **综合：约 2.9 / 5**——"可靠的单机用药工具"内核已成型，但距离"到点一定响、老人也能用"的发布标准，还差一轮以**全屏闹钟 + 设置可达性 + 建药流**为核心的体验收口。

### 0.3 三句话结论

1. **先还"承诺债"**：全屏闹钟、一把药分组、合并通知、健康徽标、隐私三档、铃声选择，是 FINAL 文档已拍板、用户也最期待的能力，应在发布前按优先级补齐。
2. **再治"可达性"**：把设置放回今日页顶栏、把健康检查入口做进今日页，让"保命/保数据"功能一触即达。
3. **后做"打磨层"**：统一顶栏与字号体系、补足触觉与 5 秒 Undo、完成 TalkBack 与 200% 字号验证，把适老化从"原则"变成"可验证的事实"。

- **量化证据（本次实测）**：
  - 全 UI 层硬编码字号字面量（`.sp`）**约 63 处**（不含 `Type.kt` 内的样式定义），散落于 15 个文件；
  - `contentDescription = null` **28 处**，分布于 12 个文件（部分为装饰性图标，需逐项审计）；

## 3. 信息架构与导航问题

### U-01【P0】"设置"入口错位，仅藏在"统计"Tab，今日页回调未接线

**现状**：
- 全局设置齿轮**只**出现在统计页顶栏（`StatsScreen.kt:67-72`，`actionIcon = Icons.Outlined.Settings`）；
- 今日页虽然声明了 `onNavigateToSettings` 回调（`TodayScreen.kt:99`）、也 `import` 了设置图标（`TodayScreen.kt:31`），但**全函数未使用**——顶栏 `actions` 里只有连续打卡徽章（`TodayScreen.kt:135-140`），设置入口实际未渲染。

**影响**：设置承载的是**权限健康自检、备份与恢复、铃声、（规划中的）隐私三档**等"保命/保数据"功能，却埋在使用频率最低的 Tab。新用户在"提醒为什么没响 / 想备份"时几乎必然迷路。这是典型的"功能存在但不可发现"，比功能缺失更挫败。

**建议**：
1. 今日页顶栏 `actions` 增加设置齿轮（接线已有的 `onNavigateToSettings`），与连续打卡徽章并列；
2. 或采用 Android 惯例：今日页顶栏右侧放**健康徽标**（见 U-03）+ 设置齿轮；统计页齿轮可保留可去除；
3. 验收：从今日页 ≤1 次点击可达设置；走查脚本补该路径断言。

### U-02【P1】二级页数量多、层级深，缺少全局返回/定位一致性

**现状**：二级页已达 9 个，且进入路径深浅不一。例如"修改提醒"需 药箱 → 药品详情 → 提醒设置（3 层）；"盘点库存"需 药箱 → 详情 → 库存（3 层）。各二级页顶栏不统一（见 V-04），返回形态有箭头、有"取消"文字两种。

**影响**：用户在深层级容易丢失"我从哪来、还能去哪"的定位；多药、多操作时反复进出，路径冗长。

**建议**：
1. 统一二级页顶栏为 `CarroMedTopAppBar` + 标准返回箭头 + 页名字号；表单页（添加/补录）可用"取消/保存"，但全 App 只此一种例外；
2. 药品详情页作为该药品的**唯一枢纽**，把"提醒设置 / 库存 / 补药 / 历史"做成同页锚点卡片（现状已基本如此），减少跨页跳转；
3. 关键操作（补药、盘点）支持完成后**逐级返回或直接回今日页**，避免一层层后退。

### U-03【P1】"健康状态徽标"未实现，提醒链路降级对用户不可见

**现状**：FINAL-UI §四 规定今日页右上有健康徽标（绿=链路正常 / 黄=降级中，点击进入健康检查页）。实际顶栏只有**连续打卡徽章**（`TodayScreen.kt:136-139`），健康检查页只能经 设置 → 保活自检 进入（而设置本身难找，见 U-01）。

**影响**：当精确闹钟权限被撤、电池白名单失效、通知渠道被关时，**用户在首页看不到任何"提醒可能不响"的信号**，直到真的漏服。这与"第一承诺"形成信任落差。

**建议**：
1. 今日页顶栏增加健康状态圆点（复用健康检查页已有的检测项结果聚合：全绿 / 有黄或红）；
2. 黄/红态常显并可一键进入健康检查；全绿态可弱化为小图标；
3. 连续打卡徽章与健康徽标分工：**打卡徽章=成就（可保留现状入口到月历），健康徽标=链路安全**，不互相替代。

### U-04【P2】进展页"三视图"实际为"两视图"，月历热力图位置与文档不一致

**现状**：FINAL-UI §九 规定进展页含「7 天阵列 / 流水 / 月历热力图」三视图；实际 `ProgressScreen` 只有阵列、流水两个 Tab，月历热力图移到了今日页打卡徽章弹窗（`DoseHistoryCalendarSheet`）。

**影响**：功能仍在、未丢失，但与文档不一致；用户在"进展"视角下无法直接看月历，认知动线被打断。

**建议**：二选一——① 按文档把月历热力图作为进展页第三视图；② 更新 FINAL-UI，明确"月历入口在今日页徽章"，消除文档与实现的长期分叉（建议选 ②，避免与今日页重复）。

## 4. 核心任务流程问题

### F-01【P0·需产品拍板】新建药品与设置提醒割裂，"新建的药默认不提醒"

**现状**：
- 添加/编辑页已**移除全部排程字段**（频次、时点、剂量，见 `AddEditMedicationScreen.kt` 注释中 2026-09-29 的 UX 变更），页面仅采集药品档案信息；
- 保存后跳转药品详情页，用户需自行点击"提醒设置"才能配置频次与时间；
- 页内虽有提示卡"保存后进入详情页设置提醒"，但**没有强制引导**。

**问题**：
1. 与 **D-16「仅药品名称与时间必填」直接冲突**——时间不再必填，结果是**新建药品默认没有任何提醒**；
2. 用户的核心任务"每天早上 8 点提醒我吃 X"从 **1 段变成 3 段**（填档案 → 保存 → 详情页找提醒设置 → 配置），中途流失即"永不提醒"；
3. 这与产品**第一承诺"提醒可靠"**在用户旅程的第一步就埋下断点。

**竞品做法**：MyTherapy、Medisafe、药管家**无一例外**在"添加药品"流程内完成时间/频次设置（数据库选药或扫码后即进入频次与时间），把"建档即会响"做成默认。

**建议（按推荐排序）**：
1. **【推荐】创建流程内联"最简提醒"**：在档案表单底部加一个默认展开的最简区块——"需要提醒吗？（默认开）每天 1 次，时间 08:00（可改）"，高级频次进"提醒设置"。既保住"极简录入"，又保证"建档即响"；
2. **【次选】保存后强引导**：保存后不直接落详情页静态展示，而是弹出/直达提醒设置，完成后才进入今日页；"仅建档、暂不提醒"需用户显式选择；
3. 无论哪种，**"无提醒的药品"在今日页/详情页应有明显标记**（如"未设置提醒"警示条 + 一键去设置），不允许静默存在。

> 备注：把"药品档案"与"排程规则"在**数据层**解耦是完全正确的（应坚持）；本问题针对的是**用户交互层**不应让用户为这种解耦付成本——解耦应发生在底层，而非把流程切碎给用户。

### F-02【P1】"一把药"分组批量确认未实现，多药用户重复打卡

**现状**：FINAL-UI §四、M-04 明确"同一时点（±5 分钟）的多药合并为一组，组级『全部已吃』原子批量确认"。实际 `pendingItems` 是按时间排序的**扁平列表**（`TodayViewModel.kt:78、247`），每个药品一张独立卡片、各自一个打卡按钮。

**影响**：以目标场景（早 8 点同时吃 2–3 种药）为例，用户需逐一点击 N 次；漏点其中一种即被记为"未确认"。批量确认是用药 App 的高频刚需，也是"合并通知"在 App 内的对应动作。

**建议**：
1. 今日待服列表按"时点（±5 分钟容差）"分组渲染：组头显示"09:00 · 共 2 种药"+ 组级"全部已吃"主按钮；
2. 组内保留各药子卡片（可展开看说明、单独打卡），兼顾"一把吃"与"只吃其中一种"；
3. 批量确认复用现有单药打卡的事务路径，保证**原子性**（全成功或全不执行）与库存逐药扣减；
4. 该分组逻辑与 F-03 合并通知**共用同一套分组判据**，避免两处定义漂移。

### F-03【P1】多药同时到点"合并通知"未实现，锁屏堆叠多条

**现状**：M-03 承诺"多药同时到点合并为一条通知 + 全部已吃"。实际 `Notifications.showDoseNotification` 按每个 slot 独立发通知（id = `slot.id`）；`AlarmReconciler` 仅做**错峰**（其注释直言"全部同一瞬间弹出会糊成一片，错开一点"，`AlarmReconciler.kt:98`），并未合并。

**影响**：同一时刻锁屏/通知栏出现多条提醒，用户要逐条处理、逐条点"已吃"，体验嘈杂且易漏；与 F-02 共同削弱"一把药"场景。

**建议**：
1. 通知发送侧按"时点 + 容差"聚合：同一组只发一条通知，`InboxStyle`/`BigTextStyle` 列出各药，Action 为「全部已吃 / 推迟 / 跳过」；
2. 点"全部已吃"走与 F-02 相同的批量事务；通知体点击展开可逐药操作；
3. 错峰作为"无法合并时"的兜底，而非主方案。

### F-04【P1】误触后"5 秒撤销"从列表消失，纠错路径变长

**现状**：FINAL-UI §12 场景 2 规定"5 秒 Undo 窗口（Toast/Snackbar 内可直接恢复）"。实际列表卡上**不再放撤销**（`TodayScreen.kt:758` 注释，2026-09-29 起低频操作统一收进记录详情页）；打卡后列表上没有 Undo 入口，用户需：找到已服项 → 点进记录详情 → 找"撤销"。

**影响**：手滑点错是用药 App 的高频失误，恢复成本从"1 次点击"变成"3 次点击 + 两次页面跳转"。尼尔森"用户控制与即时退出"原则要求高频可逆操作就近提供出口。团队"列表只留高频动作"的出发点可以理解，但**撤销恰恰是打卡后的高频紧接动作**。

**建议**：
1. 打卡成功后用 Snackbar 提供 **5 秒"撤销"**（带库存已加回的说明），与现有 `snackbarHostState` 复用，成本低；
2. 记录详情页的"撤销"作为窗口过期后的兜底（保留现状）；
3. 同理，"跳过"也应支持 Snackbar 撤销（误跳比误打更常见地影响完成率）。

### F-05【P1·待产品拍板】手动补录语义未决："补打卡"与"额外服药"混为一谈

**现状**：开放问题清单 **D1** 已记录：`logManualDose` 只写 `slotId = null` 的独立事实，**不回填当日开放/过期槽位**。于是用户"补一次早上忘打的卡"后，完成率仍把该次算漏服；补录页也未在文案上区分两种意图。

**影响**：补录是高频纠错手段，但当前结果可能与用户预期相反（"我都补了，为什么完成率还是低？"），统计可信度受损。

**建议**：
1. 产品先定语义（开放问题 D1）：**推荐**补录默认"补打卡"——按 `(药品, 当天, 时间最近的开放/过期槽位)` 命中并完成；"额外加服（PRN）"作为显式选项；
2. 补录页顶部用两个意图入口或开关区分"补上漏服的计划剂量 / 记录一次计划外服药"；
3. 命中槽位时提示"将完成当天 08:00 的计划剂量"，未命中时提示"记为一次计划外服药（不计入完成率）"，让结果可预期。

### F-06【P2】打卡成功缺少触觉反馈，操作"确认感"不足

**现状**：全工程除通知渠道的震动开关（`Notifications.kt:59、69`）外，**UI 交互无任何触觉反馈代码**（无 `performHapticFeedback` / `Vibrator` 调用）。FINAL-UI §四 提到"打卡触觉震动"。

**影响**：打卡是最高频动作，缺少触觉"咔哒"确认，尤其在单手、视线不看屏幕时，用户不确定是否点中；老人更依赖多感官确认。

**建议**：打卡成功给一次轻触反馈（`HapticFeedbackType.LongPress` 或预定义 `VirtualButton`/`Confirm`），批量确认给一次稍强反馈；错误/禁用不震动。注意遵循系统"触感反馈"设置，不引入强权限依赖。

## 5. 视觉设计问题

### V-01【P1】通知小图标用系统通用图标，品牌专业感受损

**现状**：`Notifications.kt:188` 使用 `setSmallIcon(android.R.drawable.ic_dialog_info)`——这是 Android 系统的通用"信息"图标，不是 App 自有图标。

**影响**：状态栏/通知栏/锁屏上，提醒显示为一个通用系统符号，既无品牌识别，也容易被误认为系统提示，专业感与可信度下降。竞品均使用自有药丸/品牌单色图标。

**建议**：提供符合通知规范的**白色单色透明小图标**（如药丸/胶囊剪影，`Notification` 专用 drawable），替换系统图标；同步配置应用图标与圆形图标。

### V-02【P1】基础正文字号偏小，与"老人友好、默认偏大"原则有差距

**现状**：`Type.kt` 中 `bodyMedium = 13sp`，而用药说明、时间、库存等大量信息以 bodyMedium/bodySmall 呈现；分段选择器出现 11sp（`ReminderSettingsScreen.kt:226`）、12–13sp 多处。

**影响**：目标用户含慢病老人，13sp 正文在标准视口上偏小，弱光/老花场景阅读吃力；11sp 已接近可读性下限。

**建议**：
1. 基础正文上调（如 bodyMedium 14–15sp、bodySmall 不低于 12sp），关键信息（时间、剂量、库存）用 bodyLarge/titleMedium；
2. 分段按钮文字不低于 13sp，宁可减少每段字数也不缩字号；
3. 保证系统字号缩放到 130%–200% 时布局不破（见第 7 节）。

### V-03【P2】字号体系未被严格执行，硬编码字面量散落

**现状**：除 `Type.kt` 外，UI 层约 **63 处**直接写 `xx.sp`，同一种"辅助说明"在不同页面可能是 11/12/13sp；`Type.kt` 还**缺少 `bodySmall`、`labelMedium`** 槽位（开放问题 L8），部分文字回退到 Material 默认样式。

**影响**：排版节奏不统一，后续调字号要逐处改；缺槽位导致样式"隐性漂移"。

**建议**：
1. 补齐 `bodySmall`、`labelMedium` 等缺失槽位；
2. 用样式 Token 替换硬编码 sp，建立"标题/正文/辅助/标签"四级固定字号；
3. lint/评审规则：新增文字默认走 `MaterialTheme.typography`，硬编码 sp 需说明理由。

### V-04【P2】二级页顶栏未统一，inset 与视觉靠各页自觉

**现状**：今日/统计/药箱已用 `CarroMedTopAppBar`，但**设置、药品详情、提醒设置、库存、补药、添加编辑、记录详情**仍直接用 Material `TopAppBar`。

**影响**：视觉（页名粗细、背景色、返回样式）与状态栏 inset 处理不统一；此前已实际发生"标题下移 63px""AppBar inset 重复计算"等缺陷（见 `ANALYSIS-APPBAR-INSET-20260930.md`），根因就是各页手写顶栏。

**建议**：按 `PLAN-TITLEBAR-STANDARDIZATION-20260930.md` 全部收敛到 `CarroMedTopAppBar`；表单页统一"取消/保存"模式作为组件变体；验收以走查截图逐页比对。

### V-05【P2】详情页分类标签用"可点击样式"但无点击行为

**现状**：药品详情页分类/剂型标签使用 `AssistChip`（视觉为可点击胶囊）但 `onClick = {}` 为空。

**影响**：视觉上"可点"、实际无反应，违反"所见即可操作"的一致性，用户会以为按钮失灵。

**建议**：纯展示标签改用无点击态的 `Surface`/`SuggestionChip(只读样式)`，去掉涟漪；若希望可点（如按分类筛选），则补上筛选行为。

### V-06【P2】配色与卡片层级总体良好，但需收敛"同色多透明度"用法

**现状**：色彩 Token 完整、深浅色双套齐备（`Color.kt`），状态色语义清晰；但多处用 `xxxContainer.copy(alpha=…)` 现场调透明度（如提醒/补录页 0.3/0.35/0.4/0.45 多种取值）。

**影响**：同语义底色在不同页面明度不一，深色模式下 alpha 叠加还可能出现对比不足。

**建议**：把常用底色沉淀为固定 Token（弱底/中底/强底三档），减少 alpha 现场取值；关键文字与底色组合做对比度校验（见第 7 节）。

## 6. 交互反馈与状态可见性

### I-01【P0】锁屏"全屏闹钟"未实现——与第一承诺差距最大的体验缺口

**现状**：
- FINAL-PRODUCT D-11、FINAL-UI §八（灭屏全屏弹窗）、M-03 均承诺锁屏全屏提醒；
- 实际**没有闹钟 Activity**（`AndroidManifest.xml` 仅注册 `MainActivity`），通知**未调用 `setFullScreenIntent`**；`ReminderSettings.kt:19` 的注释自承"用户以为开了锁屏全屏弹窗，实际什么都没有"；
- 灭屏到点仅呈现 heads-up 横幅 + 通知渠道的**一次性默认提示音**，**无循环铃声、无渐强、无大按钮确认**。

**影响**：
1. 手机静音/勿扰/放包里/深睡时，一条横幅 + 短音极易被忽略——直接动摇"到点一定响"的第一承诺；
2. 老人、听障、关键药物（抗排异、降压、抗凝）场景风险尤高；
3. 国内长辈向产品（药管家）已把"**闹钟级提醒、穿透静音与专注模式、超大字高对比**"作为头号卖点，本产品在此项明显落后。

**建议（发布前必做）**：
1. 新增**独立闹钟页（如 `AlarmActivity`）**，通过通知 `setFullScreenIntent` 在锁屏/灭屏上全屏拉起；
2. 全屏页采用**闹钟级体验**：大号药名/剂量/时间、**循环或渐强铃声直到操作**、震动；超大主按钮"**我已吃药**"（≥60dp 高），次按钮"推迟 10/30 分钟""跳过"；
3. 关键药（已有的"重要提醒"标记）默认开启全屏 + 穿透勿扰（`setAlarmClock` / DND bypass，按权限与厂商能力分级）；
4. 锁屏隐私三档（I-03）作用于全屏页与通知；
5. 明确并在健康检查页说明系统边界（Force Stop、厂商后台清理后失效），配合 U-03 徽标做可见提示。

### I-02【P1】无铃声 / 震动模式选择，提醒"响度"不可控

**现状**：FINAL-UI §八 承诺"提醒铃声与震动模式（跟随系统 / 温和药铃 / 强提醒急促音）"。实际设置页无该入口，通知声音由渠道默认决定、用户不可改。

**影响**：用户无法按药品重要性或睡眠场景选择"温和/强提醒"，也无法换一个更醒目的铃声；对"关键药要吵、保健药要轻"的真实需求无能为力。

**建议**：
1. 设置页提供铃声选择（系统闹钟铃声/通知铃声/自定义）与震动模式（关/标准/强）；
2. 支持**全局默认 + 单药覆盖**（与现有"推迟时长跟随全局/专属"的交互模式保持一致，体验已有先例）；
3. 注意 Android 通知渠道一经创建参数不可改，切换铃声需重建渠道或在发送时按渠道/声音策略处理（项目已有双渠道经验可复用）。

### I-03【P1】锁屏通知隐私三档未实现

**现状**：D-12 承诺"完整显示 / 仅显示『该吃药了』 / 隐藏"三档（默认完整）。实际 `strings.xml` 无相关文案、设置页无入口，通知一律显示完整药名与剂量。

**影响**：注重隐私的用户在锁屏暴露病种/药名（如精神类、传染病用药），缺少最基本的遮挡；这是产品已拍板但未交付的能力。

**建议**：设置页提供三档选择，作用于通知标题/正文与全屏闹钟页；"仅该吃药了"隐藏药名剂量、点解锁后可见；与 I-01 全屏页同步实现。

### I-04【P2】无应用内主题/深色模式开关

**现状**：`Theme.kt:74` 深色主题仅 `isSystemInDarkTheme()` 跟随系统，无应用内"浅色/深色/跟随系统"开关；FINAL-UI §二 规定设置含"主题"。

**建议**：设置页提供三选主题开关，偏好持久化到 `AppSetting`；动态取色（Material You）可作为可选开关。成本低、能补全设置完整度。

### I-05【P2】二级页返回后数据不自动刷新

**现状**：开放问题 M9 已记录：历史、库存、详情等页为进页一次性 `load()`，返回不重载；全 App 仅健康检查页有 `ON_RESUME` 重载。

**影响**：补药/盘点/改计划后返回，旧页面可能显示过期数据，用户怀疑"没保存成功"。

**建议**：相关 ViewModel 改 Flow 数据源（`observe*`，由 Room 失效追踪自动驱动），比逐页贴 `ON_RESUME` 更可靠；走查补"入库返回即时正确"断言。

### I-06【P2】"今日已全部完成"缺少强完成态与情绪价值

**现状**：待服清空后仅显示一张普通卡片"今日已完成"（`TodayScreen.kt:304-327`），无进度环/鼓励态；连续打卡（streak）入口在小徽章里，不够显性。

**影响**：完成一天用药是值得正向强化的时刻，当前反馈偏平淡，未利用好"成就—坚持"的留存抓手（竞品普遍在此做轻庆祝与连击）。

**建议**：全部完成时展示轻量完成态（今日进度环满 + 一句鼓励 + 连续天数），克制不浮夸；连续打卡保持现状的非压力式表达，避免"断签焦虑"。

## 7. 可访问性与适老化

### A-01【P1】部分关键控件触控热区 < 48dp

**现状**：实测 12 处控件尺寸/高度落在 30–47dp：今日打卡按钮为 **42dp** `IconButton`、详情页暂停按钮 **46dp**、添加/详情页若干图标按钮偏小。

**影响**：违背自家"触控目标 ≥48dp"与老人/运动单手场景的防误触要求；图标按钮视觉小、可点区域也小，容易点空或误触相邻项。

**建议**：打卡圆钮可保持视觉 42dp 图标、但**外扩可点区域到 ≥48dp**；所有 `IconButton` 默认按 48dp 盒模型；走查以控件实际可点尺寸为准（而非图标尺寸）。

### A-02【P1】TalkBack 支持未系统审计，28 处 contentDescription=null 需定性

**现状**：全 UI 有 28 处 `contentDescription = null`。其中纯装饰性图标（卡片角标、分隔图标）置空合理，但**功能性图标按钮**若置空，屏幕阅读器将读不出操作；打卡圆环是否向 TalkBack 播报"药品 + 已服用/待服用 + 剂量"状态（FINAL-UI §十五）尚未验证。

**建议**：
1. 逐处审计：功能性按钮必须有语义描述（可用现成的 `xxx_cd_` 资源），装饰性图标显式标注并合并到父元素语义；
2. 打卡项用 `semantics` 合并"药名、时间、剂量、状态、打卡动作"为一条可读卡片，状态变化时 TalkBack 能读出"已服用"；
3. 把"关键流程可纯 TalkBack 走通"列入验收。

### A-03【P2】大字号（130%–200%）布局未验证

**现状**：FINAL-UI §十五 要求 200% 字号下布局不破碎，目前未见验证记录；多列行（日期+时间、剂量+单位）在大字号下可能挤压。

**建议**：在 130%/175%/200% 系统字号下走查今日、详情、补录、统计；多列行允许换行/纵向堆叠，关键按钮不被压缩；纳入走查脚本。

### A-04【P2】对比度需在深色模式与 alpha 底色上复核

**现状**：状态色 + 形状冗余整体良好，但 `copy(alpha=…)` 的弱底色（见 V-06）与小号文字组合，可能出现对比度低于 4.5:1。

**建议**：对"正文/辅助文字 × 各容器底色"做对比度检查（尤其实测深色模式），不达标则提高文字明度或底色不透明度。

### 值得保留的优点

- **不依赖精细手势**：打卡为单击，已移除"长按 sheet"等隐蔽手势，老人可用；
- **状态不只靠颜色**：圆环、对勾、跳过/过期形状 + 文字多重冗余，色盲友好；
- **药品色与状态色分离**：自选药品色不承载语义，符合规范。

## 8. 首次启动与引导

### O-01【P1】三步 Onboarding 未实现，仅有内联提示卡

**现状**：M-10 规定首启 3 步引导（添加第一个药品 → 设时间与提醒并触发健康检查 → 库存可跳过）。实际无独立引导，仅在今日空状态内联一张 `FirstRunGuideCard`。

**影响**：新用户缺少"这个 App 能做什么、第一步做什么、为什么要授权"的完整上下文，上手依赖自行摸索。

**建议**：
1. 轻量实现首启引导（可 1–3 页可跳过）：讲清"到点提醒—打卡—库存/统计"价值，主按钮"添加第一个药品"；
2. 把"设时间与提醒"并入首次加药流程（与 F-01 一并解决），完成首个药品后再引导权限与健康检查；
3. 预置常见药品模板/分类，降低首次录入成本（FINAL-UI §13）。

### O-02【P1】通知权限在冷启动直接申请，缺少前置说明

**现状**：`MainActivity.kt:37` 启动即 `requestNotificationPermissionIfNeeded()`，未授权结果"不阻塞主流程"。

**影响**：用户尚未理解 App 价值时就被弹权限，拒绝率高；一旦拒绝又缺乏有效引导，提醒直接哑火，与第一承诺冲突。

**建议**：
1. 权限申请**延后到有上下文的时刻**（如首次设置提醒/首个药品保存时），先用一屏说明"为什么需要通知权限（到点提醒你吃药）"，再触发系统弹窗；
2. 被拒后在今日页用健康徽标/横幅持续、温和地引导（而非反复弹），并提供一键跳设置；
3. 精确闹钟、电池白名单等同样遵循"说明—申请—可稍后—可见提示"的节奏（健康检查页已具备跳转能力）。

### O-03【P2】缺少"数据仅存本机、卸载即清除、请定期备份"的首次提示

**现状**：FINAL-UI §13 要求首次明确备份与数据风险；当前未见该提示（设置页有备份能力，但首启无提醒）。

**建议**：首启或首次进入设置时轻提示一次"数据只存在本机，卸载/清除会丢失，建议定期备份"，并提供"立即备份"；可与自动滚动备份（D-13）联动。

### 9.2 各竞品值得借鉴的点

- **Medisafe**：① **Medfriend**——漏服 30 分钟未确认即通知照护者（本产品虽战略不做社交，但其"漏服升级"逻辑可用于**本地**更强提醒：连续未响应→首页红色警示+升级铃声，对应 P1 backlog）；② **药品照片/外形辨识**，避免吃错药；③ 药物相互作用检查；④ 复杂排程与自定义通知音；⑤ 面向医生的服药报告。
- **MyTherapy**：① **药品数据库 + 条码扫码**快速建档，手填兜底；② **自动文档化**每次服用/跳过，笔记随单次记录；③ 20+ 项健康日记；④ **一次性码分享报告**；⑤ 无广告、有学术机构背书的依从性方法论。
- **药管家（国内，最贴近本产品长辈场景）**：① **超大字体、高对比**；② **闹钟级提醒穿透静音/专注**；③ **三步内完成打卡、打错可快速改**；④ 家人远程监护；⑤ 买断制、主打"给爸妈"。其"**大字 + 穿透 + 三步打卡**"正是本产品适老化应补齐的三块。
- **i药管家**：复诊提醒、家人提醒、家庭药箱、电子病历、指标跟踪的一体化（本产品可参考其"复诊提醒"作为未来低成本增量）。
- **用药助手（丁香园）**：权威药品说明书/禁忌数据库——本产品不做数据库，但可佐证"说明书、注意事项"是用户刚需，详情页的说明/禁忌区块应持续做好（现状方向正确）。
- **Round Health（设计标杆）**：极简到"**下一次服药 + 还剩多久**"的单一动作，默认安全、操作极轻；印证本产品"action-first、只呈现接下来做什么"的方向，也提示今日页可进一步突出"下一次服药"的时间与一键操作。

### 9.3 差距分类（避免误判）

- **战略取舍（不补、保持定力）**：云同步/账号、家人社交监督、药物相互作用库、健康指标日记、AI 问诊——这些与"纯本地、仅用药、极简"定位冲突，**不应因竞品有就跟风**。
- **执行缺口（应补，已承诺）**：全屏闹钟、铃声选择、一把药分组、合并通知、健康徽标、隐私三档、设置可达性——**这是本次竞品对照真正要还的债**。
- **可低成本借鉴的增量（建议进 backlog）**：漏服**本地**升级提醒（不依赖社交）、复诊提醒、药品照片/外形备注、扫码/药品库（若未来愿引入本地数据包）。

## 11. 改进路线图（建议排期）

### 阶段一：还"提醒可靠"的核心债（最高优先）

1. **I-01 全屏闹钟**：新增 `AlarmActivity` + `setFullScreenIntent` + 循环/渐强铃声 + 超大"我已吃药/推迟/跳过"，关键药默认开启；
2. **U-01 设置回今日页** + **U-03 健康徽标**：让设置与健康检查一触即达、降级状态首页可见；
3. **F-01 建药流**：创建流程内联最简提醒（默认每天 1 次 + 时间），保证"建档即会响"。

> 出口标准：新建一个药 → 到点锁屏全屏响铃 → 一键确认，全链路在真机（含灭屏、静音、重启、杀后台）走通且健康徽标如实反映状态。

### 阶段二：补"一把药"与个性化（高频效率）

4. **F-02 + F-03**：统一分组判据，App 内分组批量确认 + 通知合并"全部已吃"；
5. **I-02 铃声/震动** + **I-03 隐私三档**：全局默认 + 单药覆盖；
6. **F-04 5 秒 Undo** + **F-05 补录语义拍板**：让纠错即时、结果可预期。

### 阶段三：适老化与首次体验收口

7. **V-01 品牌通知图标**、**V-02 基础字号上调**、**A-01 热区 ≥48dp**；
8. **O-01 轻 Onboarding** + **O-02 权限延后到有上下文** + **O-03 备份提示**；
9. **A-02 TalkBack 审计**、**A-03 大字号验证**、**A-04 对比度实测**。

### 阶段四：视觉与工程一致性打磨

10. **V-03/V-04/V-06**：补齐 Type 槽位、收敛硬编码 sp、统一顶栏、沉淀色彩 Token；
11. **F-06 触觉反馈**、**I-04 主题开关**、**I-05 返回刷新**、**I-06 完成态**、**U-04 文档对齐**。

> 每个阶段都应遵循 AGENTS.md 的验收闭环：**debug + release 双编译、单测全绿、改动涉及界面必亲眼看图（走查截图）、变更记录追加摘要**；新增页面/入口同步登记进走查脚本。

## 12. 结语

CarroMed 已经拥有同类产品里罕见的**正确内核**——三层解耦、事实不可变、会计式账本、离线隐私优先，这些是"长期可信赖"的地基，应当坚持，不被竞品的功能堆砌带偏。

当前差距不在"想没想清楚"，而在**"承诺的体验有没有交付到用户指尖"**：当锁屏全屏闹钟真正响起、设置与健康状态在首页可见、新建药品即可放心等它提醒时，"到点一定响、记录永不丢"才从文档承诺变成用户可感知、可验证的事实。建议按本报告"先还提醒债 → 再补一把药 → 收口适老化 → 最后打磨一致性"的顺序推进，用一到两个迭代把产品从"骨架先进"推进到"体验可靠"。
