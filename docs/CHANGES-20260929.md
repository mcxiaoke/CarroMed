## UX 改造第 2 步：服药记录可改可撤销

时间戳：2026-09-29 17:09 (GMT+8)

**测试 410 项 / 45 套全绿**（新增 26 项）；`assembleDebug` + `compileReleaseKotlin` 通过；
模拟器实测：把一条临时用药从 1 片改成 2.5 片，首页横幅 / 两张待服卡 / 台账**同时**
变成 3.50 片（台账 `SUM = 3500`，I2 成立）。

### 写测试时当场抓到的算错

改剂量的差额我第一版写成 `net - 新剂量`。`net` 是负数（`-旧剂量`），
于是"1 片改成 2 片"算出**共扣 3 片**。被 `DoseRecordEditTest` 拦下：

```
expected: -1000
but was : -3000
```

正确是 `旧 - 新`：目标是把净额从 `-旧` 挪到 `-新`。注释里写明了
"不能参与 net 运算"，因为这个错误**编译通过、逻辑看着也通**，只是账实分叉。

### 顺带补上的两个真实缺口

- **PRN 记录此前无撤销路径**：`undoDose` 靠槽位定位，补录记录没有槽位。
  新增 `undoManualDose(recordId)`，有槽位时委托给 `undoDose`（连槽位一起退回
  PENDING，否则下一次打卡会被幂等锚点挡掉）。
- **三条改写型 Query 被守门测试当场拦下**：`AppendOnlyFactTableTest` 的白名单
  断言的是**集合相等**，每次新增都变红，逼人回来论证并补专属用例钉死
  "只翻一列 + 幂等"。

### 槽位来源的记录不许改时间 / 剂量

事实与槽位的时点、剂量是配对的，单独改事实会让两处各说一套（与 C-40 同类）。
正确做法是撤销后重新打卡。**服务层也必须挡住**——光靠 UI 不提供入口，
下一次有人加个快捷指令就绕过去了。

### 超窗记录：整块不渲染，而不是置灰

置灰会让人以为"过两天就能改"，而实际上永远不能——那是比灰按钮更坏的承诺。
2 天窗口抽成纯函数 `isWithinEditWindow` 并单测，判据是 `age in 0..2`，
所以**未来时间戳也落在窗外**（坏数据不会变成"永远可改"）。

## UX 改造第 1 步：服药流水跨月分页

时间戳：2026-09-29 16:14 (GMT+8)

**测试 384 项 / 43 套全绿**（新增 7 项）；`assembleDebug` + `compileReleaseKotlin` 通过。
方案见 `docs/UX-PLAN-20260929.md`。

### 用户指出的一处设计缺陷

进展页的第二个 tab 叫「今日服药流水」，但**首页「今日」Tab 干的就是这件事** ——
同一份数据在两个地方看，进展页的独有价值（跨时间看趋势）完全没兑现。

### 换数据源时发现更大的问题

原实现的流水取的是 `todaySlots`（**排班**），不是**事实**。于是
**手动补录的服药（`slot_id == null`）从来没在流水里出现过** ——
PRN 药吃完药，今日清单查得到、进展页看不到。跨月改造顺带修掉：
数据源换成 `dose_records`，两个来源一并覆盖。

副作用也是对的：**未打卡的 PENDING 槽位不再出现**。
「流水」记录的是已发生的事实，待服清单是首页的职责。

### keyset 游标，不用 OFFSET

翻页期间用户随时可能撤销记录，而撤销在**前页**发生就会让 OFFSET 整段错位、
静默漏记录。改用 `actual_ts < :cursor` 游标分页，对数据变更免疫。
`<` 而非 `<=` 是**正确性要求**——时间戳精确到毫秒，同刻记录会在相邻两页各出现一次。

变异验证：把 `<` 改成 `<=` ⇒ 3 项测试变红；`DESC` 改成 `ASC` ⇒ 5 项变红。

### 无需升 schema

`dose_records` 早已有 `Index(value = ["actual_ts"])`，游标查询走索引。
**全流程不需要动 `AppDatabase.version`。**

### 顺手补上一个真实缺口

`DoseTrackingDao.undoDose(slotId)` 靠槽位定位，**手动补录的记录没有槽位**，
也就是 PRN 记录当前**没有任何撤销路径**。新增 `markReverted(recordId)`
（按记录 id 撤销，语义与按槽位完全一致，只翻 `status` 一列且幂等）。

它被 `AppendOnlyFactTableTest` 的白名单守门测试当场拦下 ——
那条测试断言的是**集合相等**，新增改写型 Query 必然变红，逼人回来论证。
已加入白名单，并补一条专属用例把语义钉死（除 `status` 外每列不变，含 `note`）。

### 三处"坏数据只坏在一处"

同一类缺陷的三个变体，共同点是**静默降级**：数据已经坏了，
但坏的那一处被兜底掩盖，于是用户看到的是一个**他没设置过的行为**。

| 位置 | 旧行为 | 现在 |
| :--- | :--- | :--- |
| 坏时点串写库 | 入口不校验格式 → 投影层回退 08:00 → 闹钟每天 08:00 响，界面写空 | 入口拒绝（表单 + 领域层双重），事务整体回滚 |
| 坏时点串投影（C-40） | `scheduledTs` 用回退值、`scheduledTime` 留坏串 ⇒ **同一槽位自称两个时间** | 两字段说同一句话，坏值也可见 |
| 演示数据打卡 | 事实行 COMPLETED 但无台账 ⇒ 「打卡了库存不减」的假象 | 补 `TAKEN_DEDUCT` 流水，守 I2 |

其中"入口不校验格式"是**新发现**的：既有校验只查重复时点与剂量，
不查时点格式，而空时点正是用户清空时间框后的落库样子。
测试 `daily_rejectsSingleSlotWithBlankTime` 复现了它 ——
`timeSlots.isEmpty()` 对"列表里有一条空时点"返回 **false**，校验直接放行。

### 对比度：1.68:1 → 8.30:1

进展页"部分完成"的圆点是 `SuccessGreen@45%` 底 + **白字**，
合成后 `#96D6AE` 底白字对比度 **1.68:1**。这是**文字**（显示 `1/2`），
适用 WCAG 1.4.3 的 4.5:1（大字豁免要 18.66sp，这里只有 9sp，够不着）。
改成 `SuccessGreenContainer` 底 + `OnSuccessGreenContainer` 字，实测 **8.30:1**。
顺带让"部分比全部浅一档"的视觉分级由底色承担，不再靠调 alpha 算出来。

## M2–M5 输入防御 / 口径统一 / 时间正确性 / 备份链路 / 门禁

### 途中发现并修掉的一个"编译与单测都发现不了"的崩溃

给 `StatsViewModel` 加了第二个带默认值的构造参数（为测试注入内存库），
**点开统计页必崩**：

```
Caused by: java.lang.NoSuchMethodException: StatsViewModel.<init> [class android.app.Application]
```

`viewModel()` 走 `AndroidViewModelFactory`，用 `getConstructor(Application)` **反射**找构造器，
而 Kotlin 的**默认参数不会生成单参 Java 构造器**。编译通过、单测全绿、只有真机点一下才炸。
修法是**保持 ViewModel 单参构造器不变**，把可测部分抽成普通类 `StatsStateBuilder`。
这条纪律已写进该类 KDoc：**不要给 `AndroidViewModel` 的构造器加参数**。

### 决策点落地

| 决策 | 落地方式 |
| :--- | :--- |
| D 暂停语义 | 「暂停到明天」= `paused_until = 今天`（含当天 ⇒ 明天恢复），不再压两天 |
| E 预警线 0 | 统一为「关闭告警」；「7 天内必提醒」收成显式开关，默认关 |
| E 归档药统计 | 归档过滤下沉到聚合 SQL，**默认不进依从率分母** |

### 逐批要点

**M2 输入与记账防御**：剂量草稿改 `String`（`Float` 表达不了"正在输入 `0.`"→小数点打不出来），
新增 `DecimalInput` 三层防线（字符过滤 / 提交前 `>0` / 领域层 `require`）；

`logManualDose` / `refillStock` / `takeDose` 负数全拒（负剂量打卡 = 给库存**加**药），
`calibrateStock` 拒负但接受 0（"刚好用完"是合法操作）。5 个 VM 补 `runCatching` + 同步 `isSaving` 闸门。

**M3 时间正确性**：`updateDerivedColumns` 增加 `scheduled_ts` 列 ——
它是投影的**纯函数输出**却依赖 `zoneId`，此前全工程无人写它，于是"每天 08:00"飞到纽约后**仍按北京时间响**。

**M4 口径统一**：`StatsEngine` 收敛三处五份重复实现 ——
`scheduledDaysPerWeek`（详情页那份是**坏的**：`CYCLE` 写死 5、`INTERVAL` 无下界导致负库存显示 ∞ 且永不告警）、

统计页挂「已产生结论的槽位数」探针，**跳过后数字立刻变化**（此前不刷新）。

**M5 备份与恢复**：CSV 加**公式注入**防护（`=1+1` 备注在 Excel 里会被求值成 2）
并处理 `\r`；`getAllTimes()` 改为只导出 active 计划的时点（否则每改一次计划备份就**线性膨胀**）；
`getActivePolicyForMedication` 补 `ORDER BY version DESC, id DESC`；
校验层补三类"键不是自增 id"的重复检查；`List<String>` 转换器从 `|||` 分隔改 JSON 数组
（用户注意事项里写 `|||` 会被**静默**拆成两条）。

**M6 门禁**：`StatsUnitGroupingTest` 原先在测试里**重写**了一遍分组逻辑（影子实现，
生产改回旧 bug 仍全绿）。抽出 `StatsEngine.groupByUnit` 后**第一版仍然失败** ——
只测抽出来的函数，生产代码不调它测试照样绿。于是新增

### 顺手修掉的并发审查新发现（round2 报告 N3/N4/N11a）

- **N4（第三层兜底自己饿死自己）**：`CarroMedApp.onCreate` 改用 `KEEP` 而非 `REPLACE`。
  WorkManager 冷启动进程执行周期任务时 `onCreate` 先跑，`REPLACE` 会把**正要执行的那次**
  任务取消掉并重置 15 分钟计时 —— 而"进程已死"恰是这个 Worker 最需要生效的场景。
  清数据场景 `KEEP` 同样能自愈（WorkManager 自己的库也被清掉了，没有既有任务）；
  升级/换包由 `BootReceiver`（`MY_PACKAGE_REPLACED`）显式 `REPLACE` 负责。

### #1 + #4：撤销的冲正判据（同一函数两个缺陷，一起修）

`undoDose` 原先读一条**"代表事实"**（`getRecordBySlotId` = `ORDER BY id ASC LIMIT 1`，
即**最早**那条）来决定要不要冲正。一个槽位可以有多条事实（`takeDose` 每次插一条，
`undoDose` 从不删行 —— I11 要求「吃过的药永不丢失」），于是：

| 步骤 | 事实 #1 | 事实 #2 | 台账 |
| :--- | :--- | :--- | :--- |
| 打卡 | `COMPLETED` | — | −2 |
| 撤销 | `REVERTED` | — | +2（回到原值）|
| 再打卡 | `REVERTED` | `COMPLETED` | −2 |
| **再撤销** | `REVERTED` | `REVERTED` | **不冲正** ⇒ 账面凭空少 2 |

**无任何异常**，`SUM(change_amount) == balance` 依然成立（I1 是恒等式，拦不住），
台账里「扣减 / 冲正 / 扣减」三行看起来完全合理。

既有测试 `I4 重复撤销不会二次冲正` 只覆盖了「**不重新打卡**就再撤销」——
那种情况下"不冲正"恰恰是正确行为，所以缺陷完全藏住了。

#4 是同一位置的第二个缺陷：冲正判据里的 `medication.isStockTracked` 读的是
**药品当前的开关**，而扣减发生时记的是**当时的开关**：

| 打卡时 | 撤销时 | 后果 |
| :--- | :--- | :--- |
| 未追踪（没扣） | 已追踪 | 冲正一条不存在的扣减 ⇒ **账面凭空多出** |
| 已追踪（扣了） | 未追踪 | 不冲正 ⇒ **扣减永远回不来** |

**正解**：判据改成「**这条事实的台账净额**」——
`SUM(change_amount WHERE record_id = ?)`，负数表示仍欠扣，补一条等额冲正。

这个口径同时解决两个缺陷，而且**天然幂等**：冲正后净额变 0，重复撤销不会二次冲正。
它也不需要读药品的当前状态，所以用户中途改追踪开关也不再影响冲正。

### #2：量纲混用的第 5 次（且是唯一一次落在 DAO 边界）

`getSumDoseTakenForMedication` 的 `SUM(dose_taken)` 返回**整数毫单位**，
签名却声明成 `Float?` —— 类型上完全无法与展示值区分，于是
`MedicationDetailViewModel` 的 `?: 0f` 直接当成片数用了。

**模拟器实测**：吃过 1 片的药，详情页显示「近 30 天共消耗 **1000 片**」。

关键在于**这个 bug 在 UI 走查看不出来** —— 演示数据里每个药近 30 天都是 `0 片`，
没有一条路径会走到那个数字。是靠手工点进一个"吃过药"的药的详情页才看到的。

前 4 次量纲混用都在 UI 层（手写 `/1000f`），这次落在 DAO 上 ——
而 DAO 边界是**唯一本该拦住**它的地方，因为实体的 `doseAmount: Int` 本来带着单位信息，
是 `Float?` 这个签名把它抹掉了。

新增 `DaoUnitScaleTest` 守「DAO 聚合的返回值一律是毫单位」，
并加了一条「同一条事实的两个查询实现必须给出同一个数」。

### #3：改剂量后已排好的槽位不更新

`reconcileSchedule` 的 diff 键是**日历** `(scheduledDate, scheduledTime)`，
命中 `existingKeys` 的槽位走"留"分支只插不更新，而 `DoseSlotDao.update`
**在生产代码里零调用** —— 槽位的 `dose_amount` 在其整个生命周期内被冻结在创建时的值。

改「服药时刻」不受影响（key 变化 ⇒ 删旧插新），漏的恰恰是
「**时刻不变、剂量变了**」这条最高频的路径。

后果是双重的：`dose_records.dose_taken` 是**不可变事实**（I11 不许事后修正），
错误被永久固化；同时台账长期少扣。

新增 `updateDerivedColumns(slotId, doseMilli, policyId)`，
`WHERE status IN ('PENDING','SNOOZED')` 的守卫写在 **SQL** 里而不是调用方 ——
与 `markCompletedIfOpen` / `markSkippedIfOpen` 同一套风格，
于是"既成事实不会被对账改动"成为一条**结构性**保证。

### #5：疗程结束日期清不掉（最贴近用户诉求的一条）

`saveReminderPolicy` 用 `draft.endDate ?: previous?.endDate` 实现"没改就沿用"，
但 `null` 同时表达了两种意图：

| 用户操作 | 草稿 | 期望 | 旧行为 |
| :--- | :--- | :--- | :--- |
| 没碰结束日 | `endDate = null` | 沿用原值 | ✅ |
| **关掉开关要清空** | `endDate = null` | 清空 | ❌ **沿用原值** |

而提醒设置页**确实提供**清空入口（`Switch` + 日期框 clear 图标），
关掉 Switch 后传的就是 `endDate = null`。

后果不只是"开关看着关了但没生效"：
抗生素设了「疗程至 10-05」，疗程结束后医生说继续吃，用户关掉开关保存 ——
`endDate` 仍写回 `2026-10-05`，**10-06 起所有提醒静默消失**，
而用户以为自己已经改成长期服用了。这正是"提醒不能漏"的反面。

修法：加 `PolicyDraft.clearEndDate: Boolean`，让"清空"成为**必须被表达**的意图。

### #6：自己导出的备份可能被自己的校验判为不可恢复

`dose_records.slot_id` **没有真实外键**（实体只声明了 `medication_id`），
而 `reconcileSchedule` 会物理删除 `PENDING`/`SNOOZED` 槽位，
`undoDose` 留下的 `REVERTED` 事实仍带着那个 `slot_id`。

⇒ 悬空 `slot_id` **不会**让恢复崩溃（Room 无从校验一个不存在的约束），
但它与"药品/计划外键悬空"同属 `DANGLING_FK` 且 `blocksRestore = true`，
于是用户**自己导出的**备份可能在预览页就报"不可恢复"，且没有任何绕过开关：

> 打卡 → 撤销（事实 `REVERTED`，仍带 `slot_id`）→ 把服药时间 08:00 改成 09:00
> → 旧槽位被删 → 备份里那条事实就悬空了

拆成新的 `DANGLING_SLOT_REF`（不致命）。

顺带补齐 **4 张表的主键重复**检查（P2-4）：
`dose_records` / `inventory_transactions` / `schedule_policies` / `policy_times`
的回填都是 `REPLACE` ⇒ 重复主键会**静默覆盖丢行**，
而校验层原先只覆盖了 `medications` 与 `dose_slots` 两张。
`BackupProblemKind` 从 5 个增加到 10 个，`BackupResilienceTest` 的全遍历断言自动覆盖。

### #7：`snoozeSlot` 缺状态守卫 + `Quantity` 死代码

`snoozeSlot` 是同文件里唯一没把 `status IN (...)` 下沉进 SQL 的写入口。
缺了守卫的可达路径：长按卡片弹出推迟菜单的同时，通知栏的「确认已吃」被点了 →
槽位变 `COMPLETED`、事实入库、**库存已扣** → 用户再点「10 分」⇒ 被改回 `SNOOZED`
→ SNOOZE 闹钟再响一次就会插入**第二条** `COMPLETED` 事实并**二次扣减库存**。

顺带给 `snoozeMinutes` 加 `coerceIn(1, 240)`：`Int.MAX_VALUE` 分钟会溢出成一个
**已经过去**的时间戳。

### 本轮我自己的两个错误（都被测试抓住，如实记录）

#### 1. `Quantity.withUnit` 的"修复"基于一个我没验证的假设

原代码是两个分支返回同一字符串的死代码，而 KDoc 声称「中文紧贴、西文带空格」。
我据此"修复"它复用 `unitSuffix`，并顺手按 KDoc 写下了断言
`withUnit(2f, "片") == "2片"` —— 测试**立刻变红**。

原因：`'片'.first().isLetter()` 返回 **`true`**（汉字在 Unicode 里是 Letter 类），
所以中文走的一直也是"加空格"那一支。**"中文紧贴"是文档里的虚构行为**，
实际全 App 一致地带空格（今日页 `1 片`、统计页 `2 片`）。

正确做法是先把规则收敛为一条（恒加空格）、KDoc 改成描述实际，
而不是照着一句没实现过的文档去改行为。**又一次凭想象下结论。**

#### 2. 第一次写 `QuantityTest` 时把 μ 和 μ 混成两个字符

测试名里含 `..` 之类的非法字符导致编译失败，且我对"非字母开头的单位"的规则
也是想当然写的。两处都被编译器和测试直接挡下。
