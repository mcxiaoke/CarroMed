## 2026-09-28 13:45 +08:00 —— 阶段 A6：WorkManager 周期对账（兑现 FINAL-PRODUCT D-14 第三档）

依据 `docs/REMINDER-DOMAIN-REDESIGN.md` A6。这是本项目**唯一一个新增运行时依赖**的步骤。

### 为什么单独成为一步

它不是重构的一部分，而是**补上一个一直缺的产品承诺**。
混进 A3 会让"重构顺手加了个 Worker"与"兑现代码里白纸黑字写了、却零实现的能力"混在一起，回滚时无法分离。

### A6 本体

- 新增 `androidx.work:work-runtime-ktx:2.9.1`（运行时）+ `work-testing`（测试）。
- `ReconcileWorker`：无输入、无网络约束，`doWork()` 只调一次 `AlarmReconciler.rescheduleAll`。
  失败返回 `Result.retry()` 而**不是** `failure()` —— 后者等于永久放弃这一轮，
  而对账恰恰是最该重试的事（多半是数据库被另一个事务短暂占住）。
- `PeriodicWorkRequest` 15 分钟一轮（WorkManager 名义下限），`enqueueUniquePeriodicWork` 保证唯一，
  指数退避起点 10 分钟。
- 新增 `CarroMedApp : Application` 作为唯一触发点（**任何**组件拉起进程都会先执行它），
  `BootReceiver` 里再加一次 `REPLACE` 冗余覆盖"开机后进程压根没被拉起"的情况。
  WorkManager 的周期任务**不会**随 `BOOT_COMPLETED` 恢复，也不随换包恢复。

### 15 分钟是名义下限，不是保证

官方文档明确 `PeriodicWorkRequest` 的实际间隔由系统按电量优化与厂商策略决定。
所以三层保险的分工是：**视野窗口 14 天**（覆盖）→ **触发后续期**（即时）→ **本 Worker**（兜底）。
Worker 是第二层兜底，**不要**因为"有了 Worker"就削弱前两层。已写进 KDoc。

### 本轮自己抓回的一个真 bug

`reconcileSchedule` 此前是 `getActivePolicyForMedication(...) ?: return@withTransaction` **提前返回**，
于是"用户删掉了这个药的服用计划"时，窗口内已有的 PENDING 槽位**永远删不掉**：
它们不是既成事实，却被统计当成"该吃没吃"，也仍出现在今日清单里 ——
而闹钟早已被对账器撤掉，**永远不会响**。改为"无计划时把投影当成空集"，让删除逻辑照常执行。

### 本轮发现但**没有**顺手改的一个问题（已登记待拍板）

**暂停中的药品，它的待服槽位仍会出现在今日清单里，但永远不会有闹钟。**
`AlarmReconciler` 把暂停的药从 `activeMeds` 剔掉，所以它的 `reconcileSchedule` 根本不被调用；
而 `TodayViewModel` 只过滤 `is_archived`，不过滤暂停。

这是**既有问题**（A2 的 `paused_until` 与 A3 之前的对账器都是这个行为），且修法要动产品语义：

| 方案 | 效果 | 代价 |
| :--- | :--- | :--- |
| (a) 对账时也清理暂停药的未来 PENDING 槽位 | 清单变得诚实 | "暂停中"这件事对用户不可见 |
| (b) 保留槽位但标注"已暂停" | 用户知道自己为什么看不到提醒 | 要新增 UI 状态，超出 A6 范围 |

已记入 `docs/REMINDER-DOMAIN-REDESIGN.md` §9 待拍板项，**没有**擅自决定。

### 一个测试基建坑：`AppDatabase` 单例跨 Robolectric 测试方法泄漏

`doWork()` 内部走 `AppDatabase.getInstance(context)`，那是 `companion object` 里的静态单例。
Robolectric 每个测试方法都重建 `Application` 与沙箱文件系统，但**单例不重置**，
于是后一个测试拿到的 DB 指向已被拆掉的句柄而抛异常 ——
`doWork` 的 `catch (Throwable) → Result.retry()` 把它吞成了一次"退避重试"。

也就是说**写出来的失败信息（Retry）和真实原因完全无关**，比不测更糟。
所以 `ReconcileWorkerTest` 不断言 `doWork`，改由 `AlarmReconcilerIdempotencyTest`
用**显式传入的内存库**守 `rescheduleAll` 的幂等性（那才是 A6 真正依赖的不变量）。

## 2026-09-28 13:08 +08:00 —— 阶段 A3：闹钟内容寻址（**P0-1**）+ 周期视野（**P0-2**）+ 幂等重排（P1-5）

### A3-5　闹钟身份改内容寻址 —— **P0-1 修掉**

`AlarmScheduler` 此前用算术编码区分「准点 / 提前」两类闹钟：
`requestCode = if (advance) slotId*10+1 else slotId`，注释写着
「`slotId` 是全局唯一自增主键，因此两个号段天然不相交」。

**这句话在数学上是错的。** `10N+1` 与 `M` 在 `M ≡ 1 (mod 10)` 时必然相等，
而 `PendingIntent` 的判重是 `requestCode` + `Intent.filterEquals`（**extras 不参与**），
两个分支的 component 与 action 又完全相同。于是：

- 给槽位 1 排提前闹钟 ⇒ 覆盖掉槽位 11 的准点闹钟；
- `cancel(槽位1)` 连带杀掉槽位 11 的准点闹钟 ⇒ **静默漏提醒**。

改为 `setData(carromed://alarm/{medId}/{date}/{time}/{kind})`，
身份完全由 Intent 内容决定，`requestCode` 恒为 0。
顺带把 `kind` 独立成 `MAIN` / `ADVANCE` / `SNOOZE` 三态，
`Notifications` 据此区分文案（**P1-20**：原先提前与准点的文案一模一样）。

`Notifications` 里通知栏 Action 的算术编码**是安全的**（三个 Action 的 action 字符串互不相同，
`filterEquals` 能区分），已加注释说明差别，防止后人"顺手统一"改坏。

### A3-6　`dose_slots` 唯一约束 + 幂等 diff 重排

- `(medication_id, scheduled_date, scheduled_time)` 改为 **UNIQUE 索引**（P2-5）。
  槽位唯一性从「`reconcileSchedule` 里的内存去重」升级为**数据库不变量**。
- `insertAll` 从 `REPLACE` 改 `IGNORE`：`REPLACE` 会换 id ⇒ 换闹钟 `requestCode` ⇒ 孤儿闹钟。
- `reconcileSchedule` 从「全删未来 PENDING 再重建」改为**幂等 diff**：
  已被投影命中的槽位**保留原 id**，一行不动。

### A3-7　闹钟视野 7 → 14 天 + 触发后续期 —— **P0-2 修掉**

旧实现只排 7 天且无自续期，唯一续期途径是「用户某天打开 App」——
装好 App 后不碰它，**第 8 天的提醒全部静默消失**。
上一轮审查没抓到的原因是结构性的：`FINAL-PRODUCT:159` 的验收标准恰好是
「连续 **7 天**零漏提醒」，**验收时长等于机制边界**，测试期内不可能暴露。

现在三层保险：14 天窗口 → `AlarmReceiver` 每次响铃就地续期 → A6 周期对账兜底。

`AlarmReconciler` 重写为「**先快照、后重排、再按快照清理孤儿**」：
`reconcileSchedule` 删掉的行其闹钟原本无人取消（领域层不知道 `Context`），现在靠快照找回来。

### A3-4　6 处匿名 `ViewModelProvider.Factory` → `viewModelFactory { initializer { } }` DSL

零新依赖（`lifecycle-viewmodel-compose` 已带），净减 22 行样板。

### 顺手修掉的另一个真问题：schema 版本号

`AppDatabase.version` 4 → 5（`dose_slots` 加 UNIQUE 索引）。

**顺带查出 A1 当年漏升了版本（3 → 3）**，靠 A2 的 3 → 4 顺带补救。核实依据是反编译
`room-runtime-2.6.1.aar` 的 `androidx/room/RoomOpenHelper.class`：

- `onOpen` 只有 `super.onOpen(db); checkIdentity(db);`，**无 Exception table**；
- `checkIdentity` 在 identity hash 不匹配时 `athrow`，同样**无 Exception table**；
- 破坏性回退只挂在 `onUpgrade`（版本**变大**时）这条路径。

⇒ 版本不变而 schema 变了，`fallbackToDestructiveMigration()` **不覆盖**身份校验，
冷启动直接崩 `IllegalStateException: Room cannot verify the data integrity`。
走查脚本每次都 `--clear` 清库，所以**永远发现不了**。已在 `AppDatabase` 的 KDoc 里记下版本史。

- 补药入库复用领域层 `DoseTrackingService.refillStock`，删除 ViewModel 里重复实现的内联事务。
- 库存页的写命令从 19 列的 `updateProfile` 拆成 `updateExpiryDate` + `updateMinStockAlert`
  两条细粒度命令（原本被迫重传全部档案字段，内含 read-modify-write 竞态）。
- 删除死文件 `core/data/SampleDataSeeder.kt`（0 调用点，与 debug 版重复，
  且带着药品名错别字「环抱素」混进 release 包）。

### A1b 整数毫单位（D-7）

- 6 个金额列从 `REAL` 改为整数毫单位（1 片 = 1000）：
  `change_amount` / `balance_after` / `dose_taken` / `dose_amount` / `default_dose` / `min_stock_alert`。
  浮点加法不满足结合律，长期累加必然漂移，而余额恰是累加得来的。
- 新增值对象 `core.domain.model.Dose`（`@JvmInline value class`）：实体层用 `Int`，
  领域/UI 层用 `Dose`，转换只发生在两个边界。
- 统计页**跨单位不再求和**（P0-7）：按单位分组，只有全部同单位时才给总量大数字，
  否则逐单位并列。宁可不给数字，也不能给错数字。
- 统计消耗排名的 `mapIndexedNotNull` 索引错位修复（原会导致"第 1 名已归档时
  UI 从『2.』开始显示"）。
- 全库数量格式化统一到 `ui.component.Quantity`（此前有四套并存写法，
  同一数值在四个页面显示成四种样子）。
- 备份 JSON 字段加 `Milli` 后缀明示口径。

### 顺带修掉的产品缺陷

- `InventoryViewModel` 的频次文案此前拿 `times.size`（时点个数）当"间隔天数"渲染，
  与同页用真实 `intervalDays` 算的"预计可用天数"自相矛盾。
- 周期用药的日均消耗此前写死按 5 天/周折算，对"吃 2 停 6"会把消耗高估 20 倍。
- 编辑药品不再预填库存余额（编辑账面在语义上等于直接改账面），且不再用默认值 "10"
  污染 `minStockAlert`（0 的语义是"关闭告警"）。
- 今日页/库存页/详情页的低库存判定此前**不传** `minStockAlert`，
  引擎只剩"7 天内"一条硬规则，与用户配置的预警线不一致。
